# V0.5 — Minimal Controlled Browser Runtime

Status: proposed implementation specification. The V0.4 [spike report](../research/V0.4-spike.md) is evidence for the chosen integration, not evidence that V0.5 is implemented. This specification follows the [invariants](../architecture/INVARIANTS.md) and the [roadmap](../ROADMAP.md).

## Goal and boundary

Run one bounded browser subtask from a CLI invocation through routing, execution, and independent verification. The runtime owns permissions, deadlines, budgets, cancellation, attempt state, and the final outcome. SystemOneHarness owns the inner action loop; Browser Use is the browser backend. A deterministic decision provider must permit offline checks; a Jev run is a separate live integration check.

Preserve the existing routing-only `Task 0.1` and `reflexmesh route` behavior. Add a versioned execution input and a distinct CLI execution command. A small internal capability/executor descriptor may map the selected V0 route to the browser executor; the runtime must not depend on `Route.CUA` as its permanent executor identity. V0.5 does not require a dynamic registry, Pi/MCP/HTTP task entrypoints, desktop/Cua, self-extension, or autonomous engines.

Only an explicitly configured local test site and supported criteria are admissible in the first runnable path. An unsupported route, missing executor, unsupported verification criterion, or insufficient permission produces a bounded blocker before any browser action.

## Input and result contract

The execution input identifies the task and revision, goal, allowed executor/capability, site origin, explicit action permissions, versioned TextSlots, nonempty required acceptance criteria, and finite limits for wall time, steps, model calls, and retries. It must be validated before execution. One attempt has a unique ID; continuation would create a new attempt rather than reset the task budget. Secrets and slot values are not written into ordinary traces.

The structured result records task/revision/attempt IDs, the route decision, execution outcome, stop reason, verifier assessments (`pass`, `fail`, or `unknown` per criterion), final task outcome, remaining budget, and references to evidence and trace. `completed` requires `pass` for all required final postconditions and no violated or unknown required execution constraint. A model `finish`, harness `completed`, HTTP response, or browser click alone cannot establish completion. A verified postcondition may be `fail` before later actions; the final assessment uses fresh state.

The CLI emits one machine-readable result even when the harness fails, is cancelled, or times out. Routing-only results are never presented as executed tasks. Preserve `blocked`, `cancelled`, `incomplete`, and `unknown` distinctions rather than collapsing them into a generic failure; record a confirmed violated constraint as failure even if the page later appears to satisfy the goal.

## Runtime boundaries

1. **Admission and routing.** Validate input and supported criteria; select only eligible capabilities. `NONE` or an unavailable executor yields an explicit blocker or handoff, without invoking the browser. Once selected, bind the browser executor and a single session owner to the attempt.
2. **TextSlots.** Bind immutable slot ID + version to exact text supplied by the client. The decision provider may select a field and slot; the runtime resolves the value. Unknown, changed, or stale slot references are rejected. A slot does not grant permission to submit a form.
3. **Controlled environment.** Adapt the V0.4 `Environment` wrapper in `src/reflexmesh/runtime`. Before each `execute`, recheck cancellation, monotonic deadline, remaining limits, permission, and freshness/identity of the selected target against the relevant observation. Reject an ambiguous or stale target for re-observation; do not silently click by an old element index. Only then call the browser driver. Avoid treating the V0.4 label regex or its private `_last` lookup as a general authorization mechanism.
4. **Action accounting.** Record an action as proposed, rejected before dispatch, dispatched, returned, or outcome unknown. Link each dispatch and result to the attempt and observation. Count the applicable budget before dispatch; retries do not replenish it. A timeout or lost response after dispatch does not prove that the effect failed.
5. **Verifier and final outcome.** On the controlled site, read fresh server state/log evidence independently of SystemOneHarness. Associate each assessment with task revision, criterion, target, and observation. An unavailable verifier returns `unknown`, never `pass`. The runtime alone assigns the final task outcome.

## Cancellation, deadlines, and uncertain effects

Cancellation and deadline expiration prevent every *new* driver dispatch, including a decision returned late by Jev. They do not promise to interrupt or undo an action already dispatched. Record whether that action was dispatched before cancellation, and accept its late result as supplementary evidence. The first accepted terminal transition wins; late evidence does not reopen the attempt or authorize another action. Close or quarantine the session before another owner can issue conflicting actions while the previous call may still be running.

Use a monotonic clock for the end-to-end attempt deadline; a provider socket timeout is not a substitute. The CLI must return a bounded outcome when the deadline expires, even if the browser call cannot be interrupted; implementation must explicitly define how the outstanding call and session are observed or quarantined after return. Do not claim a hard stop of external side effects.

Never automatically retry a non-idempotent action whose effect is unknown. Reconcile using fresh authoritative state, or stop and report the uncertainty. If the state confirms no effect, a retry may be considered within the original limits; a stable deduplication key is another valid route where the backend supports it. A stale UI message is insufficient evidence of no effect.

## Acceptance checks

| ID | Scenario | Required observation |
|---|---|---|
| A1 | Navigation, settings change, and TextSlot form submission from the CLI on the local site | Independent server evidence satisfies the supplied criteria; result includes linked actions and criterion assessments. |
| A2 | Harness claims success when the server state disagrees; harness declines `finish` when the server confirms the goal | Runtime follows the verifier in both directions, subject to its execution constraints. |
| A3 | Disallowed action, unavailable capability, stale target, or substituted TextSlot | No prohibited/stale action reaches the browser; reason and attempt trace are explicit. |
| A4 | Cancellation while a decision is pending, and expiry before a delayed decision returns | No action is dispatched after the accepted stop; terminal outcome is preserved. |
| A5 | Cancellation or expiry while a driver action is in flight | No subsequent action starts; late success/failure/unknown is recorded without changing the terminal outcome; session is not handed to another owner prematurely. |
| A6 | Lost response after non-idempotent submission | No blind second submission; fresh authoritative state is checked or the outcome stays unknown. |
| A7 | Step/model-call/retry/wall-time limit, verifier unavailable, malformed upstream result | Bounded stop with a specific reason; no false `completed`. |
| A8 | Trace inspection | Task and attempt IDs, decisions, dispatches, effects, verification, and terminal reason are linked; ordinary logs exclude secrets and raw TextSlot values. |

Run the checks with a deterministic provider and fault injection first. Then run the supported end-to-end cases with Jev/Browser Use in a documented environment, recording versions, exact commands, results, and limitations. Passing deterministic tests cannot be reported as a successful live Jev run. V0.5 is complete only after its CLI path and these checks are implemented and evidenced; creating this document does not change its status in `STATUS.md` or `ROADMAP.md`.
