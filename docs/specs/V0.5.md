# V0.5 — Minimal Controlled Browser Runtime

Status: proposed implementation specification, revision 2 (2026-09-25).
Addresses [review R1–R7](../research/V0.5-spec-review.md). The [V0.4 report](../research/V0.4-spike.md) establishes the integration direction; the guarantees below require implementation and evidence. The [invariants](../architecture/INVARIANTS.md) govern this specification.

## 1. Scope and ownership

One CLI request executes one bounded subtask on a controlled local site. SystemOneHarness owns the inner action loop; Browser Use executes browser actions; ReflexMesh owns admission, permissions, counters, cancellation, terminal transitions, and verification.

Keep Task 0.1 and the routing CLI compatible. Map V0 routing output to internal executor ID `browser.soh` in an adapter; the runtime uses executor IDs, not the Route enum. Only this executor is implemented. Dynamic discovery, self-extension, Pi/MCP/HTTP task interfaces, desktop, resumable attempts, and autonomous engines are later work.

The first supported environment is Linux/WSL with a fresh browser process/profile per attempt, pinned SystemOneHarness/Browser Use versions, and a loopback fixture. Existing browser sessions are not attached or reused. Required dependency access stays in the browser adapter and must be proven on the pinned version.

## 2. Request and CLI (R3)

Add `reflexmesh run --input FILE --output-dir DIR --routing-provider stub|jevrouter --action-provider script|jev`. Both providers must be explicit. Script actions are test fixtures supplied by `--script FILE`, required only with the script action provider. Preserve the existing routing command and its options.

Proposed execution input:

```json
{
  "schema_version": "execution-task/0.1",
  "task_id": "form-001",
  "revision": 1,
  "goal": "Fill in the contact form and send it once.",
  "allowed_executors": ["browser.soh"],
  "fixture": {"origin": "http://127.0.0.1:8765", "run_id": "run-001"},
  "start_path": "/form",
  "permissions": ["navigate", "type_text", "submit_form"],
  "text_slots": [
    {"id": "name", "version": 1, "value": "Test User"},
    {"id": "email", "version": 1, "value": "test@example.com"}
  ],
  "criteria": [
    {"id": "sent", "kind": "postcondition", "predicate": "form_submitted_once",
     "args": {"name_slot": "name@1", "email_slot": "email@1"}}
  ],
  "limits": {"wall_seconds": 60, "max_steps": 32, "max_model_calls": 64, "max_action_retries": 0}
}
```

All shown fields are required. Reject extra fields, duplicate JSON keys, invalid enum values, invalid slot references, duplicate criterion IDs, invalid types, nonfinite numbers, and empty criteria. Revisions/versions and step/call limits are positive integers; booleans are not integers. Wall time is finite and positive. Automatic action retries must be exactly zero. Limit UTF-8 input to 64 KiB. Slot ID/version pairs are unique and IDs cannot contain @. Task/slot/criterion IDs are nonempty strings; slot values and goal are strings, with a nonempty goal. Executors are nonempty string IDs; unsupported IDs are an availability blocker, not malformed syntax.

Paths must be declared fixture paths under the exact configured loopback HTTP origin, without query, fragment, or traversal. Only 127.0.0.1 and an explicit valid port are accepted in V0.5. Required input collections have no duplicate executors or permissions. Criteria arguments follow section 8; unknown predicate names are an admission blocker. Criteria kind is postcondition in V0.5.

Invalid input produces an error JSON on stderr with code `invalid_input`, exit 2, and no attempt. An unwritable output directory produces `output_unavailable`, exit 2, before execution. Valid but unsupported capabilities/predicates produce blocked attempts. Confirm the fixture run ID before browser startup.

Create an attempt ID and start the monotonic deadline after structural validation and output preparation, before availability checks, routing, startup, or verification. All those operations consume the same deadline. SIGINT signals the supervisor; the embedded runner exposes `cancel(attempt_id)` with identical semantics. Acceptance occurs at the synchronized transition in section 4, not when a signal first arrives.

Emit one result JSON on stdout after bounded collection/cleanup; write result.json, trace.jsonl, and redacted evidence into DIR. Abrupt process termination is outside the graceful cancellation contract. Runtime output failure prevents an unqualified success: preserve whatever evidence is available and return failed/output_error if the result can still be emitted.

## 3. Process lifetime and late evidence (R1)

The CLI supervisor owns the result and artifacts. One child worker performs routing and then SystemOneHarness/Browser Use. A bounded IPC channel carries events and observations. The supervisor remains responsive while the worker blocks in a provider, driver, or close. There is one action loop; the supervisor only coordinates state and verification.

Use fixed collection grace G = 5 seconds and termination allowance K = 2 seconds. After a terminal transition, forbid new task dispatches; collect outstanding results or read-only evidence for at most G. Grace grants no new execution permission. Then terminate/reap the worker and managed browser descendants within K; never wait indefinitely for close or join. Supervisor I/O, IPC, and verifier calls must fit within the remaining phase budget.

Record cleanup as closed, forced, or unknown. If termination cannot be established, mark unknown and quarantine the session identity/profile; V0.5 never reuses it. Process termination does not establish rollback of server effects. Collection ends at CLI exit: no background collector or post-exit update is promised. Unresolved committed actions remain effect=unknown in the result snapshot.

The deadline transition is due at t0 + wall_seconds, with at most 250 ms scheduling delay allowed in the acceptance environment. Exit must satisfy t_exit <= t_terminal + G + K + 1 second. These are measured liveness bounds, not real-time OS guarantees. Test a worker that never returns. Collection may end early when nothing remains outstanding.

## 4. Dispatch and cancellation ordering (R2)

Supervisor and worker share a short-held synchronization gate for terminal state, counters, and one in-flight action record. After revalidation, the worker rechecks observation identity, policy revision, terminal state, deadline, and counters under this gate. No network/browser call or blocking IPC occurs while the gate is held.

The worker either rejects the proposal or confirms its existing cycle/call reservations and atomically records dispatch_committed(action_id). Already reserved counters are not charged again; bootstrap navigation reserves its own step here. This is the logical dispatch boundary. Immediately afterward it calls the driver directly, without a command queue, re-observation, or another decision. Cancellation and completion use the same gate. Queued proposals have no dispatch authority until they pass it.

- If cancellation wins, the proposal never calls the driver.
- If dispatch wins, the action is in flight, even if OS scheduling delays its driver call or the server receives it after cancellation.
- The first terminal transition is immutable. The shared action record survives a worker exit before IPC delivery; missing return evidence leaves its effect unknown.

This defines local ordering, not atomicity with the site. Compare dispatch/cancel sequence numbers; server timestamps alone cannot prove a violation. Test both interleavings using barriers, including cancellation after revalidation but before commit. If the worker dies while holding the gate, supervisor recovery must use a bounded acquisition timeout and the cleanup procedure, reporting executor_error and unknown effects rather than waiting forever.

## 5. Browser adapter, permissions, and TextSlots (R4)

Implement the internal operations observe, candidates, revalidate, execute, and close. These are required adapter behavior, not claims about existing upstream API names. Reuse Browser Use enumeration and add only the metadata/checks required here.

| Object | Required data |
|---|---|
| Observation | Session ID, observation ID, monotonic capture time, current URL, target descriptors |
| Target | Fixture target ID, node identity/generation, page/frame identity, element type, operation, enabled state, destination/form identity where applicable |
| Candidate | Candidate/observation/session IDs, policy revision, operation, target, immutable parameters, optional slot ID/version |
| Revalidation | Same unambiguous node and relevant attributes; enabled, allowed URL, unchanged parameters/slot |

Add explicit fixture target IDs and track node identity/generation: a replacement node reusing an HTML ID must invalidate the old candidate. Isolate necessary private dependency access and test it against the pinned version. Unsupported required checks yield adapter_contract_unsupported, not weaker validation. Changes after revalidation remain possible; verify consequences afterward.

The finite operations/permission names are navigate, type_text, toggle_setting, save_settings, submit_form, start_export, and delete_account. Permissions apply to all fixture targets of the named operation. Derive operation identity from trusted fixture definitions and validated element attributes, not button labels or model risk scores. Finish is a control proposal, not a browser action.

Filter inadmissible candidates before selection and recheck before dispatch. Unknown IDs, altered parameters, or invalid slots stop as blocked/invalid_action. Stale/ambiguous targets trigger rejection and a fresh observation under the same step limit. Permission denial stops as blocked/policy_denied; an empty admissible set stops as blocked/no_admissible_action. Bootstrap navigation to start_path requires navigate permission, consumes a step, and passes the dispatch gate. Verifier maintenance endpoints are never browser candidates. This is a fixture policy, not a general web network sandbox.

Slots are immutable within an attempt. Resolve an exact ID/version to its value after validation; providers choose references and cannot rewrite values. New contents require a new task revision. Permission to type does not authorize submission.

## 6. Result schema and state mapping (R3)

The result schema_version is execution-result/0.1 with these required fields:

| Field | Contract |
|---|---|
| task_id, revision, attempt_id, executor_id | Request identity, runtime attempt ID, selected executor or null |
| routing | Original routing decision, including stub provenance, or null before routing |
| attempt_status | completed, blocked, cancelled, incomplete, failed |
| stop_reason | Code from the table below |
| execution_outcome | not_started, returned, error, unknown; any unresolved committed action takes precedence as unknown |
| verification | Criterion ID/kind, pass/fail/unknown, observation time, evidence refs; includes runtime constraints |
| task_outcome | pass only for completed with all checks pass; fail for confirmed final failure or constraint violation; otherwise unknown |
| actions | IDs, proposal/dispatch/return sequence, target/slot references, effect=applied/not_applied/unknown, evidence refs |
| budget | Used/remaining counters, elapsed time, measured cost or null with availability reason |
| cleanup, trace_ref, evidence_refs | Cleanup status and artifact references |

Mutable phases are admitted, running, and verifying. Exactly one terminal transition is accepted. Verify fresh baseline state, post-action state as needed, and the state when the harness ends normally or reports no confident action. A provisional failed postcondition may later pass. A confirmed execution-constraint violation is sticky; the executor never weakens criteria. Accept completed only when all task actions are settled and all required postconditions and execution constraints are confirmed pass; outstanding relevant evidence prevents completion. Baseline observation requires the permitted bootstrap navigation, but already_satisfied performs no additional goal-directed mutation.

Apply this table only while no terminal state exists. The gate orders cancellation, dispatch, and completion. Completed is forbidden at/after the deadline even if the watchdog has not yet run.

| Event | Status / reason | Task outcome |
|---|---|---|
| All criteria already satisfied at fresh baseline | completed / already_satisfied | pass |
| Normal finish or no confident action, all criteria pass | completed / verified | pass |
| Normal stop with confirmed final postcondition failure | failed / postcondition_failed | fail |
| Normal stop with missing verification and no confirmed failure | incomplete / verification_unknown | unknown |
| No eligible/fitting route, missing executor, unsupported predicate | blocked / no_route, executor_unavailable, unsupported_criterion | unknown |
| Policy/fixture/action/adapter rejection | blocked / policy_denied, fixture_mismatch, invalid_action, adapter_contract_unsupported, no_admissible_action | unknown |
| Accepted cancellation | cancelled / cancel_requested | unknown unless a constraint violation is confirmed |
| Deadline or step/model-call limit | incomplete / deadline, step_limit, model_call_limit | unknown unless a constraint violation is confirmed |
| Provider protocol error, worker/driver error, runtime output failure | failed / protocol_error, executor_error, output_error | unknown unless failure is independently confirmed |
| Unknown action effect cannot be reconciled | incomplete / effect_unknown | unknown |
| Confirmed execution-constraint violation | failed / constraint_violated | fail |

A routing response requiring confirmation produces blocked/policy_denied; failed routing transport uses failed/executor_error and retains the routing reason. NONE maps to blocked/no_route. No execution handoff/resume is implemented in V0.5.

Late evidence may update criterion/effect assessments during grace but never attempt_status or stop_reason. Cancelled + postcondition pass remains task_outcome=unknown; cancelled + confirmed constraint violation is task_outcome=fail. A late postcondition pass cannot turn a protocol error into completed. A failed postcondition at a cancelled intermediate state alone does not prove final failure.

Exit codes: completed 0, invalid input/output preparation 2, blocked 3, incomplete 4, failed 5, cancelled 130. They report attempt status; consumers inspect task_outcome and verification for effects and violations. Read-only evidence collection after a stop does not authorize another browser action.

## 7. Budget and repeated-operation semantics (R6)

- A step is one inner observe/decision cycle, including rejection or re-observation. Reserve before the cycle. Bootstrap navigation consumes one step. Trace actions and finish separately; a cycle dispatches at most one browser action.
- A model call is one actual provider request, including macro routing and micro decisions. Reserve before sending; transport retries also need reservations. Disable opaque provider retries. Script/stub calls consume zero model calls but use applicable steps. No confident action does not refund a call.
- Automatic action retries are zero, even after reconciliation proves no effect. V0.5 performs no automatic continuation.
- Derive operation keys from attempt, fixture run, operation/target, and payload slot versions. After an unknown non-idempotent effect, prohibit all new mutations and reconcile authoritative state; otherwise stop effect_unknown. A second model-proposed submit/export/settings mutation is subject to this rule even if no retry helper is involved. With zero retries, a repeated dispatch for a previously attempted non-idempotent operation is rejected as blocked/invalid_action.
- Charge measured macro/micro usage, including calls without browser actions. Missing cost is null with a reason. This version has finite time/call limits and does not accept a hard currency-budget field.

A successful driver return does not by itself prove effect=applied. Reconciliation updates action effects using authoritative evidence; absence from an intermediate state does not prove not_applied while a server operation may still be running.

## 8. Verification and fixture isolation (R5)

Runtime installs required constraints for permission enforcement, immutable slot use, single session ownership, dispatch ordering, budget compliance, and no uncertain repeats. Their assessments require complete relevant runtime/adapter evidence; missing evidence is unknown. Request criteria are postconditions from this table, not executable code.

| Predicate | Arguments | Evidence |
|---|---|---|
| current_page | path, target_id | Fresh browser observation confirms current URL and expected target; historic GET is insufficient |
| settings_saved | notify_email boolean | Server setting equals expected and save count increased exactly once from baseline |
| form_submitted_once | name_slot, email_slot | Exact resolved server values and exactly one matching POST since baseline |
| export_completed_once | none | One export request and server export count increased once from baseline |
| account_intact | none | Account present and no delete request since baseline |

Predicate arguments are exact: reject missing/extra keys or invalid types. Slot arguments use ID@version. Baseline completion is allowed only where the predicate holds under its defined semantics; event-count predicates requiring a new change cannot already pass from a historical event.

Each attempt uses its own fixture process and fresh run ID. No shared global reset across outstanding runs. The fixture returns run ID and monotonic event sequence in state/log responses. Capture baseline before browser startup; evidence must match run ID and the criterion's baseline window. Old delayed effects belong to the old process and cannot satisfy a new run. Keep the old fixture through its observation grace, then stop it independently; killing the browser does not stop server work.

The fixture launcher is a test/example helper. Verifier requests are bounded and excluded from browser-navigation evidence. Use browser observations for current browser state and server records for committed effects. Persist redacted evidence with criterion/attempt refs; exclude raw slots, secrets, full HTML, and unsanitized upstream traces by default.

## 9. Fixed acceptance gate (R7)

Levels: U = deterministic runtime fakes; B = script decisions plus real browser/fixture; J = Jev plus real browser/fixture. Each stated variant is a separate subcase. Use barriers for races. Pin dependencies before executing; unsupported adapter requirements leave integration blocked, never silently waived.

| ID | Levels | Subcases and expected outcome |
|---|---|---|
| C01 | B, J | Current-page navigation, saved setting, submitted form: each completed/pass with section 8 evidence |
| C02 | U, B | False finish → failed/fail; no confident action with goal confirmed → completed/pass; protocol error with pass evidence → failed/unknown; already-satisfied current_page → completed/pass without new mutation |
| C03 | U, B | Policy denial, stale/reindexed node, substituted slot, unknown candidate: no rejected dispatch; stale node re-observes under budget; other invalid proposals block |
| C04 | U | NONE, missing executor, unsupported predicate, wrong fixture run, unsupported adapter contract: corresponding blocked reason and no task action |
| C05 | U, B, J | Cancel pending decision → cancelled; expire pending decision → incomplete; no later dispatch |
| C06 | U, B | Both dispatch/cancel orders, including cancel after revalidation: gate sequence and in-flight classification; no post-cancel new commit |
| C07 | U, B | In-flight cancel and deadline, each with late return and lost return: immutable stop, resolved/unknown effect; no subsequent dispatch or session reuse |
| C08 | U, B | Hung provider, driver, close separately: section 3 transition/exit bounds; cleanup and unknown effects recorded |
| C09 | U, B | Lost submit response then another proposed submit: at most one submission; reconciliation or effect_unknown stop |
| C10 | U | Step limit, macro call limit, micro call limit, retry configuration rejection, invalid/nonfinite input, verifier unavailable: exact codes/counters and no false success |
| C11 | U, B | Visit then navigate away fails current_page; old delayed export cannot affect new-run evidence; wrong-run evidence rejected |
| C12 | U, B | Cancel then late constraint violation → cancelled/fail; ordinary logs exclude sentinel secrets/slots; available evidence linked |
| C13 | J | Deterministic policy revocation injected after candidate selection: no dispatch and blocked/policy_denied even if Jev proposes the action |

Run each U subcase once, each B subcase three times from fresh fixtures, and each J subcase three times. All required assertions must pass; missing runs mean pending, failures mean failed. Repetition is a small reproducibility gate, not a statistical quality claim. For J, use JevRouter for macro and Jev for micro. Mark deterministic providers explicitly. C01 is executable-task set E; expected stops/fault cases are set B under North Star. Never combine them into task completion rate.

Before execution, freeze a manifest expanding every subcase ID, exact commands/inputs, dependency/provider/model versions, expected result fields, and environment. Preserve every planned attempt, measured timings, result, and evidence. Reruns keep the original attempt and reason; no post-hoc deletion or denominator replacement. Missing credentials leave J pending while U/B may proceed.

## 10. Implementation order and review closure

1. Request/result contracts, CLI surface, state table, and existing routing regressions.
2. Supervisor/worker, dispatch gate, budgets, and U checks.
3. Pinned browser adapter, TextSlots, isolated fixture, verifier, and B checks.
4. J checks and evidence packet; update status/roadmap only to the evidenced level.

R1 maps to section 3, R2 to 4, R3 to 2/6, R4 to 5, R5 to 8, R6 to 7, and R7 to 9. These are specification decisions; new adapter operations, fixture fields, process handling, and synchronization still require implementation and validation.
