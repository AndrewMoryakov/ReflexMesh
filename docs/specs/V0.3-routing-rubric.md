# V0.3: рубрика маршрутизации

Дата: 2026-09-24. Статус: принятые правила подготовки набора задач.
Это не полный протокол эксперимента: набор, повторы, бюджеты, baseline-модели
и численные пороги ещё предстоит зафиксировать до измерения.

## Единица решения

Маршрутизируется одна подзадача с одним проверяемым типом результата при
явно заданных входных данных и каталоге возможностей. Класс определяется
требуемой работой, а не тем, какая модель технически могла бы её выполнить.
LLM с поддержкой изображений не превращает любую perception-задачу в класс LLM.

| Класс | Требуемый результат | Пример |
|---|---|---|
| CUA | Изменение/навигация UI посредством явных действий | Открыть раздел настроек; заполнить указанное поле готовым текстом |
| PERCEPTION | Извлечение фактов из уже имеющегося наблюдения без действий в UI | Переписать сообщение об ошибке из переданного снимка |
| LLM | Рассуждение, планирование или создание нового содержания | Объяснить ошибку по переданному тексту; составить ответ |

«Прочитай ошибку на скриншоте и объясни исправление» — составная задача:
сначала PERCEPTION для извлечения, затем LLM для объяснения. В основном
наборе она разбивается на две подзадачи с соответствующими входами.
«Открой страницу и прочитай ошибку» также требует разделения действий и извлечения.
В V0.3 анализируется выбор класса; снимки/приложения не обрабатываются адаптером.

## Поля разметки (метаданные набора, не расширение Task API)

- case_id, goal, описание уже доступных входных данных;
- capabilities, allowed_routes, rationale;
- kind: single / ambiguous / refusal / composite;
- acceptable_routes: заранее согласованный набор допустимых классов;
- expected_outcome: selected либо abstained/needs_confirmation там, где это
  обосновано условиями сценария; для составной задачи — описание декомпозиции.

acceptable_routes относится к конкретному каталогу и ограничениям. Допустимое
множество непусто для selected, является подмножеством eligible и не меняется
по ответам оцениваемой модели. Несколько вариантов допустимы только при
описанных взаимозаменяемых возможностях и одинаковом требуемом результате.
Неполный контекст не следует автоматически размечать «любой маршрут верен».

При разногласии разметка уточняется до прогона либо кейс заранее переносится
в отдельный исследовательский набор без основной accuracy. Сохраняются автор
разметки, её версия и обоснование; постфактум подгонять эталон запрещено.

## Сопоставление и отказ

Для single/ambiguous ответ засчитывается только при status=selected и
route в acceptable_routes. Отказы измеряются отдельно как coverage/abstention;
ошибка транспорта или протокола не считается корректным отказом по смыслу.
При пустом eligible ожидается локальный abstained без запроса к модели.

Не смешивать отсутствие допустимых кандидатов, неопределённость модели,
неподдерживаемую по смыслу задачу и требование подтверждения. В текущем V0.2
есть локальный отказ при пустом eligible и отказ upstream по его policy;
отдельного механизма определения «ни один класс не подходит» в адаптере нет.
Такие смысловые случаи можно исследовать отдельно; их нельзя объявлять
поддержанными или заменять произвольным выбором LLM без правила протокола.

Composite оценивается отдельно, если эксперимент вообще включает
декомпозицию. Нельзя требовать единственную метку CUA/LLM/PERCEPTION от
неразделённой многошаговой цели и включать её в обычную routing accuracy.

## Сравнение

Все варианты (правила, Jev, LLM) получают одинаковые описания задачи,
входного контекста и допустимых классов. Метки и rationale эталона не передаются
оцениваемым маршрутизаторам. Способ упаковки контекста и ограничения
подсказок фиксируются в полном протоколе до измерений.
Результаты single, ambiguous, refusal и composite публикуются раздельно;
успех классификации не называется выполнением пользовательской задачи.
