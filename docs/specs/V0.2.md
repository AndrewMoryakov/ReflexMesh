# V0.2 — HTTP-адаптер JevRouter

Статус: адаптер реализован; проверен с локальным HTTP fixture и настоящим
сервером upstream в demo-режиме. Вызов облачной модели Jev ещё не проверен.

Навигация: [STATUS](../STATUS.md) · [ROADMAP](../ROADMAP.md) · [целевая архитектура](../architecture/TARGET_ARCHITECTURE.md).

## Граница

Python-ядро вызывает отдельный локальный JevRouter (Node.js 20+) через
POST /route. ReflexMesh не дублирует SDK, не управляет ключами и не запускает
исполнителей. Stub остаётся значением по умолчанию для совместимости V0.1;
JevRouter включается явно через --provider jevrouter. Автоматического fallback нет.

Проверенный upstream: [f944acb6530621bced023352e2358a63218bf4d9](https://github.com/BillionsBobby/JevRouter/tree/f944acb6530621bced023352e2358a63218bf4d9).
Контракт: src/types.ts (RouteInput/RouteResult), src/cli.ts (serve),
src/router.ts (finalize), src/provider.ts (provider names).
Обновление upstream требует повторного интеграционного прогона.

## Вход и фильтрация

Task версии 0.1 сохраняется. До сети вычисляется пересечение capabilities
и allowed_routes. В POST передаются только эти кандидаты, с фиксированными
описаниями CUA/LLM/PERCEPTION и request=goal. При пустом пересечении сетевого
вызова нет. Кандидаты объявлены unverified и dry_run: это выбор класса работ,
не подтверждение наличия исполнителя. Категория риска low относится к операции
маршрутизации, а не к будущим действиям класса CUA.

После ответа снова проверяются допустимые ID, состав кандидатов без повторов,
status, decision_only, execution.enabled=false и флаги политики выбранного
кандидата. Неизвестный ID, неверные типы, дубликаты JSON-ключей, NaN и противоречия
дают failed/invalid_response. Unknown provider не считается настоящим Jev.
Непроверенные значения остаются данными доверенного локального сервиса:
provenance не является криптографическим доказательством обращения к модели.

## Выход

Для stub сохраняется ответ 0.1. Для JevRouter — JSON-ответ schema_version=0.2:

| Поле/исход | Значение |
|---|---|
| status=selected | Только upstream selected с разрешённым ID; route заполнен; exit 0. |
| status=abstained | Пустое пересечение или upstream no_decision; route=null; exit 3. |
| status=needs_confirmation | upstream требует подтверждения; route=null, предложение остаётся в trace.upstream.selected; exit 4. |
| status=failed | Ошибка транспорта, провайдера или протокола; route=null; exit 5. |
| provider | jevrouter — идентификатор адаптера. |
| is_stub | true для распознанного jevrouter-demo (в том числе отклонённого); false не доказывает, что запрос к модели состоялся. |
| execution_performed | Всегда false. |
| confidence | Оригинальный raw_jev.answers.tool.confidence либо null; не вероятность успешного исполнения. |
| reason_code | Стабильный код причины, без текста ошибки/ключа из upstream. |
| trace | Хеши запроса/ответа, elapsed_ms, факт попытки транспорта и полученного ответа, IDs и структурированные данные upstream. |

trace.request_sent означает попытку отправки, не подтверждённое получение.
trace.response_received означает получение полного ограниченного HTTP 200 body,
не подтверждённую валидность JSON. Hash связывает байты запроса/ответа, но не
подтверждает их истинность. Ошибка не содержит raw ответа или upstream error.message.
raw_jev целиком не копируется в stdout, scores не перенормируются; оригинальный
выбор Jev и fallback_type сохраняются отдельно от окончательного выбора router.

Поддержанные provenance provider: typesafe, openrouter:~typesafe/jev-latest,
jevrouter-demo. Demo отклоняется, если нет --allow-demo. Отказ в demo может
возникнуть уже после upstream-запроса, это не preflight-проверка провайдера.

## Транспорт и лимиты

--jev-url: только http://127.0.0.1:PORT (по умолчанию 8787), без credentials,
query, fragment и дополнительных путей. Используется прямое соединение:
без proxy из окружения, редиректов, retry и автоматической установки пакетов.
--timeout: конечное число (0,120], по умолчанию 30 секунд; это тайм-аут
блокирующего socket I/O, не общий wall-clock deadline при медленной порционной
отдаче. Ответ ограничен 1 MiB. Общий deadline исполнения относится к будущему runtime.
Отмена ожидания клиента не гарантирует отмену уже начатого запроса модели на сервере.

## Приёмка и оставшийся gate

- Регрессии V0.1 проходят.
- Локальные HTTP-тесты покрывают фильтрацию, отказ, подтверждение, поломанные
  ответы, размер, timeout, HTTP failure и отсутствие скрытого fallback.
- Отдельный скрипт подтверждает совместимость с закреплённым upstream demo.
- Live gate закрывается только по следующему пакету свидетельств.

### Минимальный live-пакет V0.2

Оператор запускает реальный typesafe или openrouter (без demo/mock) и сохраняет:

1. Commit ReflexMesh и JevRouter, среду, выбранного провайдера/модель и policy
   без ключей. Если идентификатор модели недоступен — это явно отмечается.
2. Входы и выходы CLI, exit codes и связанные upstream receipts/идентификаторы
   для успешного запроса по всему пути ReflexMesh → JevRouter → облачная модель.
   Нужен status=selected, разрешённый route, execution_performed=false;
   is_stub=false само по себе не доказывает реальный вызов.
3. Как минимум один такой успешный запрос с двумя или тремя допустимыми
   кандидатами. Проверяется точное соответствие входных ID, upstream
   decision.selected и route ReflexMesh. Если router изменил выбор модели,
   jev_choice и fallback фиксируются отдельно. Корректность смысла выбранного
   маршрута здесь не является оценкой качества V0.3.
4. Проверку исключения маршрута: запрещённый ID отсутствует в отправленном
   наборе; выход не выбирает его. Пустое пересечение проверяется отдельно:
   abstained/no_eligible_route и отсутствие сетевого вызова.
5. Итоговую отметку pass/fail/не завершено для каждого пункта с датой и
   ссылками на очищенные от секретов свидетельства. Непроверенный пункт не pass.

HTTP 200 без корректного результата, ошибка провайдера, только no_decision,
только demo или выбор единственного кандидата не закрывают live gate.
Единственный кандидат годится для начальной проверки соединения; нет требования
искусственно снижать порог policy ради успешного multi-candidate запроса.

Проверка одного реального провайдера закрывает gate только для этой конфигурации.
Другой провайдер остаётся неподтверждённым до отдельного прогона. Негативные
контрактные тесты продолжают требоваться, но не заменяют live-свидетельства.
Оценка полезности routing — отдельный V0.3. На дату правки live gate открыт.

### Сбор воспроизводимого пакета

Из закреплённого checkout JevRouter запустите сервер в его рабочем каталоге
с ключом в окружении процесса (см. README). Например, для typesafe:

```sh
node dist/cli.js serve --provider typesafe --port 8787
```

Из каталога ReflexMesh во втором терминале запустите сборщик. Каталог вывода
должен ещё не существовать и находиться вне обоих репозиториев:

```sh
python scripts/collect_v02_live.py \
  --upstream-dir /path/to/JevRouter \
  --provider typesafe \
  --output-dir /path/to/private/v02-live-evidence
```

Для OpenRouter используйте `--provider openrouter` в обеих командах.
На Windows во втором терминале из каталога ReflexMesh используйте PowerShell:

```powershell
& .\.venv\Scripts\python.exe scripts/collect_v02_live.py `
  --upstream-dir 'C:\path\to\JevRouter' `
  --provider typesafe `
  --output-dir 'C:\private\v02-live-evidence'
```

Ключ нужен серверу JevRouter; сборщик удаляет
переменные ключей из окружения дочерних процессов ReflexMesh.

Сборщик проверяет commit JevRouter и `/health`, делает **два** запроса на
маршрутизацию без повторов (multi-candidate и исключённый маршрут), затем проверяет
пустой набор локально. Он сохраняет входы, stdout/stderr, exit codes, копии
upstream decision receipts, идентификаторы и сравнение SHA-256 ответа с receipt.
Если policy отклоняет выбор, результат остаётся отказом; порог не понижается.

`report.json` отмечает автоматические проверки, но `live_gate_closed` всегда
остаётся `false`: локальный provenance не доказывает фактический вызов модели.
Оператор отдельно подтверждает, что именно проверенный сервер и его policy
обслуживали запросы, связывает пакет с фактическим вызовом провайдера/модели
и заполняет результаты пяти пунктов live-пакета выше.
Receipts могут содержать входные данные и ответы модели; перед передачей пакета
нужно удалить секреты и чувствительное содержимое, сохранив проверяемые ID/хеши.
