# План ReflexMesh: V0 → V1.0 → V2.0

Исходный план: 2026-09-24. Уточнение браузерного инкремента: 2026-10-11.
Статус кода синхронизирован 2026-10-12 по PR #10,
[4a8385f](https://github.com/AndrewMoryakov/ReflexMesh/commit/4a8385f08b15ecdbdf96ad262f95c3673f94637e),
только чтением исходников; это не новый прогон и не подтверждение слияния PR.
Источник статуса реализации и свидетельств — [STATUS](STATUS.md).
Короткое руководство по текущему фокусу — [CURRENT_DIRECTION](CURRENT_DIRECTION.md).
План служит [North Star](NORTH_STAR.md) и соблюдает [инварианты](architecture/INVARIANTS.md).
Номер в pyproject.toml обозначает версию пакета, а не автоматическую приёмку этапа.

Цель — универсальное ядро координации инструментов и исполнителей. Браузер
служит первым execution-сценарием V1.0; desktop планируется после V1.0.
Эта корректировка концепции не добавляет
API/CLI/workflow-исполнителей в V0–V1.0 и не меняет уже зафиксированные gates.
CUA / LLM / PERCEPTION остаются экспериментальным каталогом V0; расширение
каталога требует отдельной спецификации и новой разметки, а не молчаливой
смены смысла текущих классов.

V0.6 уточнён после выбора стека SystemOneHarness + Browser Use + Jev.
Сначала доказывается работа на сайтах без fixture IDs и сценариев конкретной страницы,
затем принимаются тонкие MCP/Pi обёртки общего Browser Core. Уже существующие
[fixture MCP/Pi](guides/V0.6-mcp-pi.md) принимают `execution-task/0.1` и продолжают
цепочку в свежем браузере; они не реализуют общий `browser-task/0.1` API и не
закрывают M3/M5. Продолжение после handoff в живой сессии
входит в этот инкремент; восстановление после перезапуска процесса остаётся поздним.
Изменение плана не закрывает V0.5 gates, не меняет INV-01–16 и не добавляет
новых тестовых или браузерных свидетельств. Статус реализации в STATUS сохраняет
свою дату и кодовую базу.

V0.3 относится к исследованию маршрутизации, а не к исполнению; V0.4 уже
проверил fixture интеграцию SOH + Browser Use. Их результаты не доказывают
качество общего micro-loop. При провале гипотезы Jev в сравнении V0.6 решение
фиксируется по его протоколу; сменные decision providers сохраняются.

## Ближайшая работа

Текущий продуктовый приоритет — M1–M2 [V0.6 Browser Core](specs/V0.6-browser-core.md):
общий адаптер и реальный выбор действий Jev на неизвестных сайтах. Обязательные
ограничения runtime доводятся вместе с этим путём; открытая fixture приёмка V0.5
не объявляется закрытой и не превращается в отдельный бесконечный этап вместо
проверки основной гипотезы. Выполненные routing исследования ниже остаются
основанием и регрессиями, а не новым центром разработки.

1. M1 — **реализация присутствует в проверяемой ветке**: новые browser контракты, общий adapter и наблюдения со свежими refs;
   реальный DOM сценарий с script provider без fixture IDs и site-specific сценария показан в датированном отчёте.
2. M2 — **механика реализована, Jev не подтверждён**: SOH, TextSlots, admission и общий учёт исторически проверены на script и
   заглушке эндпоинта решений; свежая проверка текущего кода и короткий реальный прогон поиска/формы с настоящим Jev (нужен ключ) остаются открыты.
   Нужны прослеживаемый выбор, dispatch и эффект. Runtime gaps исправляются вместе с этим путём, без объявления
   прежней приёмки закрытой.
3. M3–M4: handoff/continuation в той же сессии и общая verification с доказательствами
   всех обязательных constraints; до этого успешное действие не означает completed.
4. M5: функциональная приёмка и сравнение Jev/LLM по протоколу; затем MCP/Pi
   путь рабочего общего ядра к V1.0. Наличие fixture Task API, Pi extension и
   acceptance runners не означает прохождения этих gates. Подробные условия milestones — в V0.6.

Выполненные V0.2–V0.4 и открытая приёмка fixture V0.5 перечислены в STATUS.
Прямой typesafe, более трудный routing dataset и новые варианты refusal
исследуются при конкретной потребности; они не являются предпосылками M1–M2.

Отсутствие ключа не блокирует подготовку протокола и fixtures, но исключает
заявление о проверенной облачной интеграции и реальном качестве Jev.

## Приёмка V1.0

| Сценарий | Подтверждение |
|---|---|
| Навигация к целевому разделу | Ожидаемый URL и нужный элемент относятся к свежему наблюдению |
| Заполнение поля TextSlot | Точное значение выбранной версии слота в целевом поле |
| Недостижимая цель | Ограниченная остановка с причиной, без ложного completed |
| Необходимость нового содержания | Handoff в Pi с контекстом; следующая подзадача возвращается через тот же API |

Дополнительно проверяются отмена и поздний ответ, исчерпание лимита, устаревшая
цель действия, запрет, потеря ответа после неидемпотентного действия и недоступный
verifier. Подтверждённое нарушение не стирается поздним достижением цели.
В сравнении используются одинаковые начальные состояния и критерии принятия.
Для нового browser core фиксируется протокол из [V0.6](specs/V0.6-browser-core.md#17-сравнение-jev-и-решение-о-режиме-по-умолчанию):
Jev без помощи, Jev с metered LLM assistance и LLM с тем же adapter/verifier.
Продуктовые пороги фиксируются до прогонов и не являются результатами измерений.
Выполнимые задачи и сценарии отказа/отмены/handoff образуют отдельные наборы:
для первых измеряется достижение цели, для вторых — соответствие ожидаемому
поведению. Их успехи не складываются в общий task completion rate;
правила знаменателей заданы в [North Star](NORTH_STAR.md).

До V1.0 маршрутизируется отдельная ограниченная подзадача; декомпозиция остаётся
у клиента. LLM — допустимый handoff вызывающему агенту. PERCEPTION доступен
для исполнения только при подключённом провайдере. Полноценный desktop, OCR,
control plane, специализированные engines и HTTP Task API не обязательны для V1.0.

## Расширение после V1.0

Это предварительный порядок, а не обещание уже реализованных функций.

| Версия | Продуктовое расширение | Условие включения |
|---|---|---|
| V1.1 | OCR/резервное восприятие | Сценарии, где структурированных наблюдений недостаточно; измерен выигрыш |
| V1.2 | Desktop и переходы browser ↔ application | Выбраны поддерживаемые ОС/backend; действия и критерии проверены |
| V1.3 | Расширенное recovery и восстановление после перезапуска процесса | Повторяющиеся причины сбоев подтверждены трассами; durable продолжение нужно по измерениям |
| V1.4 | Очередь, UI, история, scheduling, approvals | Проверена пригодность ClawBridge; lifecycle не обходит runtime |
| V1.5 | Durable workflows и повторяемые макросы | Skyvern/Ui.Vision или замены полезны конкретным сценариям и обеспечивают ограничения |
| V2.0 | Согласованный runtime для разных классов исполнителей | Выбранные сквозные сценарии без GUI и browser/desktop с verification, recovery и управлением задачами |

V2.0 — завершение первой концепции. Подробные сценарии, поддерживаемые среды
и критерии его приёмки определяются после V1.0. Подключение всех названных
библиотек само по себе не является готовностью продукта. После V1.0 отдельно
выбирается небольшой сценарий без GUI (например, через API/MCP tool или CLI),
который покажет, что ядро не зависит от UI-пути. Это направление приёмки V2.0,
а не новая задача текущего MVP и не обязательство поддержать все виды инструментов.

## Правило обновления плана

У этапа должны быть спецификация, критерии выхода, свидетельства и явные
ограничения. Реализация, проверка и принятие решения — отдельные отметки.
Изменение порядка отражается здесь; изменение инварианта — через ADR.
LOC-оценки и сроки не заменяют критерии приёмки.
