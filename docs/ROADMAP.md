# План ReflexMesh: V0 → V1.0 → V2.0

Дата: 2026-09-24. Источник статуса и свидетельств — [STATUS](STATUS.md).
План служит [North Star](NORTH_STAR.md) и соблюдает [инварианты](architecture/INVARIANTS.md).
Номер в pyproject.toml обозначает версию пакета, а не автоматическую приёмку этапа.

## Путь до первого продукта

| Этап | Работа | Критерий выхода | Статус на дату документа |
|---|---|---|---|
| V0.1 | Task, RoutingDecision, CLI, явная заглушка, валидация | Запуск без Pi/сети; выбор только допустимого; ошибки имеют формат | Реализован и проверен в указанной в отчёте среде |
| V0.2 | HTTP-адаптер JevRouter, причины отказа, trace, timeouts | Контрактные проверки и полный [live-пакет](specs/V0.2.md) для указанного провайдера | Код и demo проверены; live gate открыт |
| V0.3 | Размеченный набор задач; правила, Jev и LLM; единый отчёт | Измерения по заранее принятому протоколу; решение о применении Jev | Рубрика подготовлена; полный протокол и прогоны не начаты; закрывает routing-этап V0 |
| V0.4 | Spike SystemOneHarness ↔ Cua MCP на контролируемом сайте | Цикл воспроизводим; проверены контроль до действия, результат, остановка и поздний ответ; зафиксирован пошаговый/автономный режим и решение по gap | Не начат |
| V0.5 | Минимальный runtime, TextSlots, verifier, лимиты, отмена, trace | Из CLI выполняется браузерная подзадача; успех только с проверкой; повторы/гонки покрыты | Не начат |
| V0.6 | MCP-интерфейс и отдельная интеграция Pi, handoff | Pi передаёт задачу, получает результат/блокер и отправляет следующую подзадачу | Не начат |
| V1.0 | Приёмка, сравнение Jev + Cua с LLM + Cua, установка и демонстрации | Четыре продуктовых сценария и негативные проверки ниже; ограничения документированы | Первый законченный browser MVP, впереди |

V0.3 относится к исследованию маршрутизации, а не к исполнению. V0.4 можно
подготовить как отдельное исследование совместимости, пока ожидаются данные
V0.2/V0.3; это не закрывает их gates. При провале гипотезы Jev не проталкивается
в обязательный путь — решение фиксируется, архитектура адаптеров сохраняется.

## Ближайшая работа

1. Закрыть live gate V0.2 по [минимальному пакету](specs/V0.2.md): реальный
   провайдер, успешный полный путь, multi-candidate запрос с проверкой ID,
   исключение запрещённого маршрута и пустой набор без сетевого вызова.
   Одна задача с единственным вариантом или ошибка не закрывает gate.
2. Подготовить протокол V0.3 **до прогона**: критерии разметки, неоднозначные задачи,
   случаи отказа, языки, повторения, budgets, метрики и численные пороги принятия.
   Использовать [рубрику маршрутов](specs/V0.3-routing-rubric.md): атомарные
   подзадачи, допустимые множества ответов и отдельные случаи отказа.
   Пороги ещё не установлены; не выводить их задним числом из результатов.
3. Подготовить набор и одинаковые входы для простых правил, Jev и LLM;
   измерить качество выбора, долю отказов/ошибок, latency, calls и доступную стоимость.
4. Зафиксировать вывод: где Jev полезен, где неприемлем, какие вопросы остались.
5. Перед V0.4 выбрать небольшой воспроизводимый сайт и проверить реальные
   MCP-схемы/версии зависимостей. Только затем решать об адаптере/candidate builder.

Отсутствие ключа не блокирует подготовку протокола и fixtures, но исключает
заявление о проверенной облачной интеграции и реальном качестве Jev.

## Приёмка V1.0

| Сценарий | Подтверждение |
|---|---|
| Навигация к целевому разделу | Ожидаемый URL и нужный элемент относятся к свежему наблюдению |
| Заполнение поля TextSlot | Точное значение выбранной версии слота в целевом поле |
| Недостижимая цель | Ограниченная остановка с причиной, без ложного completed |
| Необходимость нового содержания | Handoff в Pi с контекстом; следующая подзадача возвращается через тот же API |

Дополнительно проверяются отмена и поздний ответ, исчерпание лимита, устаревшая
цель действия, запрет, потеря ответа после неидемпотентного действия и недоступный
verifier. Подтверждённое нарушение не стирается поздним достижением цели.
В сравнении используются одинаковые начальные состояния и критерии принятия.
Выполнимые задачи и сценарии отказа/отмены/handoff образуют отдельные наборы:
для первых измеряется достижение цели, для вторых — соответствие ожидаемому
поведению. Их успехи не складываются в общий task completion rate;
правила знаменателей заданы в [North Star](NORTH_STAR.md).

До V1.0 маршрутизируется отдельная ограниченная подзадача; декомпозиция остаётся
у клиента. LLM — допустимый handoff вызывающему агенту. PERCEPTION доступен
для исполнения только при подключённом провайдере. Полноценный desktop, OCR,
control plane, специализированные engines и HTTP Task API не обязательны для V1.0.

## Расширение после V1.0

Это предварительный порядок, а не обещание уже реализованных функций.

| Версия | Продуктовое расширение | Условие включения |
|---|---|---|
| V1.1 | OCR/резервное восприятие | Сценарии, где структурированных наблюдений недостаточно; измерен выигрыш |
| V1.2 | Desktop и переходы browser ↔ application | Выбраны поддерживаемые ОС/backend; действия и критерии проверены |
| V1.3 | Recovery и продолжение после handoff | Повторяющиеся причины сбоев подтверждены трассами; supervisor нужен по измерениям |
| V1.4 | Очередь, UI, история, scheduling, approvals | Проверена пригодность ClawBridge; lifecycle не обходит runtime |
| V1.5 | Durable workflows и повторяемые макросы | Skyvern/Ui.Vision или замены полезны конкретным сценариям и обеспечивают ограничения |
| V2.0 | Согласованный heterogeneous execution runtime | Сквозные сценарии browser/desktop/engines с verification, recovery и управлением задачами |

V2.0 — завершение первой концепции. Подробные сценарии, поддерживаемые среды
и критерии его приёмки определяются после V1.0. Подключение всех названных
библиотек само по себе не является готовностью продукта.

## Правило обновления плана

У этапа должны быть спецификация, критерии выхода, свидетельства и явные
ограничения. Реализация, проверка и принятие решения — отдельные отметки.
Изменение порядка отражается здесь; изменение инварианта — через ADR.
LOC-оценки и сроки не заменяют критерии приёмки.
