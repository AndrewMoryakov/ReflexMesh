# Текущее направление разработки

Зафиксировано: 2026-10-11. Это краткое руководство по выбору следующей работы;
контракт и критерии принятия задаёт [V0.6 Browser Core](specs/V0.6-browser-core.md).
Фактическая готовность и открытые проверки — в [STATUS](STATUS.md).

## Что строим сейчас

Первый продуктовый путь ReflexMesh — выполнение ограниченной браузерной
подзадачи на DOM-сайте, для которого не написан отдельный сценарий и не нужны
специальные fixture IDs. Пользователь получает проверенный результат либо
содержательную остановку/handoff с возможностью продолжения в той же сессии.
Это первый прикладной путь универсального ядра, а не обещание выполнять
любую задачу на любом сайте.

Ближайший приоритет — **M1–M2 V0.6: общий адаптер и реальный выбор действий Jev**.
Существующий fixture runtime — основа для переиспользования и регрессий.
Его ограничения доводятся вместе с общим путём; открытые U/B/J вопросы
не закрываются изменением документации. Полная приёмка старого стенда
не становится отдельным обязательным этапом перед любой работой над M1–M2.
При этом незакрытые обязательные constraints исключают заявление о
подтверждённом `completed`.

## Выбранный стек и решения

| Участник | Что решает и делает |
|---|---|
| Вызывающий LLM/агент | Декомпозирует цель, задаёт разрешения и критерии, готовит версионированные TextSlots; решает, как помочь после handoff |
| Jev | Выбирает операцию, цель из свежего наблюдения и готовый слот из конечного набора; не генерирует текст, selectors, JS или shell |
| SystemOneHarness | Организует единственный observe → decide → act цикл и связывает предложения с контролем runtime |
| Browser Use | Через BrowserSession и низкоуровневые операции наблюдает и выполняет допущенное действие; автономный LLM Agent не запускается |
| ReflexMesh runtime | Проверяет возможности и допуск, владеет сессией и попытками, считает бюджеты, обрабатывает отмену и неизвестные эффекты, принимает терминальное состояние |
| Verifier | Проверяет принятые критерии по свежим связанным свидетельствам; runtime отдельно требует все шесть обязательных execution constraints |

Полный **jev-ultrafast не является зависимостью** и не добавляет второй driver
или цикл. Заимствуем компактное наблюдение, проверку актуальности цели,
запись исхода действия до следующего наблюдения и остановку при отсутствии
прогресса. Закреплённые версии основного стека указаны в V0.6.

**Решающая модель (2026-10-13).** M2 проверяется на настоящем Jev через OpenRouter
(`--action-provider jev`). Локальная `laya-browser` подключена как дополнительный провайдер,
но для нужд ReflexMesh недостаточна: она обучена на узком формате вопросов jev-ultrafast,
и часть выбора (слот, `goal_reached`) за неё делает переходник. Локальный кандидат
для сравнения в M5 — открытые веса OpenJev (27B и Flash 9B, лицензия CC BY-NC 4.0);
на машинах без GPU их скорость не измерена.

## Следующие инкременты

| Milestone V0.6 | Прикладной результат |
|---|---|
| M1 | Общие BrowserTask, наблюдение и адаптер; цели связаны с snapshot/node refs и проверяются перед действием, а не ищутся по fixture IDs |
| M2 | Jev действительно выбирает действия и TextSlots в этом пути; короткие браузерные проверки показывают выбор, действие и проверку эффекта |
| M3 | SessionManager и continuation сохраняют браузер после handoff; помощь LLM идёт через тот же admission и общие бюджеты, с новой связанной попыткой |
| M4 | Общие критерии и runtime evidence позволяют честно различать pass/fail/unknown и подтверждать `completed` только при выполнении всего контракта |
| M5 | Функциональная приёмка и заранее зафиксированное сравнение Jev/LLM на одинаковом backend; затем тонкие клиентские MCP/Pi обёртки к V1.0 |

Это последовательность результатов, а не запрет работать над нужным
контролем раньше его milestone. Свежесть, разрешения, владение, отмена,
неизвестные эффекты и budgets проверяются при появлении соответствующего пути.
В первый BrowserTask не переносится unlimited режим прежнего fixture CLI.

Проверка M1–M2 должна показывать работу без site-specific сценария,
конечный выбор на свежем наблюдении, точный ввод подготовленного TextSlot
и отсутствие dispatch после запрета, отмены или потери актуальности цели.
Script/fake подтверждает только механику. Настоящий Jev требует свидетельства
вызова decision provider; полезность Jev требует отдельного сравнения.
Пока M4 не доказан, успешное действие или постусловие не обозначается как
полностью принятое выполнение задачи.

## Когда расширяем состав

MCP/Pi предоставляют доступ к рабочему ядру и не заменяют его проверку.
Routing API сохраняется; browser-вход с единственным явно выбранным
`browser.soh` не требует дополнительного macro-вызова JevRouter.
Исследования V0.3/V0.3b остаются свидетельствами о routing, не основанием
для автоматического вывода о качестве браузерных micro-действий.

OpenJev 4B v0.2 — первый кандидат позднего локального сравнения через сменный
decision provider. Playwright MCP, Stagehand, OmniParser и OCR/VLM рассматриваем
при измеренном недостатке выбранного пути. Cua/desktop, discovery/self-extension,
ClawBridge, Skyvern, Ui.Vision, очередь/UI, другие классы исполнителей и HTTP
Task API относятся к последующим задачам. Их присутствие в целевой архитектуре
или пустом каталоге не делает их предпосылкой текущего браузерного инкремента.

Если код расходится с контрактом, отмечаем gap и исправляем его; наличие
реализации не ослабляет требование. Если новая согласованная задача меняет
направление, обновляем эту страницу, ROADMAP и затронутые спецификации;
изменение инварианта обосновываем ADR. Не приписываем новым планам старые
результаты и не меняем исторические SHA, числа или условия прогонов.
