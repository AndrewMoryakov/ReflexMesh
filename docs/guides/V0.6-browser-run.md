# V0.6 browser path: install, run, read the result

Scope: the generic browser path built for V0.6 **M1–M2** and the page verifier of **M4**
(`reflexmesh browser run`). It runs one bounded browser subtask on a site the core has no scenario for.
It is not the fixture runtime (`reflexmesh run`, see [V0.5-local-run](V0.5-local-run.md)) and not the whole
browser MVP: the Jev/LLM comparison (M5) does not exist yet, continuation after a handoff needs the session service
or Python ([Continuing after a handoff](#continuing-after-a-handoff)), and an attempt on a site without a registered
check cannot reach `completed` (see [Completed](#completed-what-it-takes)).
What was run, and what was not, is in [the M1–M2 evidence](../research/V0.6-M1-M2-2026-10-11.md);
the contract is [V0.6 Browser Core](../specs/V0.6-browser-core.md).

## Install

Linux, WSL or native Windows ([below](#windows-native)), Python 3.11+. The core itself has no dependencies; the
browser capability does.

```sh
python -m venv .venv
.venv/bin/pip install -e .

# SystemOneHarness at the pinned commit
git clone https://github.com/HarnessRouter/SystemOneHarness.git ../SystemOneHarness
git -C ../SystemOneHarness checkout ab8e8f08b4a6268c0633a474423d556599ee06a4
.venv/bin/pip install -e ../SystemOneHarness

# Browser Use at the pinned commit (the dependency the adapter was written against)
.venv/bin/pip install --no-deps \
  "git+https://github.com/browser-use/browser-use.git@5c892e013a73e6622e6f50336e1eb0aa2c4405f2"

# A Chromium; the headless shell is enough and small
.venv/bin/pip install playwright && .venv/bin/python -m playwright install chromium-headless-shell
export REFLEXMESH_CHROME=$(ls ~/.cache/ms-playwright/chromium_headless_shell-*/chrome-headless-shell-linux64/chrome-headless-shell)
```

Every result carries a `components` block: the installed SOH and Browser Use commits next to the
pinned ones (`matches_pin`), the Chromium version, the provider and whether the sandbox was on.

**Chromium sandbox.** It is on by default. Some hosts forbid unprivileged user namespaces
(Ubuntu 23.10+ with AppArmor: `No usable sandbox!`); there pass `--no-sandbox` or set
`REFLEXMESH_CHROME_NO_SANDBOX=1`. That is a per-host decision and is recorded in the result
(`components.chromium_sandbox`). Do not use it for sites you do not control without thinking about it.

**Temporary files.** Browser Use copies a custom Chrome profile into `/tmp` unless the directory
name carries its marker; the adapter names its profile `browser-use-user-data-dir-reflexmesh-*`,
verifies that Chrome really uses it and removes it. If `/tmp` is a RAM disk, set `TMPDIR`.

### Windows (native)

The browser path (`browser run`, `serve` and its clients, `view`) runs on native Windows Python; the fixture runtime
of V0.5 (`reflexmesh run`) does not (it needs `fork`). Checked on Windows 11 with Python 3.13 and Google Chrome 142.

```powershell
git clone -b integrate/v0.6-into-main https://github.com/AndrewMoryakov/ReflexMesh.git
git clone https://github.com/HarnessRouter/SystemOneHarness.git
git -C SystemOneHarness checkout ab8e8f08b4a6268c0633a474423d556599ee06a4
py -3.13 -m venv ReflexMesh\.venv
ReflexMesh\.venv\Scripts\python.exe -m pip install -e .\ReflexMesh -e .\SystemOneHarness
ReflexMesh\.venv\Scripts\python.exe -m pip install "browser-use @ git+https://github.com/browser-use/browser-use.git@5c892e013a73e6622e6f50336e1eb0aa2c4405f2"
ReflexMesh\.venv\Scripts\python.exe -m pip install playwright      # only for the test suite (verifier probe, viewer page)
```

The installed Google Chrome is used (`REFLEXMESH_CHROME`, default `C:\Program Files\Google\Chrome\Application\chrome.exe`),
with its sandbox on. Its version is read from the install directory: Windows Chrome ignores `--version` and would
start a browser instead. The demo in one command, from your own session (a window needs the desktop; over SSH the
browser runs, but nobody sees it):

```powershell
cd ReflexMesh
powershell -ExecutionPolicy Bypass -File experiments\v06\windows\run-demo.ps1                # one run, real Jev, visible Chrome, viewer
powershell -ExecutionPolicy Bypass -File experiments\v06\windows\run-demo.ps1 -Mode chain    # handoff chain through the service
powershell -ExecutionPolicy Bypass -File experiments\v06\windows\run-demo.ps1 -Provider script   # mechanics only, no key
```

The script starts the demo site (8770) and the viewer (8780), runs, and stops both at the end. With `jev` it takes the
key from `OPENROUTER_API_KEY` or asks for it (kept in that process only) and checks the key and the route first:
`401` = the key is rejected or expired, `403` = openrouter.ai refuses the exit country (turn the VPN on, or pass
`-Proxy http://127.0.0.1:PORT`; the provider also follows the Windows proxy settings). Runs land in `runs\`.

What differs on Windows: the session service listens on a named pipe instead of a Unix socket (below); leftover
browser processes are found and killed through psutil instead of `/proc`; Chrome also asks the page's origin for
`/favicon.ico`, which the headless shell on Linux does not.

## Run the demo scenario

The demo site (`experiments/v06/site/server.py`) is an ordinary order desk: a nav, a search form,
a results list, an order page with a note form. It has no ReflexMesh markup; the core has no
scenario for it.

```sh
.venv/bin/python experiments/v06/site/server.py --port 8770 &

.venv/bin/reflexmesh browser run \
  --input experiments/v06/tasks/order-note.json \
  --output-dir ./run-001 \
  --action-provider script --script experiments/v06/tasks/order-note.script.json
```

`--action-provider script` plays fixed steps against the options each step offers, picking them by
their visible description. It proves the mechanics (observation, admission, dispatch, effects,
cleanup). It says **nothing about Jev**.

### With the real Jev provider

The key is read from the environment only; never put it in a task, an argument or a chat.
Keep it in a file only you can read, outside the repository:

```sh
install -m 600 /dev/null ~/.config/reflexmesh/openrouter.env      # then add one line yourself:
# OPENROUTER_API_KEY=...
set -a; . ~/.config/reflexmesh/openrouter.env; set +a

.venv/bin/reflexmesh browser run \
  --input experiments/v06/tasks/order-note.json --output-dir ./run-jev-001 \
  --action-provider jev            # optional: --model NAME
```

`TYPESAFE_API_KEY` selects the provider's own API instead. Provider retries are off: every request
is reserved against `max_model_calls` first. `--decisions-url` points the same client at a stand-in
or proxy (https, or http on loopback); it is recorded in `components.decision_provider.config_id`.
Evidence that the real service was used is `decision_requested` / `decision_received` rows in
`trace.jsonl` with `served_model`, `request_id` and token usage; without them a run is not a Jev run.
First runs on the demo task, and what they showed: [V0.6 Jev runs 2026-10-13](../research/V0.6-jev-run-2026-10-13.md).

### With a local laya-browser server

`--action-provider laya` asks a [laya-browser](../research/V0.6-laya-local-provider-2026-10-13.md) server
(`laya_browser.py serve`, the `/v1/systemone` wire) in the format that model was trained on. It needs no key;
`--decisions-url` is required and must be https or http on loopback, so reach a server on another machine
through an ssh tunnel:

```sh
ssh -N -o BatchMode=yes -L 127.0.0.1:8791:<server-address>:8791 <user>@<host> &
.venv/bin/reflexmesh browser run \
  --input experiments/v06/tasks/order-note.json --output-dir ./run-laya-001 \
  --action-provider laya --decisions-url http://127.0.0.1:8791
```

What laya chose and what the translator filled in (the slot to type, `goal_reached`) is recorded per decision
in `translated.derived`; `go_back` and `switch_tab` are not offered to it (they never appeared in its training).
It is not Jev, and its confidence is not calibrated against the 0.7 threshold.

## Watching a run

A separate, read-only page shows each decision, who made it and how long it took. It reads the run
directory (`trace.jsonl` is written line by line, so it updates while the run is going) and can be started
before the run:

```sh
.venv/bin/reflexmesh browser view --run-dir ./run-001          # prints http://127.0.0.1:8780/
```

Per step: the author (`served_model`, so a stand-in, Jev or another model is visible), the chosen action and
the option it pointed at, confidence and the threshold it was judged against, the outcome, and the time split
into observation, decision (our measurement of the whole round trip, next to the provider's own figure),
admission and the browser command. The header gives the number of decisions, total decision time and its share
of the run, median, p95 and maximum. Click a row for the full menu that was offered, with the chosen entry marked.

It binds to loopback only, answers only GET, checks the `Host` header, and shows every value as text (page
text reaches option names). It never writes and never contacts a browser or a provider. Times are differences
between journal events (millisecond resolution); the first navigation includes starting the browser.

## Criteria: what the runtime checks

The runtime judges the task's criteria itself, on every observation, never on the model's word
([V0.6 section 11](../specs/V0.6-browser-core.md); details in [the M4a report](../research/V0.6-M4a-verifier-2026-10-13.md)):

- `page_match` / `revisit_match` (`anchor_slot_ref`, `field_name`, `expected_slot_ref`): the field named
  `field_name` of the object whose title is the anchor slot shows the expected slot exactly;
  `scoped_extract` (`anchor_slot_ref`, `field_name`, `output_key`) reads it into `outputs`.
- The anchor is the whole text of one visible element: for an order page titled "Заказ №125" give a slot with
  that value, not "125". Object and field are bound only through structure (a container the anchor names, or a
  table row); several matches, frames, shadow DOM or mere nearness give `unknown`.
- When every criterion holds on the page the loop stops (`criteria_met`) and the verifier checks once more. A
  `revisit_match` also needs the verifier to reopen the document: a GET of the same URL through the dispatch gate,
  spending a step and needing `navigate`.
- `registered_check` (`check_id`, `subject`, `expected_slot_refs`) names a check the service registered with
  `--checks FILE`; a task cannot supply one. Anything else is `blocked/unsupported_criterion` before the browser starts.

## Completed: what it takes

`completed/verified` needs every criterion `pass`, all six `runtime.*` constraints `pass`, no action effect left
`unknown` and nothing in flight ([V0.6 section 11](../specs/V0.6-browser-core.md);
[the M4b–M4c report](../research/V0.6-M4bc-completed-2026-10-13.md)).

- **Ownership** is evidenced for the browser session the attempt launched: a child process with its own profile, the
  same process throughout, only this runtime connected to its loopback debugging port at every observation, closed at
  the end. Another process on that port is `fail`; a client between two observations is not seen.
- **Repeats and effects** need a registered source that sees the server side. Without one they stay `unknown`, and so
  does the attempt. The only kind so far is `order_desk`, the demo site's oracle:

```sh
.venv/bin/reflexmesh browser run --input experiments/v06/tasks/order-note-verified.json \
  --checks experiments/v06/checks/order-desk.json --output-dir ./run-verified --action-provider jev
```

  It claims the site before the first navigation (a second claim is refused: `blocked`, `check_busy`) and, after the
  browser stopped, reads with a secret token what happened under the claim.

## Continuing after a handoff

`reflexmesh browser run` is one process per attempt: it holds no browser after it returns, so its handoff says
`continuation: {"allowed": false, "reason": "no_session_service"}`. To continue in the same browser session, run the
session service ([report](../research/V0.6-session-service-2026-10-13.md)) and talk to it:

```sh
.venv/bin/reflexmesh browser serve --socket ./svc.sock --state-dir ./state --action-provider jev \
  --checks experiments/v06/checks/order-desk.json &
.venv/bin/reflexmesh browser submit --socket ./svc.sock --input task.json > first.json      # may hand off
# continuation.json: {"token": <first.handoff.continuation.token>, "parent_attempt_id": <first.attempt_id>,
#                     "operation": "start", "mode": "jev", "task": <revision 2, optional>}
.venv/bin/reflexmesh browser resume --socket ./svc.sock --input continuation.json
.venv/bin/reflexmesh browser status --socket ./svc.sock          # chains, open sessions, remaining budget
.venv/bin/reflexmesh browser shutdown --socket ./svc.sock        # closes every browser
```

The socket is a local Unix socket (mode 0600, same-user peers only), not a network port. On Windows, which has no
Unix sockets in CPython, `--socket PATH` names an address file instead: the service listens on a named pipe with a
random name, every connection must answer a challenge with a random key (multiprocessing's HMAC handshake), and the
file holding the pipe name and the key gets an ACL of the current user alone. Whoever can read that file acts as
you, as with the socket. The same operations from Python are the embedding API ([the M3 report](../research/V0.6-M3-handoff-2026-10-13.md)):

```python
from reflexmesh.runtime.browser_core import BrowserCore

core = BrowserCore(chrome=chrome, provider_factory=factory, action_provider="jev", out_dir=Path("./chain"),
                   checks=load_checks("experiments/v06/checks/order-desk.json"))
first = core.execute(task)                                   # incomplete/needs_handoff, browser kept open
cont = first["handoff"]["continuation"]                      # one-time token, 60 s lease
second = core.resume({"token": cont["token"], "parent_attempt_id": first["attempt_id"],
                      "operation": "start", "mode": "jev", "task": revision_2})   # same session, shared budget
```

`mode: "llm"` returns `browser-progress/0.1` instead: a fresh observation and its finite options; send one
`{"operation": "step", "proposal": {"observation_id", "operation", "option_ref"[, "slot_ref" | "direction"]}}` at a
time with the newest token (at most five per handoff), then `return_to_jev` or `stop`. A new revision is the same task
with a higher number and nothing wider (permissions, origins, budget). The token is withheld from `result.json`.
If the lease runs out the browser is closed. A write whose driver call failed is never handed over: the session closes.

## Reading the result

`result.json` is `browser-result/0.1`; `trace.jsonl` is the redacted journal.

| Where | What it tells you |
|---|---|
| `attempt_status`, `stop_reason` | How the attempt ended. `completed/verified` only as described in [Completed](#completed-what-it-takes); a run whose criteria all pass without a registered source is `incomplete/verification_unknown`. A criterion that fails after `finish` or `criteria_met` is `failed/postcondition_failed`; a constraint `fail` is `failed/constraint_violated`. |
| `verification[]` | Criteria (`pass`/`fail`/`unknown`, with the reason and `scope`: `ui_observation` or `ui_after_reopen`) and the six `runtime.*` constraints. Permissions, dispatch ordering, immutable slots and budget can `pass` on gate and ledger evidence; ownership and no-uncertain-repeats stay `unknown`. |
| `outputs[]` | Values a `scoped_extract` criterion read, with the criterion and its evidence reference. |
| `actions[]` | One row per committed dispatch (`producer`: the decision provider, or `verifier` for its reopen; `request`: what a click sends, when known): option, target role and name, slot reference, driver outcome, `ui_effect` (what the next observation showed) and `effect` (server side: `unknown` unless something settled it). |
| `trace.jsonl` | `observed` → `options_built` → `decision_requested` → `decision_received` → `threshold_judged` → `proposal` → `admission_rejected`/`reobserve` or `dispatch_committed` → `driver_returned` → `effect_assessed` → `terminal`. |
| `budget`, `cleanup`, `components`, `decision` | Steps, model calls and dispatches; whether the browser and profile are gone; versions; requested and served model. |

Slot values never appear in the trace: secrets are always replaced, and normal values of four or
more characters too. Page text and typed content are not stored. A secret slot's value is also
withheld from the decision provider (it gets the reference and "secret value, not shown").

Exit codes: `0` completed, `3` blocked, `4` incomplete, `5` failed, `130` cancelled.

```sh
.venv/bin/python -m unittest discover -s tests -p 'test_v06_browser_*.py'   # 162 tests; the real-browser ones skip without REFLEXMESH_CHROME
```

The deterministic modules (`contract`, `control`, `providers`) need no browser. `test_v06_browser_real.py`
needs `REFLEXMESH_CHROME` and the pinned dependencies; without them it is *pending*, not passed.
A fake decision server in that module checks the provider plumbing (key header, call accounting,
no hidden retry) and is not Jev.

## Known limits

- The loop runs in the calling process (a watchdog thread kills the browser if the decision
  provider or driver hangs), not in an isolated supervised process.
- Offered operations: click, type_text, select_option, scroll, wait, go_back, switch_tab, and the
  first navigation. Not offered: key presses, `focus_region`, frames, cross-origin frames, open shadow
  DOM, file upload, drag and drop. Those capabilities are declared `false`, not probed.
- `allowed_origins` is checked on link destinations and tab switches before dispatch. A server-side
  redirect to another origin is **detected after the request** (the run stops `blocked/policy_denied`);
  it is not prevented.
- Starting Chromium occasionally fails (seen once in about twenty starts: Browser Use could not attach to the first
  target); the attempt then ends `failed/executor_error` and a rerun works.
- Clicks and typing can reach a server whatever the UI shows: their `effect` stays `unknown`.
- Repeats (V0.6 section 8): the same action in the same essential state (URL, visible text, values set; not
  Browser Use's per-capture numbering) is refused before dispatch as `repeated_action`, `wait` excepted; three
  cycles in a row without a new state stop the attempt as `needs_handoff/no_progress`. A write (click, typing,
  select) is also refused as `repeated_mutation` when the same action was already sent on the same document (URL),
  however the page changed since: a write changes the page itself, and its server effect is unknown (section 9).
  Typing into a field the site cleared after a validation error is refused the same way. Progress means a new
  page state only: no effect or criterion can be seen to move in this build, and a page that is still loading
  but looks the same counts as no progress.
- Browser Use lists the controls near the window. Anything outside it makes `coverage` `partial`
  (`more_content_below`/`above`, `next_window: scroll`); a scroll reveals more. The 200-control cap is also
  reported (`control_limit`) but no test reaches it.
