# V0.5 local execution checks

The current implementation supports a deterministic process supervisor, a pinned SystemOneHarness integration, and an isolated test site. Browser acceptance requires Browser Use 0.13.10 and Chromium in the same Linux/WSL environment. Jev requires a working provider configuration in SystemOneHarness and a JevRouter endpoint for macro routing. Do not call the V0.5 gate complete until the [specification's matrix](../specs/V0.5.md) has evidence.

## Install and run deterministic checks

```bash
python -m venv .venv
.venv/bin/python -m pip install -e .
.venv/bin/python -m unittest discover -s tests -p 'test_v05*.py' -v
```

After installing the pinned optional SystemOneHarness checkout and its dependencies, execute the [U manifest](../../experiments/v05/u-manifest.json) against a clean committed tree and a **new** output path:

```bash
PYTHONPATH=src:../.deps:../SystemOneHarness python experiments/v05/run_u.py \
  --output ./v05-u-attempt.json
```

The runner preserves every planned subcase, including skipped dependencies and failures. An output path that already exists is rejected to avoid replacing a prior attempt. The [recorded U acceptance](../research/V0.5-U-acceptance.md) is historical evidence for its recorded revision, not a run of the current completion gate. No new acceptance result is implied by the regression source changes below; the historical manifest and result files are unchanged.

To exercise the real SystemOneHarness controller, install [HarnessRouter/SystemOneHarness](https://github.com/HarnessRouter/SystemOneHarness) at commit `ab8e8f08b4a6268c0633a474423d556599ee06a4` and its dependencies. Install Browser Use `0.13.10` and a matching Chromium build to attempt the browser path. The pinned harness is an optional dependency; its test module skips if absent and must then be recorded as pending.

## Run the isolated fixture

Start one fixture process per attempt, on a free loopback port, with a unique run ID:

```bash
python experiments/v05/site/server.py --port 8765 --run-id example-001
```

In another shell, create an input file matching the JSON example in [V0.5.md](../specs/V0.5.md), using `http://127.0.0.1:8765`, run ID `example-001`, and `start_path: "/form"`. For the deterministic provider, a script file can contain:

```json
[
  {"action":"type_text","target_id":"name","slot":"name@1"},
  {"action":"type_text","target_id":"email","slot":"email@1"},
  {"action":"click","target_id":"send-form"},
  {"action":"finish"}
]
```

Run the CLI with a fresh output directory:

```bash
reflexmesh run --input task.json --output-dir ./evidence-form-001 \
  --routing-provider stub --action-provider script --script form-script.json
```

The CLI emits one JSON result and writes `result.json`, `trace.jsonl`, and `evidence.jsonl`. Check that `attempt_status=completed`, `task_outcome=pass`, and the `form_submitted_once` assessment is `pass` before reporting success. If browser dependencies or required adapter checks are unavailable, the CLI must report a blocker; that is not a successful browser run.

## Completion assessment gate

The supervisor always emits these six `execution_constraint` rows in `verification`:
`runtime.permissions`, `runtime.immutable_slots`, `runtime.ownership`,
`runtime.dispatch_ordering`, `runtime.no_uncertain_repeats`, and `runtime.budget`.
Task criteria cannot remove them or use the reserved `runtime.` ID prefix. Worker
events and postcondition-verifier responses cannot supply mandatory runtime passes.

Before accepting `completed`, all six must be `pass`, alongside passing
postconditions and the existing action-settlement, cancellation, and deadline gates.
Absent or incomplete evidence is `unknown`. Confirmed constraint failures are
sticky: later passing or missing evidence cannot erase them. Cancellation and
deadline retain their accepted status/reason; a confirmed violation still makes
`task_outcome=fail`. Merely exhausting a finite budget through its guard is an
ordinary stop, not evidence of exceeding it.
An accepted completion retains its confirmed assessments if a later read is
missing. A late confirmed violation still replaces the affected assessment with
`fail` and sets `task_outcome=fail`, while leaving the accepted status/reason
unchanged, as required by the immutable terminal-state contract. Consumers must
check `task_outcome` and assessments, not only `attempt_status` or the exit code.
Evidence collection remains inside the existing bounded grace/cleanup window.

The current implementation can assess only the scoped local counters in
`runtime.budget`. The other five rows deliberately remain `unknown`, with reasons
and empty evidence references. Admission guards, immutable Python objects, settled
effects, and one visible dispatch do not prove full target/policy identity, slot
resolution at dispatch, exclusive fixture/session ownership, shared gate ordering,
or an adapter-internal single-shot action. This change does not implement those
missing evidence sources. Thus existing browser/fake workflows with passing
postconditions now stop `incomplete/verification_unknown` instead of `completed`.
The synthetic all-pass rows in gate unit tests prove only the decision logic,
not real adapter conformance. V0.5 acceptance remains incomplete.

Unknown assessments are fully described in `result.json`; they do not fabricate
entries in `evidence.jsonl`. Confirmed local-budget assessments retain their scoped
evidence references and export their reason. Historical U/B/J results are not new
measurements, and no tests, builds, analyzers, browser runs, or model runs were
performed for this implementation change.

## Task budgets, hours, and explicit unlimited mode

The primary budget is elapsed system work on the task. `wall_seconds` starts when
the supervisor is created, before fixture preflight, routing and browser startup,
and includes provider waits and completion verification. It is not a timeout for
one model call. Hours are ordinary positive values: `7200` means two hours.

Finite wall/step limits and locally controlled call reservations keep their
existing behavior. Opaque JevRouter accounting is corrected as described below.
To disable an individual
budget, set its value to JSON `null`, for example:

```json
"limits": {
  "wall_seconds": 7200,
  "max_steps": null,
  "max_model_calls": 200,
  "max_action_retries": 0
}
```

`"limits": null` disables all three task budgets. Alternatively, pass `--no-limits`
to `reflexmesh run` to override the budgets in an otherwise valid input file.
Omitting the flag never disables a budget. Zero, negative values, booleans,
numeric infinity and NaN are not unlimited markers and remain invalid for these
three budget fields. `max_action_retries` still must be zero: removing budgets
does not authorize repeating uncertain or non-idempotent actions.

`max_steps` retains its existing meaning: observe/decision cycles plus bootstrap
navigation, rather than just browser actions. Stub/script decisions consume no
model calls. `max_model_calls` limits **locally controlled provider requests**;
it is not a global cap on a router service's internal requests (see below).
Results echo the effective three `budget.limits` and use `null` for
each disabled `remaining_*` value; finite exhausted budgets report zero. Counters
and elapsed time continue to be recorded with limits disabled.

With no wall deadline there is no fallback 60-second or other whole-task cap.
SIGINT cancellation, permissions, refusal/repetition checks, required verification
and bounded cleanup still apply. The task may continue until a terminal outcome
or manual cancellation. Operation timeouts remain independent: fixture HTTP reads
use at most 2 seconds, local model I/O at most 30 seconds, the JevRouter socket
uses `--timeout` (30 seconds by default, at most 120), and the pinned browser
bridge waits at most 120 seconds per operation. These limits detect a stuck
operation; they do not add an overall task deadline. Terminal cleanup keeps its
5-second grace and 2-second owned-process cleanup allowance. Completion
verification remains interruptible even without a task deadline, and an accepted
cancellation cannot be overturned by a late passing result.

## Replaceable routers and honest model-call accounting

The execution path uses the small `Router` interface in
[`routing/router.py`](../../src/reflexmesh/routing/router.py). The CLI still
offers only the existing stub and JevRouter. An embedded caller can inject a
router into `BrowserExecutionStrategy(..., router=...)`; no local-model backend
is implemented. Every router returns a decision and `RouterUsage`, and declares
one `RouterCapabilities.model_call_accounting` mode:

- `none`: no model provider calls (the fixed-order stub).
- `local`: the adapter must call the supplied `reserve_call()` immediately before
  each actual provider request, including every stage or retry. Its calls share
  the same local budget as the action provider. New adapters must be reviewed
  for this contract; the interface does not make an opaque service enforceable.
- `opaque`: internal model requests cannot be counted or limited at this boundary
  (the current JevRouter HTTP service). `RouterUsage.model_calls` is `null`.

JevRouter remains usable even when `max_model_calls` is finite. Its internal
requests are outside that cap and may be unlimited. In the
[audited JevRouter revision](https://github.com/BillionsBobby/JevRouter/blob/f944acb6530621bced023352e2358a63218bf4d9/src/router.ts#L336-L363),
one HTTP route request may invoke the provider twice when the candidate count
exceeds `single_stage_max_candidates`. The service's health/route interfaces do
not establish an enforceable per-request provider budget. Counting a route as
one model call or counting response stages afterwards would be misleading.

The result therefore reports:

- `budget.model_calls`: locally reserved request attempts if all work is observable;
  `null` once opaque routing has been attempted, including failed/interrupted
  calls. `model_calls_reason` explains the unknown total.
- `budget.local_model_calls`: locally reserved provider requests, still bounded
  by finite `max_model_calls`; `remaining_model_calls` refers to this same scope.
- `budget.model_call_limit_scope`: `locally_controlled_provider_requests`.
- `budget.router_invocations`: calls to the router interface, not model calls.
- `router_capabilities` and `router_usage`: the selected adapter's accounting
  contract and returned usage, when available. A missing response does not turn
  unknown internal usage into zero.

The `runtime.budget` verification row and its exported evidence explicitly use
`scope: steps_and_locally_controlled_model_calls`. A pass on this scoped check
does **not** claim that total JevRouter provider usage was bounded or verified.
The opaque marker is stored in shared state before invoking the router, so worker
termination cannot lose this uncertainty. Stub routing plus the existing Jev
action provider can retain an entirely locally counted model budget.

Task time, cancellation, permission checks and completion verification belong
to the supervisor for every router. Cancellation stops local waiting/execution
and bounded cleanup; it cannot revoke a request already received by an external
router/provider. That service may still finish its internal work.

For a live Jev check, choose `--routing-provider jevrouter --action-provider jev`, configure JevRouter locally and the harness provider using their own documentation, and preserve exact versions, commands, results, and model identity. Runtime tests with scripted decisions do not replace that live check.
