# V0.2: реальный прогон JevRouter на Windows

Этот сценарий собирает свидетельства для [live gate V0.2](../specs/V0.2.md#минимальный-live-пакет-v02).
Он проверяет выбор маршрута ReflexMesh через отдельный сервер JevRouter с настоящим
провайдером. **Задача пользователя не исполняется**: результатом является только
решение о маршруте. Для оценки качества маршрутизации нужен отдельный этап V0.3.

## Что потребуется

- Windows PowerShell, Git, Node.js 20+, npm, Python 3.11 или 3.12 и доступ в сеть.
- Действующий API-ключ OpenRouter (`OPENROUTER_API_KEY`) с доступом к Jev.
  JevRouter — локальный код, собственного API-ключа у него нет. Если у вас уже
  есть прямой ключ TypeSafe, этот вариант описан ниже.
- Два терминала. Первый останется занят сервером JevRouter, второй запустит
  сборщик из ReflexMesh.
- Место для приватного каталога свидетельств вне обоих репозиториев. Запрос
  отправляет облачной модели тестовую фразу на русском языке; сервер сохраняет
  ответы в `.jevrouter/decisions/` и может расходовать средства API. Сборщик
  посылает два запроса на маршрутизацию без retry; JevRouter может сделать
  несколько внутренних вызовов для одного решения.

Создайте аккаунт OpenRouter и на [странице API Keys](https://openrouter.ai/settings/keys)
создайте отдельный ключ для этого прогона. Задайте ему небольшой лимит
расходов; при отсутствии доступного баланса проверьте условия оплаты в
OpenRouter. [Документация Jev на OpenRouter](https://openrouter.ai/docs/guides/community/jev)
подтверждает, что отдельный аккаунт TypeSafe не требуется. Закреплённый
JevRouter использует через OpenRouter модель `~typesafe/jev-latest`.

Команды ниже используют **OpenRouter** и пример каталогов `C:\work` и `C:\private`.
Замените их своими абсолютными путями. Не вводите API-ключ в Task, аргументы
командной строки, файлы проекта и переписку.

## Терминал 1: установить и запустить JevRouter

Создайте рабочую папку, получите исходники и перейдите на проверенный commit:

```powershell
New-Item -ItemType Directory -Force 'C:\work' | Out-Null
Set-Location 'C:\work'
git clone https://github.com/BillionsBobby/JevRouter.git
Set-Location '.\JevRouter'
git checkout f944acb6530621bced023352e2358a63218bf4d9
git rev-parse HEAD
npm ci --ignore-scripts
npm run build
```

`git rev-parse HEAD` должен вывести `f944acb6530621bced023352e2358a63218bf4d9`.
Если JevRouter уже клонирован, перейдите в его каталог и выполните команды,
начиная с `git checkout`; сначала сохраните свои незакоммиченные изменения,
если Git не позволяет переключить commit. Сборщик откажется работать с другим
commit. Не запускайте сервер из другого рабочего каталога: receipts должны
появляться в `C:\work\JevRouter\.jevrouter\decisions\`.

Введите ключ скрытым вводом и запустите сервер в **этом же терминале**:

```powershell
$secret = Read-Host 'OPENROUTER_API_KEY' -AsSecureString
$env:OPENROUTER_API_KEY = [System.Net.NetworkCredential]::new('', $secret).Password
Remove-Variable secret
node dist/cli.js serve --provider openrouter --port 8787
```

При отсутствии ключа провайдер может запросить его интерактивно; всё равно
убедитесь, что запущен именно `openrouter`, а не `demo`. Секрет останется в памяти
процесса и окружении этого терминала до их завершения. После прогона завершите
сервер `Ctrl+C` и закройте терминал.

## Терминал 2: подготовить ReflexMesh и собрать пакет

В отдельном терминале получите актуальный `main`. Для **новой** копии:

```powershell
Set-Location 'C:\work'
git clone https://github.com/AndrewMoryakov/ReflexMesh.git
Set-Location '.\ReflexMesh'
```

Если у вас уже есть локальный ReflexMesh, перейдите в его каталог, проверьте
`git status --short` и, когда рабочее дерево чистое, выполните `git pull --ff-only`.
Не запускайте сборщик на старом checkout или с неучтёнными изменениями. В
обоих случаях затем установите пакет и проверьте версию:

```powershell
git rev-parse HEAD
git status --short
python --version
python -m venv .venv
& .\.venv\Scripts\python.exe -m pip install -e .
```

`git status --short` не должен выводить изменений, кроме созданной
игнорируемой `.venv`; запишите SHA commit ReflexMesh из `git rev-parse HEAD`.
Если Python не доступен под командой `python`, используйте установленный
Python 3.11/3.12 для создания `.venv`.

При работающем сервере проверьте его ответ:

```powershell
Invoke-RestMethod 'http://127.0.0.1:8787/health' | ConvertTo-Json
```

Ожидаемый `provider`: `openrouter:~typesafe/jev-latest`. Проверка `/health` **не доказывает** вызов
облачной модели. Создайте только родительскую папку для результатов и запустите
сборщик; папка `v02-live-evidence` ещё не должна существовать:

```powershell
New-Item -ItemType Directory -Force 'C:\private' | Out-Null
& .\.venv\Scripts\python.exe scripts/collect_v02_live.py `
  --upstream-dir 'C:\work\JevRouter' `
  --provider openrouter `
  --output-dir 'C:\private\v02-live-evidence'
$collectorExitCode = $LASTEXITCODE
$collectorExitCode
```

Не запускайте команду повторно с тем же `--output-dir`: сборщик требует
несуществующий каталог, чтобы не смешать свидетельства разных прогонов. Для
нового прогона используйте новое имя каталога. Значение `0` означает, что
**автоматические** проверки прошли; `1` — хотя бы одна не прошла. При ошибке до
создания пакета прочтите текст ошибки и исправьте причину (например, неверный
commit, недоступный `/health`, неподходящий provider или уже занятая папка).

### Если уже есть прямой ключ TypeSafe

В терминале 1 вместо `OPENROUTER_API_KEY` используйте `TYPESAFE_API_KEY` (или
`JEV_API_KEY`) и запустите `node dist/cli.js serve --provider typesafe --port 8787`.
В терминале 2 замените `--provider openrouter` на `--provider typesafe`.
Ожидаемый `/health` provider — `typesafe`. Всё остальное остаётся тем же.
`--provider demo` не закрывает live gate.

## Прочитать результат

```powershell
$packet = 'C:\private\v02-live-evidence'
$report = Get-Content (Join-Path $packet 'report.json') -Raw | ConvertFrom-Json
$report.mechanical_checks_passed
$report.cases | ConvertTo-Json -Depth 8
Get-Content (Join-Path $packet 'metadata.json') -Raw
```

Ожидаемая картина: `mechanical_checks_passed: true`, успешный `multi` с
`status=selected` и кодом `0`, успешный `filtered` без `CUA`, успешный `empty`
с локальным `abstained/no_eligible_route` и без нового сетевого запроса.
Проверьте `multi.stdout.json`, `filtered.stdout.json`, `empty.stdout.json`,
их коды в `report.json` и два файла `decisions/*.json`. Сборщик сверяет SHA-256
исходного ответа с сохранённым upstream receipt и точные наборы кандидатов.
Он записывает `reflexmesh_dirty`, commit и данные среды в `metadata.json`.

Если `mechanical_checks_passed` равно `false`, сохраните каталог и изучите
`cases.*.checks` и соответствующие `*.stderr.txt`. Отказ policy или ошибка
провайдера — полноценный результат диагностики, но **не успешный live gate**.
Не снижайте порог policy ради получения `selected`; укажите его значение и
причину отказа, если она известна, без ключей. При необходимости выполните
новый прогон в отдельный каталог.

Даже при успешных автоматических проверках `live_gate_closed` всегда равно
`false`. `is_stub=false`, `/health` и provenance локального сервера не являются
независимым доказательством обращения к модели.

## Что подтвердить вручную и передать для ревью

По [пяти критериям спецификации](../specs/V0.2.md#минимальный-live-пакет-v02)
запишите `pass`, `fail` или `не завершено` (с датой и ссылками на данные):

1. Commit обоих репозиториев, версии Python/Node, фактическую модель/провайдера
   и policy. Если модель нельзя установить, так и запишите.
2. Связь входов, выходов и exit codes с upstream receipts; `selected`,
   разрешённый маршрут, `execution_performed=false`.
3. Успешное решение с двумя или тремя кандидатами: точные ID, совпадение
   `decision.selected` и `route`; отдельно `jev_choice` и fallback при отличии.
4. Отсутствие запрещённого `CUA` во втором запросе и отсутствие сетевого
   вызова при пустом наборе.
5. Сводную отметку по каждому пункту и подтверждение **реального** вызова
   провайдера/модели. По возможности сопоставьте время и число запросов с
   журналом/учётом API провайдера и настройкой запущенного серверного процесса.
   Если подтверждения нет, оставьте пункт `не завершено`.

Оставьте **оригинальный пакет неизменным у себя**: изменение receipt ломает
сверку с `response_sha256`. Для передачи сделайте отдельную копию и проверьте
в ней `metadata.json`, `report.json`, `*.input.json`, `*.stdout.json`,
`*.stderr.txt` и `decisions/*.json` на наличие ключей, личных данных и
чувствительных фрагментов. Если редактируете receipt, укажите, что передана
очищенная копия и её хеш уже не совпадает с хешем оригинала; приложите
исходный SHA-256 и результат проверки из неизменённого `report.json`.
Не публикуйте пакет в открытом репозитории. Передайте очищенный пакет и
ручные отметки для анализа; API-ключ передавать не нужно.

После проверки пакета обновляются [статус](../STATUS.md) и исторический отчёт.
Если фактический вызов модели не доказан или один из пяти пунктов не пройден,
V0.2 live gate остаётся открытым с конкретной причиной.
