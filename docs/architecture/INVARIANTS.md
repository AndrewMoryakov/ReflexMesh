# Архитектурные инварианты ReflexMesh

Дата: 2026-09-23. Статус: зафиксированные требования к реализации.
Область: V0 → V1.0 → V2.0.

Документ закрепляет согласованную архитектуру и уточняет её проверяемые границы.
Требования ниже не означают, что соответствующая функциональность уже реализована:
на момент фиксации репозиторий содержит каркас.
«Обязан» и «запрещено» обозначают требования, а не пожелания.

## Постоянные инварианты

### INV-01. Ядро независимо от пользовательского клиента

Pi — основной планируемый интерактивный клиент, но не обязательная часть ядра.
Контракты, маршрутизация, выполнение и проверка не зависят от Pi.
CLI, MCP и будущий HTTP используют одинаковую семантику задач и результатов.
Специфика Pi находится в integrations/pi; отдельный пакет может называться reflex-mesh-pi.

Проверка: одну и ту же задачу можно передать без Pi; клиент не добавляет
обязательные скрытые данные или собственные условия успешности.

### INV-02. Внешние компоненты заменяемы

JevRouter, SystemOneHarness и Cua — исходные кандидаты интеграции.
Их специфические типы и протоколы изолируются на границах адаптеров.
ClawBridge, Skyvern и Ui.Vision — последующие кандидаты, не обязательные зависимости ядра.
Отсутствие необязательного компонента не должно ломать базовый запуск.

Проверка: контрактные проверки адаптера выполняются с тестовой реализацией;
отключённые возможности не рекламируются как рабочие.

### INV-03. Решение, разрешение и исполнение разделены

Маршрутизатор выбирает путь и не исполняет действия.
Jev предлагает маршрут или действие. Runtime проверяет допустимость,
управляет попыткой и вызывает исполнителя. Verifier оценивает результат.
Будущий control plane управляет жизненным циклом через те же границы,
не создавая обходного пути выполнения.

Проверка: вызов routing не меняет внешнее состояние; ни один executor
не вызывается в обход проверок runtime.

### INV-04. Ограничения обеспечиваются кодом

Permissions, availability, budget, locks и необходимые подтверждения
не определяются уверенностью модели.
Допустимые варианты фильтруются до выбора и проверяются повторно перед действием.
LLM fallback, handoff и смена исполнителя не расширяют разрешения автоматически.
Данные страницы, OCR и ответы инструментов не могут менять политику доступа.

Проверка: запрет, исчезнувшая доступность или отозванное разрешение блокируют
действие даже при максимальной модельной оценке.

### INV-05. Jev выбирает из конечного проверяемого набора

Micro-loop передаёт Jev конечный набор кандидатов с идентификаторами и
валидированными параметрами. Ответ вне набора отклоняется.
Jev не создаёт произвольный исполняемый код, команды или свободные параметры.
Кандидаты привязаны к наблюдению; при изменении существенного состояния
нужны повторное наблюдение и проверка применимости.

Проверка: неизвестный candidate ID, изменённые параметры и устаревшая цель
не приводят к слепому выполнению.

### INV-06. Генерация текста отделена от его применения

Текст приходит от пользователя, вызывающего агента, LLM или
детерминированного источника. В Jev-loop он используется через TextSlots.
Выбранная версия слота задаёт точное значение; Jev выбирает слот и цель,
но не переписывает содержание. Обновление текста создаёт новую версию/идентичность.
Наличие слота само по себе не разрешает отправку или публикацию текста.

Проверка: ввод соответствует выбранному значению; отсутствующий или
подменённый слот отклоняется.

### INV-07. Маршрутизация не равна выполнению

RoutingDecision, исход попытки выполнения и результат проверки различаются.
Выбор CUA не означает выполненную браузерную задачу; выбор LLM не означает
сгенерированный ответ. Маршрут, требующий передачи вызывающему агенту,
явно обозначается как handoff.

Проверка: routing-only запуск не выдаёт completed для исходной задачи.
Успешность самой операции маршрутизации обозначается отдельно.

### INV-08. Успех требует свидетельств

Модельное FINISH и upstream completed — только заявления о завершении.
Runtime может объявить задачу completed лишь после pass всех обязательных
критериев принятия на релевантных свидетельствах.
Критерии определяются до выполнения; исполнитель не ослабляет их ради успеха.
Изменение цели или критериев требует новой ревизии задачи.
Отсутствие проверяемого критерия означает неподтверждённый результат или handoff,
а не автоматический успех.

Проверка: FINISH с высокой уверенностью при невыполненном критерии
не превращается в completed. Verifier проверяет состояние, а не пересказывает
заявление исполнителя.

### INV-09. Неопределённость сохраняется явно

Verification различает pass, fail и unknown; отсутствие данных не равно pass
и само по себе не доказывает fail. Пропущенная проверка также не считается pass.
Для обязательных критериев: любой подтверждённый fail исключает успех;
без fail, но с unknown/непроверенными критериями результат не подтверждён.
Причина остановки, исход исполнения и verification сохраняются раздельно.
Отмена, тайм-аут, ошибка протокола и handoff не маскируются под completed.

Проверка: утрата наблюдения, malformed response и недоступный verifier
дают явные причины и не создают ложного успеха.

### INV-10. Любая попытка ограничена

Выполнение имеет конечные лимиты времени, шагов, повторов и модельных вызовов;
денежный бюджет учитывается, если применим и измерим.
Retry и handoff не обнуляют общий бюджет автоматически.
После принятой отмены новые действия не запускаются; уже отправленное действие
может завершиться, и его известные либо неизвестные последствия отражаются в результате.

Проверка: зацикливание завершается по лимиту; отмена не обещает откат
уже совершённых внешних изменений.

### INV-11. Повтор и владение средой контролируются

Одна управляемая сессия браузера/desktop имеет одного активного владельца
действий. Передача владения явная.
Неидемпотентное действие с неизвестным исходом нельзя автоматически повторять:
сначала проверяется состояние, иначе выполняется остановка/handoff.
Exactly-once исполнение внешних действий не обещается.

Проверка: потеря ответа после отправки формы не приводит к повторной отправке;
два исполнителя не управляют одной сессией одновременно.

### INV-12. Передача управления сохраняет смысл задачи

Handoff содержит идентичность задачи и попытки, цель, причину остановки,
известные выполненные действия и их исходы, ссылки на наблюдения,
оставшийся бюджет и ограничения.
Возврат управления не означает достижения цели.
Продолжение получает свежие наблюдения; изменение цели создаёт новую ревизию.

Проверка: получатель различает «не пытались», «выполнено» и
«возможно выполнено», не повторяя последнее действие вслепую.

### INV-13. Возможности и оценки сообщаются честно

Заглушка, существующий каталог, установленный пакет или выбранный маршрут
не доказывают доступность исполнителя.
В execution доступны только проверенные подключённые возможности и
явно согласованные handoff-пути.
Routing benchmarks могут использовать синтетический каталог, но помечаются
как эксперименты без реального исполнения.
Модельный score не называется вероятностью успеха без калибровки;
отсутствующие оценки, причины и стоимость не выдумываются.

Проверка: отключённый PERCEPTION исключён из execution;
синтетический прогон не попадает в отчёт как end-to-end success.

### INV-14. Результат прослеживается до попытки и свидетельств

Журнал связывает task/attempt IDs, версии контрактов и компонентов,
разрешённые кандидаты, решение, вызов действия, его исход и verification.
Отмечаются тайм-ауты, отмены, повторы и handoff.
Секреты не записываются; чувствительные наблюдения и TextSlots
редактируются или сохраняются по явной политике с контролируемым доступом.
Трасса объясняет ход выполнения, но не обещает детерминированный replay сайта.

Проверка: для completed можно найти критерии и свидетельства;
тестовые секреты отсутствуют в обычных логах.

### INV-15. Сложность вводится по подтверждённой необходимости

Сначала проверяется нативная связка SystemOneHarness ↔ Cua MCP.
Собственный CuaEnvironment/CandidateBuilder появляется только после фиксации
конкретного разрыва совместимости и минимального сценария его воспроизведения.
Perception выбирается по потребности; OCR/VLM не обязательны на каждом шаге.
Наличие RFC или описание в README зависимости не заменяет интеграционный прогон.

Проверка: дополнительный адаптер сопровождается описанием проблемы
и проверкой, показывающей, зачем он нужен.

### INV-16. Полезность Jev и готовность релиза подтверждаются измерениями

Маршрутизация сравнивается с простыми правилами и LLM;
computer-use — с LLM + тем же execution backend.
Сравнение использует одинаковые сценарии, начальные состояния,
критерии принятия и явно описанные бюджеты.
Измеряются success, false completion, latency, steps, calls,
recovery и доступные данные стоимости. Неизмеренное помечается неизвестным.
Результаты routing не подменяют end-to-end completion.
Jev сохраняется там, где подтверждён полезный компромисс качества,
задержки и стоимости; он не обязан участвовать в каждом решении.

Проверка: отчёт содержит версии, конфигурацию, число прогонов и неудачи;
ограниченная демонстрация не называется универсальной поддержкой.

## Границы версий — план, а не постоянные инварианты

| Этап | Результат и проверяемая граница |
|---|---|
| V0.1 | Контракты и CLI; заглушка явно обозначена. |
| V0.2 | Реальная маршрутизация и проверка допустимости; без выполнения. |
| V0.3 | Проверка полезности routing; завершённый V0. |
| V0.4 | Проверка SystemOneHarness ↔ Cua на контролируемом сайте. |
| V0.5 | Ограниченное browser execution, TextSlots, verifier, отмена и трассировка. |
| V0.6 | MCP и Pi; структурированный возврат управления. |
| V1.0 | Первый законченный browser MVP с воспроизводимыми сценариями. |
| V1.1–V1.5 | Предварительный порядок: perception, desktop, recovery, control plane, дополнительные engines. |
| V2.0 | Ориентир полной первой концепции; отдельные критерии приёмки определяются после V1.0. |

До V1.0 единица маршрутизации — ограниченная подзадача.
Декомпозиция сложной цели остаётся у вызывающего агента.
Первый встроенный execution-путь — CUA/browser; LLM может быть
согласованным handoff в вызывающий агент. PERCEPTION включается только
с доступным провайдером. Это границы MVP, не вечное ограничение архитектуры.

V1.0 требует четырёх сценариев:
1. Навигация с подтверждением ожидаемого URL и элемента.
2. Заполнение поля TextSlot с проверкой точного значения.
3. Недостижимая цель с ограниченной остановкой без ложного успеха.
4. Handoff в Pi с контекстом и отправкой следующей подзадачи.

OCR, desktop, ClawBridge, Skyvern, Ui.Vision, отдельный HTTP API и
модельный meso-supervisor не являются условиями выпуска V1.0.
Количество строк и календарные оценки не являются критериями приёмки.

## Применение и изменение

Инвариант применяется с появлением соответствующего пути:
routing-правила — в V0, execution/verification — при подключении исполнения,
handoff — при его реализации. Необязательная подсистема не требуется
только потому, что для неё сформулировано правило.

При реализации каждый затронутый INV-ID связывается с проверкой в тесте,
интеграционном прогоне или отчёте; пока таких свидетельств нет,
соответствие считается не подтверждённым.

Изменение постоянного инварианта фиксируется отдельным архитектурным решением:
какой INV-ID меняется, почему, последствия и способ проверки.
Дорожная карта может уточняться отдельно и не отменяет инварианты молча.
