# V0.6: браузерный путь на нативном Windows, 2026-10-13

Владелец хочет проверять V0.6 сам на своей машине с Windows и отказался ставить Linux/WSL. До этой правки
браузерный путь запускался только на Linux. Проба Python 3.13.7 на Windows 11 показала: нет `socket.AF_UNIX`, нет
`signal.SIGKILL`, из способов запуска multiprocessing есть только `spawn`.

## Что мешало и что сделано

| Место | Linux | На Windows было | Сделано |
|---|---|---|---|
| `SlotEvidence` (журнал неизменяемых слотов) | пара `AF_UNIX`-датаграмм | `AttributeError` при старте любой попытки | при отсутствии `AF_UNIX` — ограниченная очередь в процессе с теми же вызовами; в браузерном пути отправитель и получатель живут в одном процессе |
| общие значения попытки | `mp.get_context("fork")` | `ValueError` | `fork`, если есть, иначе `spawn`; из этого контекста процессы не запускаются, только `Value` |
| «жив ли процесс» | `os.kill(pid, 0)` | **на Windows это `TerminateProcess`: проверка убила бы процесс** | `psutil` |
| добивание остатков браузера | `os.kill(pid, SIGKILL)` | `AttributeError` | `psutil.Process.kill()` |
| поиск процессов по профилю | `/proc/*/cmdline` | нет `/proc` | `psutil.process_iter` |
| версия Chromium | `chrome --version` | Windows-Chrome не знает `--version` и **запускает браузер** (в сессии владельца — окно его Chrome) | версия берётся из имени каталога установки рядом с `chrome.exe` |
| сервис сессий | Unix-сокет 0600 + `SO_PEERCRED` | ни того, ни другого | именованный канал со случайным именем; каждое соединение проходит HMAC-рукопожатие со случайным ключом (`multiprocessing.connection`); имя и ключ лежат в файле `--socket`, ACL которого сброшен до одного текущего пользователя (по SID: под SSH `USERDOMAIN` — это `WORKGROUP`) |

Попутно:

- `--headed` у `browser run` и `browser serve` показывает окно браузера (по умолчанию его нет). Значение
  `headless` и раньше записывалось в `components`.
- `result.json` пишется атомарно (временный файл и `os.replace`). На Windows тест увидел цепочку закрытой раньше,
  чем файл появился; `browser view` на живом каталоге тоже мог прочесть половину файла.
- Сценарий цепочки (`experiments/v06/chain_demo.py`) — переносимая версия `flow.py` из свидетельств сервиса.
- Запуск демо для Windows одной командой: `experiments/v06/windows/run-demo.ps1` (см. руководство, раздел Windows).

Что из этого не защита: `chmod 0o600`/`umask` на Windows ничего не закрывают, поэтому там защищают только ACL файла
адреса и ключ. Пайп по умолчанию принимает и клиентов по SMB, но без ключа рукопожатие не проходит.

## Проверено

На рабочей машине владельца с Windows 11 (Python 3.13.7, Google Chrome 142.0.7444.176; вход служебной учётной
записью по SSH, поэтому без видимого рабочего стола), в отдельном каталоге с клонами ReflexMesh и SystemOneHarness и
venv с версиями пакетов как на Linux. Время проверки — ночь на 2026-10-14 по часам машины:

- `components`: Browser Use `5c892e0` и SOH `ab8e8f0`, у обоих `matches_pin: true`; песочница Chromium включена.
- `browser run` со сценарием на демо-сайте: путь пройден (номер, поиск, заказ, заметка, сохранение);
  `cleanup: closed`, профиль удалён, процессов Chrome не осталось.
- Набор `test_v06_browser_*.py`: 162 теста, OK. В первом прогоне 14 пропусков (проба проверяющего и безопасность
  страницы просмотрщика ждут пакет `playwright`, который ни от чего не зависит и сам не поставился); после
  `pip install playwright` эти два модуля — 33 теста, OK.
- `run-demo.ps1 -Provider script -NoPause` под SSH, с `--headed` (полный Chrome с окном, `components.headless: false`)
  и с `-Headless`: оба раза `completed/verified`, все критерии и шесть ограничений
  `pass` (в том числе `runtime.ownership`: `psutil` видит клиентов отладочного порта и на Windows); после выхода нет
  слушателей 8770/8780 и процессов Python. Первая версия скрипта гасила только запускатель `python.exe` из venv, а
  настоящий интерпретатор — его дочерний процесс — оставался бы слушать порт; теперь `taskkill /T`.
- `browser view` на Windows: страница 200, `/api/run` отдаёт 7 шагов прогона.
- `chain_demo.py` с настоящим Jev — на Linux (с машины с Windows openrouter.ai закрыт): A1 `needs_handoff/no_confident_action`,
  A2 (ревизия 2) снова `no_confident_action`, помощь LLM, шаг «Save note» — `completed/verified`; цепочка 20 шагов,
  16 вызовов модели. Сайт, сервис и Chrome погашены.
- На Linux тот же набор: 162 теста, OK (1 пропуск — проверка ключа именованного канала, она только для Windows).

Три теста упали на Windows, и это были допущения самих тестов:

- модуль `test_v06_browser_control` создавал контекст `fork` при импорте;
- тест lease ждал фиксированные 3 с: на Windows Chrome закрывается дольше, а цепочка помечается закрытой раньше
  записи `result.json`. Теперь тест ждёт закрытия, конца процесса Chrome и файла;
- тест «редирект на чужой origin замечен, а не предотвращён»: полный Chrome запрашивает у чужого origin ещё и
  `/favicon.ico`, а headless shell на Linux этого не делает. Переход по-прежнему один, тест не считает значок.

Свидетельства: [evidence/V0.6-windows-2026-10-13](evidence/V0.6-windows-2026-10-13/) — `result.json` и
`trace.jsonl` обоих прогонов скрипта запуска на Windows, хвост лога набора тестов там же, три попытки цепочки с Jev
на Linux (токен продолжения в файлах — `[withheld]`).

## Не проверено

- Настоящий Jev с Windows. Сейчас openrouter.ai с этой машины отвечает `403 Access denied by security policy`
  (выход из РФ, VPN выключен). Скрипт запуска проверяет ключ и маршрут одним запросом и называет причину.
- Видимое окно глазами: под SSH браузер с окном запускается и проходит путь, но рабочего стола нет; окно увидит
  только владелец в своей сессии.
- `run-demo.ps1 -Mode chain` на Windows: режим цепочки нуждается в Jev, поэтому не запускался (его части по
  отдельности проверены: сервис через именованный канал — тестами с Chrome на Windows, `chain_demo.py` — с Jev на Linux).
