## Как устроен SystemOneHarness (по коду)

Цикл `observe → compile → encode → decide → gate → execute` в `Controller.run`. Окружение —
`Environment` с `observe()` и `execute(action, params)`. Параметры действий должны быть
перечислимыми: enum, boolean, целое с диапазоном ≤ 10 значений или `x-candidates`
(список, который `observe` отдаёт на каждом шаге). Свободный текст запрещён: значения
подставляются по имени из заранее переданных `--text name=value`.

Готовые окружения: процесс, MCP-сервер, **браузер через Browser Use** (CDP, Chrome;
`envs/browser.py`, также как MCP-сервер `envs/browser_mcp.py`). Браузерные действия:
click, type_text, select_option, press_key, hold_key, scroll, switch_tab, go_back, wait.
**Cua в SystemOneHarness не используется.**

## Вопрос 1. Совместимы ли MCP-схемы Cua с action space SOH?

[`experiments/v04/probe_cua_compile.py`](../../experiments/v04/probe_cua_compile.py) передаёт в
`compile_tools` схемы `get_window_state`, `click`, `type_text`, `press_key`, `scroll` из документации.
**Результат: не компилируется ни один инструмент** («no tool compiled to an action»).
Все требуют `pid: integer` без диапазона. Кроме того, `click` адресует элемент числом
`element_index` или строкой `element_token`, а текст для `type_text` — свободная строка.

Вывод: нативная связка «SOH ↔ Cua MCP» невозможна без тонкого MCP-адаптера. Он должен:
`observe` отдаёт элементы из `get_window_state` как `x-candidates`, `click(element)`
переводит выбранный элемент в `element_token`, а текст берётся из именованных значений.
Нужно подтвердить на настоящем `cua-driver mcp` (`s1 tools --mcp ...`).

## Вопрос 2. Точки контроля ADR-0002

[`experiments/v04/probe_control_points.py`](../../experiments/v04/probe_control_points.py):
встроенное окружение заказов SOH и `ScriptProvider` (фиксированная последовательность действий,
без модели). Обёртка над `Environment.execute` записывает, какие вызовы дошли до «драйвера».

| Свойство | Штатный controller | Через обёртку `execute` |
|---|---|---|
| Запрет действия до драйвера | **Нет хука.** `on_step` вызывается после `execute` | Можно. Но только исключение даёт честный исход (`failed/environment_error`). `Result(ok=False)` — цикл продолжается, в пробе итог **`completed/goal_reached`**. `Result(terminal=True)` — **`completed/environment_terminal`**: ложное завершение |
| Результат действия доступен | **Да**: `Step.result` в `on_step` и trace | — |
| После отмены нового действия нет | **Нет.** `cancel()` проверяется только в начале шага; действие, выбранное после отмены, выполнено (`pack`) | Да: обёртка отказывает, если стоит флаг отмены runtime |
| Поздний ответ не возобновляет цикл | **Нет.** `timeout_seconds` проверяется только в начале шага; решение, пришедшее через 0.3 с при лимите 0.1 с, выполнено, затем `incomplete/timeout` | Да: та же проверка флага/дедлайна в обёртке перед драйвером |

Оговорка: `goal_reached` в варианте `ok=False` отчасти артефакт `ScriptProvider`: после конца
сценария он выбирает `finish` с уверенностью 0.95. Для ReflexMesh важен сам вывод: итог
`completed` у controller зависит от собственной оценки модели и не подтверждает цель.
Это уже требуется INV (независимый verifier).

## Итог pre-spike

1. SOH даёт нужный внутренний цикл, trace и перечислимые действия. Точки контроля «до действия»,
   «после отмены» и «после дедлайна» он **не обеспечивает сам**. Их можно обеспечить в процессе,
   обёрткой над `Environment.execute`, которая принадлежит runtime. Запрет — через исключение;
   итоговый статус runtime назначает сам, не доверяя `completed` от controller.
2. Нативная связка с Cua не компилируется. Реалистичные пути: Browser Use (уже встроен в SOH)
   или свой тонкий MCP-адаптер к Cua.
3. На текущем Linux-хосте нет графической сессии и Chrome (2 CPU, 3 ГБ): Cua-driver не
   запустить, для Browser Use нужна установка Chromium (headless). На Windows-машине
   a-moryakov-nb есть рабочий стол; OpenRouter оттуда — только через туннель.
