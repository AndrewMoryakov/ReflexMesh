# V0.6: `order@1` в цели и возврат на `start_url` при новой ревизии, 2026-11-05

Продолжение [эксперимента с формулировкой цели](V0.6-goal-wording-2026-11-05.md). После него оставались два вопроса: виновато ли
упоминание `order@1`, и почему после неудачной первой попытки не работает ни одна цель. Настоящий Jev
(`typesafe/jev-1.14-20261014`), порог 0.70, демо-сайт заказов, Windows 11, Chrome 142, запуск по SSH на отдельной машине.

## 1. Упоминание `order@1`

Предсказание до запуска: если виновато упоминание, цели без него пройдут в свежем браузере, а короткая цель с одним только
`order@1` застрянет. Новые цели:

```
G  Find order 125 (order number order@1) in the order desk, add the prepared note to it and save the note.
H  The order number is now provided. Replace the text in the Order number field with it, search, open order 125,
   add the prepared note to it and save the note.
F  Find order 125 in the order desk, add the prepared note to it and save the note. The search field may hold a wrong value.
```

Вместе с прошлыми результатами (число прогонов, дошедших до `completed/verified`):

```
цель                  свежий браузер                      после неудачной первой попытки
короткая              9 из 9                              0 из 5, поле не исправлено, не выше 0.42
G короткая + order@1  5 из 5                              0 из 5, поле исправлено в 3 из 5 (0.71-0.77), дальше стоп
длинная с order@1     0 из 5, стоп на результатах         0 из 7, стоп на результатах
H длинная без         5 из 5                              0 из 5, поле не исправлено, не выше 0.46
с фактом и order@1    0 из 5, стоп на Search              0 из 5, стоп на Search
F с фактом, без       0 из 5, доходит до Save, до 0.69    0 из 5, 4 стоп на Search до 0.68, 1 до Save до 0.69
```

Предсказание верно наполовину. G прошёл, значит само упоминание Jev не ломает. Но из длинной цели и из цели с фактом его удаление
заметно сдвигает остановку вперёд. Механизм не установлен. Прошлый отчёт спрашивал, почему добавленный к цели текст снижает уверенность: так ставить вопрос неверно,
G и H с добавленным текстом проходят. Остаётся вывод, что исход зависит от текста цели.

Всего без возврата на `start_url` цепочку сам Jev не прошёл ни разу: 0 из 32.

## 2. Возврат на `start_url`

Гипотеза: при продолжении браузер остаётся на странице неудачи, с неверным значением в поле, и дело в этом. В эксперименте вторая
попытка новой ревизии начинается с обычного первого перехода на `start_url`: через тот же gate, бюджет шагов и журнал, в той же
сессии, с той же заявкой на проверяемый источник. Код репозитория не менялся: метод подменяется снаружи
([`serve_with_restart.py`](evidence/V0.6-goal-restart-2026-11-05/serve_with_restart.py)).

Предсказание до запуска: короткая цель дойдёт до конца как минимум в 4 из 5.

```
цель                  с возвратом    чем закончилось
короткая              2 из 5         во всех 5 номер, Search, ссылка и заметка приняты; в 3 стоп на Save note, 0.54-0.69
G короткая + order@1  5 из 5         всё принято с первого раза, Save note 0.75-0.82
длинная с order@1     0 из 5         как в свежем браузере: номер и Search приняты, стоп на результатах
```

- **Предсказание неверно:** 2 из 5 вместо 4 из 5. Контрольная цепочка до серии тоже дошла (`restart/pilot`), в счёт она не входит.
- **Гипотеза подтверждается в той части, которую проверяла.** Поле больше не мешает: во всех 15 цепочках номер принят сразу (0.95-0.99),
  тогда как без возврата короткая цель поле не исправляла. G и длинная цель дальше ведут себя как в свежем браузере; короткая нет, см. ниже.
- **Впервые Jev сам проходит цепочку:** 7 из 15, цель G 5 из 5. Без возврата и с той же G было 0 из 5.
- **Браузер тот же.** В каждой из 15 цепочек PID браузера до и после перехода совпал (`experiment_restart` в трассе), профиль и сессия те же,
  все ограничения в завершённых прогонах `pass`, включая `runtime.ownership`. Проверка понадобилась, потому что `_record_session`
  перезаписывает сведения о процессе и сам новый Chrome не заметил бы.

Короткая цель в свежем браузере дала 9 из 9, а с возвратом 2 из 5, и все 3 неудачи на Save note. Значит, возврат не делает попытку
полностью равной свежей или разница случайна: Save note и в свежем браузере идёт почти по порогу (там бывает 0.60-0.67 перед успехом).
По 5 прогонам это не различить.

## Что это значит для кода

Возврат на `start_url` в этой серии работает, но как поведение по умолчанию он опасен: на многошаговых формах переход мог бы потерять
достигнутое (это рассуждение, такие сайты не проверялись). Раздел 10 спецификации требует новой попытки в той же browser session и
обычного цикла для новой ревизии, а про переход ничего не говорит; без него продолжает нынешний код (`BrowserControlledEnvironment.reset`). Если его делать,
то как явный выбор вызывающего агента в запросе на продолжение. Это решение о контракте, здесь оно не принято и код не менялся.

## Не установлено

- Почему упоминание слота мешает в длинных целях и не мешает в короткой.
- Откуда разница 9 из 9 и 2 из 5 у короткой цели.
- Что будет на других сайтах и версиях модели: один сайт, одна версия, по 5 прогонов на клетку, кроме указанных выше.

Свидетельства: [evidence/V0.6-goal-restart-2026-11-05](evidence/V0.6-goal-restart-2026-11-05/), решения по каждой попытке в `summary.txt`.
`no-restart` раздел 1, `restart` раздел 2 (`S` короткая, `G`, `L` длинная), токен продолжения в файлах `[withheld]`.
