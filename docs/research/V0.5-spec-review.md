# V0.5 Specification Review

Date: 2026-09-25. Reviewed commit: `dd70764`.
Scope: [V0.5 specification](../specs/V0.5.md), existing invariants, V0.4 wrapper and test site, and the routing adapter.
Verdict: **changes required before implementation**. The scope and component ownership are sound, but the specification leaves consequential runtime decisions to the implementer.

## R1 — P1: Process lifetime and late evidence have no defined owner

Specification lines 19 and 31–33 require one CLI result, bounded return despite an uninterruptible call, and collection of late evidence. No process/worker lifetime, cleanup bound, or artifact owner is defined. The V0.4 implementation invokes the controller synchronously and closes the backend in `finally`; it does not establish this behavior.

An implementation could block forever while closing, exit and discard the promised evidence, or leave a worker with access to the session. These are materially different outcomes.

Required correction: choose one bounded lifecycle for V0.5. Define when the task deadline starts, how dispatch is stopped, the finite evidence/cleanup grace interval, and who owns the worker and trace during that interval. After that interval, unresolved effects must be explicitly unknown; collection of arbitrarily late evidence cannot be promised by an exited CLI. Define a measurable process-exit bound and test a driver that never returns. A background service is unnecessary unless post-exit collection is actually required.

## R2 — P1: Cancellation is not serialized with action dispatch

Specification lines 25–26 and 31 promise no new dispatch after accepted cancellation but only prescribe checks before the driver call. The existing wrapper has a check-to-call gap: cancellation can arrive after the flag check and before `inner.execute`. Moving the same checks into `src/` will not remove that race.

Required correction: define the linearization point for dispatch and cancellation in one synchronized state transition. Distinguish queued, admitted/dispatched, and externally applied actions; a server request timestamp is not the dispatch timestamp. If dispatch wins, the action is in flight; if cancellation wins, no driver invocation is permitted. A pending worker command must pass the same gate before execution. Verify both interleavings using barriers rather than timing-dependent sleeps.

## R3 — P1: Result fields and terminal precedence remain ambiguous

Specification lines 15–19 name execution outcome, final task outcome, verifier outcomes, and statuses without enums or a transition/mapping table. A2 says to follow the verifier in both directions, while the invariants also say protocol errors, timeout, and cancellation cannot be masked as completion. A plain decline to finish must be distinguished from those stop conditions.

For example, the document does not give one exact result for a verifier pass after a protocol failure, or a verifier pass after accepted cancellation. Nor does it explain which field records a later discovered constraint violation without rewriting a terminal status.

Required correction: define minimal request/result schemas, allowed statuses and reason codes, and the completion/stop precedence table. Include normal finish, no confident action, protocol error, missing verification, verified failure, cancellation followed by a confirmed external effect, and an already-satisfied goal. Define the new CLI command, cancellation interface, and exit-code mapping. Reject invalid input explicitly rather than manufacturing an execution attempt.

## R4 — P1: Freshness and permission enforcement lack an adapter contract

Specification lines 15 and 25 require explicit permissions, fresh target identity, and rejection of stale element indices, while declining to treat the spike's label regex/private `_last` lookup as a general mechanism. No replacement target descriptor, supported permission vocabulary, or revalidation operation is specified. Filtering inadmissible micro candidates before selection, required by INV-04, is also not described.

Required correction: define one small supported action vocabulary and observation/target envelope for the controlled site. Bind the chosen action and immutable parameters to an observation and session; specify how the browser adapter rechecks the target and exposes only admissible candidates. Document any necessary dependency-specific access at that boundary. Unsupported checks must yield a blocker. Test an element replacement/reindexing while the decision is pending. Do not claim atomicity of a changing DOM or general isolation of arbitrary web pages.

## R5 — P2: Verification can inherit insufficient or contaminated fixture evidence

Specification lines 27 and 41 require fresh server evidence but do not identify supported predicates or how evidence belongs to one run. In V0.4, the navigation verifier accepts any GET to `/reports`; that proves a visit, not that the browser is currently there. The fixture has global state and no run identifier. Its delayed export increments global state after sleeping, so resetting the fixture while an earlier export is pending can contaminate a later run.

Required correction: define exact scenario predicates and distinguish final-state goals from event-history goals. Capture a baseline and isolate or identify each fixture run; use a separate fixture process per run or drain/reset safely with run correlation. Include an old delayed action completing after a new run starts, and a visit followed by navigation away. Do not reuse historical GET evidence as a current-location check.

## R6 — P2: Retry and model-call accounting do not define their boundaries

Specification lines 15, 26, and 35 name finite counters but leave the unit of a step, provider call, and retry unspecified. A new model-selected click on the same submit button can repeat a non-idempotent operation without being labeled a retry. Counting only around `execute` also misses model calls made without a driver action.

Required correction: define counter units and their reservation points, including macro and micro decisions and re-observation. Apply uncertainty handling to subsequent proposals for the same operation, regardless of whether they are called retries. V0.5 can set automatic action retries to zero. Record model cost when measurable and explicitly report missing cost information. Test repeated submit proposals after a lost response, not only a retry helper.

## R7 — P2: The acceptance gate has no fixed coverage or pass threshold

Specification lines 39–50 bundle many independent failure modes into eight rows and then request only the 'supported end-to-end cases' with Jev. No fixed list of live cases, repetition count, exit-latency tolerance, or treatment of skipped/failed attempts is given. Different implementations could claim completion from different coverage.

Required correction: enumerate subcases and expected result fields before implementation. Separate deterministic runtime checks, deterministic real-browser checks, and live Jev checks; freeze the required runs and evidence for each. Include all R1–R6 regressions, keep successful tasks and expected stops separate per North Star, and mark an unexecuted required case as pending rather than passed. Keep the packet small and reproducible.

## Recommended revision order

1. Resolve lifecycle and dispatch/cancellation ordering (R1–R2).
2. Define the minimal schemas, state table, CLI surface, and adapter checks (R3–R4).
3. Specify fixture evidence and budget/repetition semantics (R5–R6).
4. Freeze the acceptance matrix and evidence packet (R7).

Retain Browser Use, SystemOneHarness's ownership of the action loop, independent verification, and the limited V0.5 scope. No dynamic capability registry or self-extension implementation is required to address these findings.

## Review evidence and limits

This was a specification and source inspection, not a runtime execution or a live Jev run. The cancellation race and fixture contamination are derived from the code paths, not reported as reproduced failures. Formatting checks on the specification do not establish architectural completeness.
