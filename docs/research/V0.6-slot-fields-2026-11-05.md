# V0.6: слот знает, в какие поля его можно вводить, 2026-11-05

[Прогоны многошаговой формы](V0.6-restart-2026-11-05.md) показали, что без нужного значения Jev подставляет чужое: в 3 цепочках из 10 ввёл `team@1` в поле Note и в одной
записал это на сервер дважды. Спецификация (раздел 7) уже требовала проверять разрешённые пары «поле и слот» кодом, но в коде этого не было и в контракте для этого не было поля.

Настоящий Jev (`typesafe/jev-1.14-20261014`), порог 0.70, Windows 11, Chrome 142, запуск по SSH на отдельной машине.

## Что сделано

Слот получил необязательное поле `fields`: имена полей, куда значение можно ввести. Сравнение идёт с label или accessible name, без учёта регистра и лишних пробелов.

- `fields` нет: значение идёт в любое поле, как раньше. Это нужно для незнакомых сайтов, где вызывающий агент не знает имён заранее.
- `fields: []`: значение никуда не вводится, оно только для проверки (например, `record@1`).
- Поле, для которого нет подходящего слота, модели не предлагается. Его имя попадает в трассу и в `handoff.fields_without_slot`: так вызывающий агент узнаёт, какого значения не хватает.
- В списке значений остаются только слоты, подходящие хотя бы к одному полю страницы.
- Выбранная неподходящая пара отклоняется до отправки: `slot_field_mismatch`. Попытка продолжается, повторы ограничены счётчиком `no_progress`.
- Новая ревизия не может поменять `fields` у прежней версии слота (`slot_reference_redirected`), для этого нужна новая версия.

В задачах демо-сайта `fields` заполнены.

## Результаты

Предсказание до запуска: на форме Jev ни разу не введёт чужое значение и не запишет неверную заметку; в цепочке заказа поле номера больше не засоряется, поэтому `restart` становится необязательным; одиночный прогон не ухудшается.

```
сценарий                               дошли до completed/verified   без fields (прошлые отчёты)
форма из 3 шагов, продолжение          10 из 10                      2 из 5
цепочка заказа, продолжение            3 из 5                        0 из 5
цепочка заказа, restart                4 из 5                        5 из 5 и 3 из 3
один прогон, свежий браузер            4 из 5                        9 из 9 с короткой целью
```

Сайт подтвердил форму сам: в каждой из 10 цепочек ровно по одной отправке каждого шага и одна верная заметка (`console.txt`).

Во всех 25 прогонах Jev вводил только верные пары: `order@1` в Order number 15 раз, `note@1` в Note 24 раза, `team@1` в Team 10 раз. Поле без слота попало в наблюдения 51 раз.
Без значения заметки Jev в 7 цепочках просил помощи, а в 3 упирался в Next с уверенностью 0.22-0.41.

Где остановились 4 незавершённых прогона:

```
цепочка, продолжение  2  стоп на Save note, 0.38-0.69
один прогон           1  стоп на Save note, 0.52-0.68
цепочка, restart      1  стоп на Search, 0.60-0.65
```

- **Подстановка чужого значения в этих сценариях закрыта:** было 3 из 10 и одна неверная запись, стало 0 из 10.
- **Цепочка заказа теперь идёт и без `restart`:** было 0 из 5, стало 3 из 5, потому что поле не засоряется. Разница с `restart` (3 и 4 из 5) на таких числах ничего не значит. `chain_demo` пока продолжает его использовать.
- **Одиночный прогон ухудшения не показывает, но и не доказывает обратного.** 4 из 5 против 9 из 9 укладывается в известную проблему: Save note идёт почти по порогу (в 2 из 9 прошлых прогонов там тоже были отказы перед успехом).

Рост формы с 2 из 5 до 10 из 10 объясняется этим же: все 3 неудачи без `fields` были из-за чужого значения в поле Note. Сравнение идёт с 5 цепочками, так что точная величина роста не установлена.

Набор `test_v06_browser_*.py` на Windows: 180 тестов, OK. На Linux не запускался.

## Что это не закрывает

- **Защита работает, только если вызывающий агент заполнил `fields`.** Без него поведение прежнее, и подстановка возможна. На незнакомом сайте имён полей заранее может не быть. Стоит ли со временем требовать `fields`, здесь не решалось.
- **Неверное имя поля не приводит к ошибке, а скрывает поле:** Jev его не увидит, а `fields_without_slot` назовёт. Значит, ошибка в имени поля остановит попытку, но ничего не испортит.
- **Отправка формы с незаполненным полем ничем не запрещена.** Jev не нажимал Next без заметки только потому, что не был уверен (0.22-0.41). Это порог, а не правило.
- **Проверка пары после выбора в этих прогонах ни разу не сработала:** на этих страницах по одному текстовому полю, и лишние значения отсеиваются раньше. Её покрывает тест через путь помощи, но не прогон с настоящим Jev.
- Другие сайты и версии модели не проверялись.

Свидетельства: [evidence/V0.6-slot-fields-2026-11-05](evidence/V0.6-slot-fields-2026-11-05/), решения по каждой попытке в `summary.txt`, вывод с записями сайта в `console.txt`.

## 2026-11-07: сравнение по полному имени поля

Ревью PR #14 (Codex) нашло, что слот сравнивался с именем поля, обрезанным до 80 символов (`MAX_NAME` в `_signature`), а `fields`
принимает имена до 200. Поле с длинной подписью не находило свой слот и пряталось от модели, а два поля с одинаковыми первыми 80
символами для слота были одним полем. Теперь у записи поля есть `field_name`, полное доступное имя, и все четыре места сравнения
смотрят на него; обрезанное имя осталось для показа и для идентичности.

Проверка: страница `/long-fields` на демо-сайте, два поля с одинаковыми первыми 87 символами подписи, слот разрешён только для одного.
На новом коде он предлагается с `slot_refs: ["note@1"]`, второе поле названо в `fields_without_slot`. На старом коде оба поля скрыты.
`test_v06_browser_handoff` на Windows: 25 тестов, OK. Модель по-прежнему видит обрезанные имена, и два таких поля для неё выглядели бы
одинаково, если бы слот подходил к обоим; это не исправлялось.

Второй круг ревью (Codex) нашёл, что проверка перед вводом сравнивала подпись узла, а в ней имя тоже обрезано до 80 символов: поле,
переименованное между наблюдением и вводом после 80-го символа, получало значение, разрешённое для старого имени. Теперь перед вводом
полное имя свежего узла сравнивается с наблюдавшимся, и при расхождении цель устаревшая (`stale_target`). Тест меняет подпись через CDP
между наблюдением и вводом: на старом коде значение введено, на новом ввод отклонён. `test_v06_browser_handoff` на Windows: 26 тестов, OK.
