# V0.6: локальная решающая модель laya-browser вместо Jev, 2026-10-13

Датированный отчёт о подключении локальной решающей модели к общему браузерному пути V0.6 и о
первых прогонах. Это **не Jev** и не сравнение Jev/LLM (M5). Выводы о качестве — по одной демо-задаче
и трём прогонам; калибровки нет.

## Что за модель и почему понадобился переходник

`cklxx/laya-browser` — неавторегрессионный энкодер laya (mmBERT-base, 322M), дообученный как решающая
голова `browser-use/jev-ultrafast`. Сервер модели (`laya_browser.py serve`) говорит на проводе System One
(`POST /v1/systemone`), тем же, что TypeSafe, и SOH-клиент доходит до него без изменений. Но провод — это
только конверт:

| | SystemOneHarness отправляет | laya читает |
|---|---|---|
| состояние | `goal`, `instructions`, `observation{summary,…}`, `history` (строки) | `page{url,title,text}`, `elements[]`, `recent_actions[]` |
| вопросы | свои тексты, ключи `next_action`, `click__element`, … | тексты обучения: `operation` + `<op>_target`, инструкции `NEXT_ACTION`/`TARGET` |

Первый прогон через `--action-provider jev` с `TYPESAFE_API_KEY=local` дошёл до модели, но ни одного из
трёх ключей состояния у неё не было: три одинаковых ответа с уверенностью **0.0765** и `needs_handoff`.

## Что сделано

`--action-provider laya --decisions-url URL` (`adapters/system_one/laya_provider.py`):

- переводит один запрос SOH в формат обучения и отправляет **ровно один** HTTP-запрос (`retries=0`,
  каждый запрос резервируется против `max_model_calls`, как у Jev);
- тексты `NEXT_ACTION`, `TARGET`, подписи операций, `DONE`/`BLOCKED` скопированы из `laya_browser.py`
  дословно (sha256 `3dfaba40…`, записан в модуле); страничные контролы — из `snapshot.js` jev-ultrafast:
  `Scroll down` (только когда ниже есть содержимое), `Scroll up` (только когда прокручено), `Wait for the page
  to update`;
- элементы нумеруются 1..N в порядке страницы, ссылкам снимается наш суффикс `→ /путь`, выбранная опция
  списка идёт текущим значением, а не целью; разметка Browser Use (`[25]<input/>`, `|SHADOW|`, `*`) из текста убрана;
- ответ отображается обратно на ключи SOH и проходит тот же валидатор и тот же порог 0.7.

Что решает не модель — записано в каждом `decision_received` (`translated.derived`):

| Что | Откуда |
|---|---|
| операция и цель | laya |
| какой слот вписать (`type_text__value`) | переходник: один слот — он; несколько — по имени ссылки слота против имени поля (`order@1` ↔ «Order number»); иначе вероятность 0 и отказ шлюза. jev-ultrafast отдаёт текст отдельной LLM, laya его не выбирает |
| `goal_reached` | вероятность `DONE` у laya |
| направление прокрутки | какой из двух контролов выбран |
| `go_back`, `switch_tab` | не предлагаются: в обучении их не было (`translated.not_offered`) |

В результате прогон подписан `decision.kind=laya`, `config_id=laya:laya-browser@…`; `served_models` —
то, что вернул сервер. Поля `id` сервер не отдаёт, `request_id` пуст.

## Прогоны (демо-задача `order-note`, сервер модели через ssh-туннель на loopback)

| Прогон | Что было | Итог |
|---|---|---|
| без переходника | 3 запроса, уверенность 0.0765 ×3, отказ шлюза | `incomplete/needs_handoff` |
| с переходником, до исправления истории | ввод 125 (0.81) → Search (0.84) → **Search ещё 59 раз** (0.75–0.82) | `incomplete/deadline`, 62 вызова, ни одного POST на сервер сайта — [before-fix-result.json](evidence/V0.6-laya-run-2026-10-13/before-fix-result.json) |
| с переходником, после исправления | ввод 125 (0.81, 620 мс) → Search (0.84, 710 мс) → **`finish`** (0.81, P(DONE)=0.94) на странице результатов | `incomplete/verification_unknown`, 3 вызова, 3 действия — [result.json, trace.jsonl](evidence/V0.6-laya-run-2026-10-13/) |

Причина повторов была в переходнике: `page_changed` сравнивал сырой текст, а Browser Use перенумеровывает
элементы при каждом снимке — каждое нажатие выглядело как смена страницы. Исправлено (сравнивается
то, что видит модель), закреплено тестом.

Последний прогон — ошибка суждения модели: заказ не открыт, заметка не добавлена, а laya уверена, что
цель достигнута. Без верификатора (M4) это `verification_unknown`, а не `completed` — граница сработала.

Это известный отказ чекпойнта: по README модели (раздел «What still fails», процитирован владельцем сервера,
сам README здесь не перечитан) ранняя остановка на странице выдачи — около 60 % провалов на реальных сайтах, и
пять попыток автора исправить её обучением не дали результата выше шума. Уверенность при таком DONE высокая, порогом
он не отсекается; защищать от него должна внешняя проверка цели в ReflexMesh (M4), а не модель.

Задержка 0.6–1.1 с против 0.23–0.37 с у владельца сервера через тот же путь — не из-за двухпроходного разбиения
широких вопросов: во всех записанных запросах не больше 5 вариантов на вопрос, а разбиение начинается с 61. Причина
не установлена.

## Находка, которая касается не только laya

60 одинаковых нажатий Search не остановило ничто, кроме дедлайна. Проверка SOH на повтор сравнивает
действие с параметрами, а Browser Use даёт той же кнопке новый номер на каждом снимке (26 → 55 → 92 → …),
так что повтор каждый раз «новый». У jev-ultrafast такая страховка есть на её стороне (по словам владельца сервера, `agent.py:156`: три повтора с `page_changed=False` и не `wait` считаются зацикливанием). Правило §8 «три цикла без нового состояния» в нашем пути этим не
закрыто; `runtime.no_uncertain_repeats` честно остаётся `unknown`. Закрыто в тот же день: подпись
состояния страницы больше не включает номера Browser Use, повтор того же действия (по роли, имени, опции, адресу,
слоту) в том же состоянии отклоняется до отправки, три цикла без нового состояния дают `needs_handoff/no_progress`.
Сценарий «Search снова и снова» на реальном Chromium теперь даёт два нажатия (на форме и на выдаче) и остановку
(`tests/test_v06_browser_real.py`).

## Не проверено

- Совпадает ли наш текст страницы с тем, что jev-ultrafast брал в обучении (`innerText` против очищенного
  представления Browser Use); подсказки полей из патча автора (placeholder, input_type, format_hint) не передаются.
- Ни одна задача, кроме демо, и ни одного повторного замера задержек (0.6–1.1 с на решение через туннель; на
  самой машине модели — 0.08 с по словам её владельца).
- Подходит ли порог 0.7 для laya: её уверенность не откалибрована (по карточке модели).
- Совпадает ли наш `page_changed` с обучением: мы сравниваем URL и очищенный текст, поэтому ввод в поле
  без других изменений записывается как `page_changed: false`; как считал jev-ultrafast, не сверено.
- Task API (`api/service.py`, MCP) провайдера `laya` не знает: там по-прежнему `script` и `jev`.

Страница просмотра (`reflexmesh browser view`) показывает, что заполнил переходник: у таких параметров
пометка «выбрал переходник, не модель», в раскрытой строке — список с причиной.
