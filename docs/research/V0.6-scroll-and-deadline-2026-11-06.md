# V0.6: прокрутка и лимит времени, 2026-11-06

Два дефекта из [сравнения M5](V0.6-M5-results-2026-11-06.md) и медленный поиск процессов на Windows, найденный при их разборе. Прокрутка и лимит воспроизведены тестами, которые на старом коде падают; поиск процессов замерен до и после.

## Прокрутка

**Что было.** `quotes-scroll` не прошёл ни одного запуска ни в одном режиме: вторую прокрутку вниз runtime отклонял как
`repeated_action`. Ключ повтора это действие плюс подпись страницы, а подпись в `_page_signature` строится из URL и текста.
Текст читается целиком и при прокрутке не меняется, пока новая порция не подгрузилась у самого низа, поэтому для runtime
окно, которое сдвинулось, было тем же состоянием. По той же подписи считался и счётчик «три цикла без нового состояния»
(`no_progress`).

**Что сделано.**

- Адаптер кладёт положение окна (`pixels_above` из `page_info`) в отчёт наблюдения как `scroll_y`.
- `state_key` для `scroll` добавляет его к ключу. Прокрутка из нового положения больше не повтор. Прокрутка, которая окно не
  сдвинула (конец страницы), сохраняет ключ и по-прежнему отклоняется. Для остальных действий ключ прежний: тот же клик на
  той же странице остаётся повтором, где бы ни стояло окно.
- Счётчик `no_progress` в `observe` сравнивает пару (подпись, `scroll_y`).
- `scroll_y` добавлен и в `obs.fields`. SystemOneHarness хеширует их для собственной остановки «то же действие на том же
  состоянии», без этого он остановил бы вторую прокрутку сам. Это меняет то, что видит модель: в наблюдении появилось одно
  число.

**Проверка.** На демо-сайте новая страница `/tall`: четыре коротких абзаца на высокой странице, текст одинаков при любой
прокрутке. Тест `test_scrolling_down_again_is_not_a_repeat_while_the_window_moves` делает три прокрутки вниз: на старом коде
вторая отклонена (`['repeated_action'] != []`), на новом отказов нет. Два теста на поддельном адаптере проверяют ключ и
счётчик, на старом коде оба падают.

## Лимит времени

**Что было.** В M5 начальная навигация `scrape-oscars` J1 вернулась через 1796 с при `wall_seconds: 240`, а в отложенном
повторе запуски шли до 4 часов. Сторож объявлял `deadline` вовремя, но не мог остановить браузер.

- Browser Use обрабатывает свои события по одному, поэтому `session.kill()` сторожа вставал в очередь за зависшей навигацией.
- Каждый вызов в цикл драйвера (`BrowserEnvironment._run` в SystemOneHarness) ждёт до 120 с. После зависания такие вызовы
  шли друг за другом: последний взгляд оракула, закрытие сессии. Отсюда длительности, кратные 120 с.

**Что сделано.**

- Сторож через 5 с после остановки сам завершает процессы, у которых в командной строке профиль этой попытки, и только потом
  просит Browser Use остановиться, не дожидаясь ответа. Зависший вызов падает на закрытом соединении.
- После этого каждый вызов в цикл драйвера ограничен 2 с (`KILLED_CALL_SECONDS`), а закрытие не ждёт штатной остановки,
  которая встала бы в ту же очередь: процессов уже нет, цикл просто останавливается.
- Процессы сессии, переданной цепочке (`retained`), сторож не трогает.

**Проверка.** Тест `test_deadline_ends_the_attempt_even_if_the_first_navigation_never_loads`: начальная страница на сокете,
который принимает соединение и не отвечает, лимит 5 с. На ноутбуке с Windows 11: старый код 42.8 с (здесь навигацию в итоге
бросил сам Browser Use, в M5 он ждал до 30 минут), новый в пределах 30 с, процессов браузера не остаётся.

Раскладка одной такой попытки с лимитом 10 с на новом коде: остановка в 10 с, сторож в 15 с, навигация упала в 17.2 с,
попытка вернулась в 25.7 с.

## Поиск процессов на Windows

**Что было.** Попытка в конце несколько раз ищет процессы, у которых в командной строке путь к её профилю: сторож,
ожидание выхода браузера, две оценки ограничений, уборка. На Windows `processes_using` читал командную строку каждого
процесса через psutil, это около 2.1 с на поиск при 513 процессах. В раскладке выше это 8 с из 8.5 с завершения, и так на
каждой попытке на Windows, не только на зависшей: время всех режимов в M5 включает эти секунды.

Отбор по имени процесса до чтения командной строки занимал бы 0.01 с, но этот поиск даёт и вердикт о владении («профилем
больше никто не пользуется»). С отбором по имени вердикт перестал бы видеть программу с другим именем, открывшую тот же
профиль, и сказал бы `pass` там, где должен сказать `unknown`. Это не сделано.

**Что сделано.** На Windows поиск идёт одним запросом WMI (`Win32_Process`, `CommandLine LIKE`), командные строки читает
служба WMI. Замер с живым Chrome на том же ноутбуке:

```
способ                               время поиска        найдено
psutil, каждая командная строка      2.11 2.12 2.14 с    11
WMI из Python (pywin32)              0.36 0.38 0.76 с    11, те же
WMI через запуск PowerShell          0.78 0.80 1.00 с    11, те же
psutil, отбор по имени               0.01 с              11, не взят
```

В `LIKE` символы `_`, `%`, `[` служебные, а кавычка закрывает строку, поэтому всё, кроме букв, цифр, `-` и `.`, в образце
заменяется на `_` (любой один символ), а точное совпадение пути проверяется уже в Python. Если WMI спросить нельзя (нет
pywin32, ошибка COM), поиск идёт прежним путём через psutil. pywin32 в окружении уже есть как зависимость других пакетов,
проект её не объявляет.

**Проверка.** Тест на Windows запускает процесс с меткой, где есть `_`, `[`, `%` и кавычка, и подставной процесс, который
отличается только в этих местах. WMI находит первый, не находит второй и совпадает с полным поиском psutil. Без точной
проверки пути тест падает: находится подставной. Зависшая попытка с лимитом 10 с: завершение 1.4 с вместо 8.5 с, вся
попытка 17.0 с вместо 25.7 с. Граница в тесте зависания ужесточена до 20 с при лимите 5 с.

## Не проверено

- Сайты M5 этим кодом не запускались: раздел 17 не разрешает запускать адаптер на сайтах замороженного набора вне
  замороженного прогона, повторное сравнение будет новым экспериментом.
- Зависание внутри шага после начальной навигации (клик, ввод) тест не воспроизводит. Путь сторожа тот же.
- Linux: оба новых теста на настоящем браузере запускались только на Windows. Поиск на Linux не менялся (`/proc`).
- Обычная, не зависшая попытка на Windows: ускорение завершения на ней ожидается то же, отдельно не замерялось.

Набор `test_v06_browser_*.py` на том же ноутбуке: см. описание коммита.
