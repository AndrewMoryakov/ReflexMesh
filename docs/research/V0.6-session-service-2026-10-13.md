# V0.6: сервис сессий `reflexmesh browser serve`, 2026-10-13

После M3 продолжение в той же сессии было доступно только из Python (`BrowserCore`): одноразовый `browser run` не
держит браузер после выхода и по §14 продолжения не предлагает. Сервис сессий — долгоживущий процесс, который держит
цепочки, их открытые браузеры, lease и токены, и отвечает теми же операциями, что embedding.

## Что сделано

```sh
reflexmesh browser serve --socket ./svc.sock --state-dir ./state --action-provider jev \
  --checks experiments/v06/checks/order-desk.json            # печатает {"listening": ...} и работает до shutdown
reflexmesh browser submit   --socket ./svc.sock --input task.json
reflexmesh browser resume   --socket ./svc.sock --input continuation.json
reflexmesh browser cancel   --socket ./svc.sock --chain-id ID
reflexmesh browser status   --socket ./svc.sock
reflexmesh browser shutdown --socket ./svc.sock
```

- **Обёртка без своей политики** (§14): `execute`, `resume`, `cancel` уходят в `BrowserCore` как есть; токены, lease,
  бюджет и правила успеха — в ядре. `status` — список цепочек (попытки, открыта ли сессия, идёт ли помощь, остаток
  бюджета); `shutdown` отменяет идущие попытки и закрывает все браузеры.
- **Транспорт — Unix-сокет, не HTTP** (§14: HTTP API в V0.6 не добавляется): один JSON-запрос и один JSON-ответ на
  соединение. Сокет создаётся с правами 0600, у каждого соединения проверяется `SO_PEERCRED` — другой пользователь
  ответа не получает. Каталог состояния — 0700, у каждой цепочки свой подкаталог `chain-<id>/attempt-<n>`.
- **Соединения обслуживаются в потоках**: `cancel` проходит, пока `submit` той же цепочки ещё выполняется.
- Живой сокет второй сервис не займёт; брошенный (никто не слушает) — заменяется; файл, который не сокет, не удаляется.
- Ошибка внутри обработки уходит клиенту только типом исключения (текст мог бы содержать текст страницы).
- Провайдер собирается так же, как в `browser run` (общая функция); сценарный провайдер в сервисе принимает список
  сценариев — по одному на попытку цепочки.
- Код возврата клиента: как у `browser run` по `attempt_status` (0, 3, 4, 5, 130); 0 для `browser-progress` и
  `status`; 2 для ошибки или недоступного сервиса.

`browser run` остаётся одноразовым и по-прежнему пишет `continuation: {"allowed": false, "reason":
"no_session_service"}`; продолжение через сервис — `allowed: true` с токеном в ответе клиенту (в файл не пишется).

## Прогон через сервис с настоящим Jev

Процесс `serve` с `--action-provider jev`, клиент — отдельные вызовы CLI из скрипта
([flow.py](evidence/V0.6-session-service-2026-10-13/flow.py)): задача `order-note-verified` без номера заказа в
ревизии 1, затем ревизия 2 с номером и уточнённой целью, затем, если Jev снова передаст управление, — помощь LLM
(скрипт в роли LLM выбирает вариант по видимому имени).

| Попытка | Кто | Что | Итог |
|---|---|---|---|
| 1, epoch 0 | Jev | номера нет: вписал якорь, поиск пуст | `needs_handoff`, `no_confident_action` |
| 2, epoch 1, ревизия 2 | Jev | номер, поиск, заказ, вписал заметку; «Save note» — 0.58–0.67, ниже порога | `needs_handoff`, `no_confident_action` |
| 3, epoch 2 | помощь LLM | `browser-progress` на странице заказа; один шаг — «Save note» | **`completed/verified`**, все критерии и шесть ограничений `pass` |

Цепочка: 19 шагов и 15 вызовов модели из 64/96, одна сессия Chrome, на сайте одна заметка и один POST.
Свидетельства: [evidence/V0.6-session-service-2026-10-13](evidence/V0.6-session-service-2026-10-13/). В двух прогонах
подряд Jev вёл себя по-разному во второй попытке (в первом он дошёл до `completed` сам, во втором остановился перед
сохранением) — поведение модели здесь не детерминировано, и это сведение для M5, не для обёртки.

## Проверки

```sh
.venv/bin/python -m unittest tests.test_v06_browser_service     # 6: 4 протокол без браузера, 2 через CLI с Chromium
.venv/bin/python -m unittest discover -s tests -p 'test_v06_browser_*.py'   # 157 OK с REFLEXMESH_CHROME
```

Сквозные тесты запускают `serve` отдельным процессом и `submit`/`resume`/`status`/`cancel` — отдельными процессами
CLI: продолжение в том же браузере до `completed`; токен второй раз отклонён; токен не попал в `result.json`; отмена
работающей попытки через второе соединение — `cancelled/cancel_requested`, код 130.

## Попутно

Соседняя сессия на этом хосте нашла восемь брошенных тестовых сайтов V0.5 (`experiments/v05/site/server.py --run-id
real-browser`). Причина — `tests/test_v05_real_browser.py`: его `setUpClass` падает (давнее падение, не связано с
V0.6), а `tearDownClass` после упавшего `setUpClass` не вызывается, и сайт остаётся слушать порт. Остановка сайта
теперь регистрируется `addClassCleanup` сразу после запуска; после прогона этого модуля процессов сайта не остаётся.
Три брошенных сайта и один осиротевший Chrome от моих прогонов этого дня погашены по PID.

## Не сделано

- MCP-обёртка (`browser_task`, `browser_resume`, `browser_cancel`) и Pi — следующий тонкий слой поверх того же ядра.
- Сервис не переживает перезапуск: цепочки и браузеры живут в памяти процесса.
- Одна конфигурация провайдера на процесс; выбор провайдера на задачу — нет.
