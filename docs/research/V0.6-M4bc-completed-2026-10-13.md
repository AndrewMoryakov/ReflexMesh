# V0.6 M4b–M4c: первый `completed`, 2026-10-13

Вторая и третья части M4 (V0.6 §11): зарегистрированные проверки и свидетельство владения браузерной сессией.
С ними попытка впервые получила `completed/verified` — на демо-сайте, с настоящим Jev. Это не готовность на
произвольных сайтах: на сайте без зарегистрированного источника `no_uncertain_repeats` и эффекты кликов остаются
`unknown`, и `completed` там по-прежнему недостижим (это правило, а не недоделка).

## M4b: зарегистрированные проверки

**Реестр — конфигурация сервиса, не задачи.** `reflexmesh browser run --checks FILE`:

```json
{"checks": {"order_desk.note_saved_once": {"kind": "order_desk", "url": "http://127.0.0.1:8770"}}}
```

Задача ссылается только на `check_id` из этого файла; URL, код или вид проверки она передать не может. Вид (`kind`) —
код в `verification/checks.py` со своими строгими аргументами; неизвестный вид, лишнее поле, обычный http не на
loopback — отказ при загрузке. `registered_check` с незарегистрированным id — `blocked/unsupported_criterion` до
запуска браузера.

**`order_desk` — тестовый оракул демо-сайта, и только его.** Привязка к попытке — по образцу захвата фикстуры V0.5:

- до первой навигации проверка захватывает сайт (`POST /__claim` с `attempt_id`) и получает секретный токен; второй
  захват, пока первый активен, — `409`, попытка `blocked/unsupported_criterion` (`check_busy`) без запуска браузера;
- сайт помечает каждый запрос активным захватом; свидетельства (`GET /__evidence`) отдаются только с токеном и
  содержат запросы под захватом, добавленные заметки и число ещё обрабатываемых запросов; токен не попадает ни в
  журнал, ни в результат, ни в `repr`;
- после остановки браузера (ничего больше прийти не может) проверка решает:
  - критерий: заказ `subject` получил ровно одну заметку, равную ожидаемому слоту;
  - эффекты: клик, отправляющий POST-форму, — `applied`, если POST на этот путь ровно столько, сколько таких кликов
    отправлено; остальное — `not_applied`, потому что этот сайт меняет состояние только POST'ом (свойство
    оракула, записанное в коде вида);
  - повторы: POST больше, чем отправленных кликов, — `fail` (в том числе повтор внутри драйвера); POST, которого не
    объясняет ни один клик (например, скрипт страницы отправил сам), — решения нет, эффекты остаются `unknown`.

Чтобы клик можно было сопоставить с запросом, адаптер записывает у цели, что она отправит: у ссылки — `GET href`, у
кнопки отправки — `method`/`action` её формы (с `formmethod`/`formaction`). Обработчик на скрипте — `request: null`,
такой клик не доказывается.

Ограничение захвата: он отличает эту попытку от других попыток ReflexMesh (второй захват отклоняется), но не от
постороннего клиента, который обратится к сайту во время захвата; такой POST будет засчитан как лишний — в сторону
`fail`, не `pass`.

## M4c: владение браузерной сессией

V0.5 оставлял `runtime.ownership` всегда `unknown` («исключительность контроллера браузера недоступна»): CDP
слушает TCP-порт на loopback без аутентификации, и подключиться может любой локальный процесс. Спецификация задаёт
область этого ограничения — «управляемые ReflexMesh исполнители и конкретная сессия»; в ней теперь собирается
свидетельство (`scope: browser_session_launched_by_attempt`):

- браузер запущен этой попыткой: процесс Chrome — потомок нашего процесса, профиль — каталог попытки (0700),
  проверено, что Chrome использует именно его;
- это тот же процесс всю попытку (время создания процесса сверяется на каждом наблюдении);
- **на каждом наблюдении** проверяются все установленные соединения к отладочному порту: клиент — только наш процесс.
  Чужой процесс — `fail` и `failed/constraint_violated`; соединение, владельца которого не видно (сокет другого
  пользователя), — `unknown`;
- к моменту приёма итога браузер закрыт, процессов с этим профилем не осталось.

Чего это не исключает, записано в самой строке результата: клиент, подключившийся и отключившийся между двумя
наблюдениями, не виден.

## Ворота `completed`

`completed/verified` выдаётся, только если все критерии `pass`, все шесть `runtime.*` `pass`, у каждого действия
эффект не `unknown`, ничего не в полёте и свидетельства слотов не сдвинулись с момента оценки (`expected_generation`).

## Проверки

```sh
.venv/bin/python -m unittest tests.test_v06_browser_checks     # 9: реестр, суждения, протокол захвата сайта
.venv/bin/python -m unittest discover -s tests -p 'test_v06_browser_*.py'   # 142 OK с REFLEXMESH_CHROME
```

Сквозные тесты (`test_v06_browser_real.py`): `completed` при всех свидетельствах; второй процесс на отладочном
порту — `ownership: fail`, `failed/constraint_violated`; занятый источник — `blocked` без единого запроса к
страницам; незарегистрированная проверка — `blocked`.

Найдено по дороге: на демо-сайте счётчик обрабатываемых запросов уменьшался после отправки ответа, и вопрос о
свидетельствах сразу после ответа видел `pending: 1` (тест падал примерно в одном запуске из шести). Теперь запрос
перестаёт считаться обрабатываемым до отправки ответа; 15 запусков подряд без падений.

## Не проверено и не сделано

- `completed` на любом сайте, кроме демо: для этого нужен зарегистрированный источник этого сайта (его API) —
  других видов проверок, кроме `order_desk`, нет.
- Task API и MCP о `--checks` и о провайдере `laya` не знают.
- Проверка соединений к отладочному порту — выборочная (на наблюдениях), не непрерывная.
- Начальная навигация записана с `producer` провайдера решений, хотя её делает runtime (помечена `bootstrap`).
