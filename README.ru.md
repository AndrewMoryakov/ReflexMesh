<h1 align="center">ReflexMesh</h1>

<p align="center"><b>Решайте, как выполнить задачу AI-агента — через API, CLI, модель или браузер, — держите выполнение в рамках разрешений и лимитов и считайте задачу сделанной только после подтверждения верификатором. Ранний исследовательский код для тех, кто строит агентов.</b></p>

ReflexMesh — универсальный слой принятия решений и координации выполнения
для AI-агентов: выбор инструментов и исполнителей, контроль ограничений и
проверяемый результат. Целевые пути включают API/MCP tools, CLI/скрипты,
модели и агентов, computer use, макросы и workflows.
Jev предназначен для ограниченного выбора, LLM — для планирования и генерации
содержания; код контролирует разрешения и выполнение, verifier проверяет результат.
Браузер — первый прикладной сценарий; desktop добавляется после V1.0.
Интерактивные интерфейсы не определяют границ проекта.
Это целевая концепция; её текущий реализованный объём описан ниже.

**Что есть сегодня:** маршрутизация задач (заглушка с фиксированным порядком по умолчанию или настоящий JevRouter по HTTP), измеренное исследование маршрутизации и контролируемый браузерный runtime, который всё ещё строится. Исполнители API/MCP, CLI, desktop, макросов и workflow — целевые направления, а не интеграции; см. [Статус](#статус).

## Зачем ReflexMesh?

- **Если** ваш агент может выполнить работу несколькими способами — прямым API или MCP tool, скриптом, моделью, браузером, — **то** ReflexMesh призван выбирать среди разрешённых вами способов и оставлять владение разрешениями и выполнением коду, а не модели.
- **Если** «агент говорит, что готово» вас не устраивает, **то** здесь статус завершения назначает runtime, и он принимается только когда верификатор подтвердил цель. Spike V0.4 показал, зачем это нужно: собственный статус `completed` у harness ошибался в обе стороны, а верификатор по состоянию сервера оба раза в наблюдавшихся случаях был прав.
- **Если** вам нужен честный ответ «ни один из этих маршрутов не подходит», **то** адаптер предлагает Jev кандидата `NONE`; в исследовании V0.3b это подняло долю корректных отказов Jev с 25% до 96% без потерь на обычных задачах.
- **Если** маршрутизация должна быть дешёвой и быстрой, **то** исследование V0.3 сообщает для Jev точность 1.00 (как у gpt-5.5) против 0.65 у ручных правил, медианную задержку 0.6 с против 6.4 с и примерно $0.00002 против $0.002 за решение — цифры записаны в [`docs/STATUS.md`](docs/STATUS.md) и [отчёте V0.3](docs/research/V0.3-routing.md).

Это **не** готовый фреймворк для агентов, не собственная LLM и не новая RPA-платформа; это тонкий интеграционный runtime и слой решений вокруг существующих компонентов. Сегодня не поставляется общее исполнение задач: выбранный маршрут — рекомендация, а не выполненная работа, а браузерный runtime пока остаётся контролируемым spike на тестовом сайте. Полностью офлайн-работа и поддержка всех ОС не обещаны — путь Jev предполагает облачного провайдера. Неподдерживаемая задача получает явный отказ или возвращается вызывающему агенту.

## Возможности

- **Явный контракт маршрутизации** — на вход идёт Task, на выходе JSON-решение с понятным статусом (выбран, отказ, нужно подтверждение, ошибка адаптера) и различными кодами выхода `0` / `3` / `4` / `5` / `2`.
- **Честная заглушка по умолчанию** — провайдер по умолчанию выбирает из пересечения `capabilities` и `allowed_routes` в фиксированном порядке и помечает себя `is_stub=true`, `execution_performed=false`; цель он никогда не анализирует.
- **Реальная маршрутизация через JevRouter** — включаемый явно HTTP-адаптер к локальному JevRouter; при любой ошибке модель **не** подменяется молча заглушкой. Live gate V0.2 закрыт для OpenRouter; прямой typesafe не проверен.
- **Измерено, а не предположено** — маршрутизация оценена по фиксированному протоколу (V0.3, вердикт «useful») и отдельно поведение отказа (V0.3b); результаты и их границы опубликованы в [`docs/research/`](docs/research/).
- **Контроль принадлежит коду** — выбор маршрута сам по себе не разрешает действие; отправка формы, публикация и другие внешние эффекты не разрешаются самим выбором.
- **Контролируемый браузерный runtime (в работе)** — spike V0.4 на SystemOneHarness + Browser Use под запретом, отменой и дедлайном, принадлежащими runtime, прошёл свои проверки; код исполнения V0.5 (supervisor, TextSlots, предикаты верификатора, изолированный тестовый сайт) есть локально, а его приёмочные gates всё ещё открыты.
- **Без runtime-зависимостей** — у пакета нет ничего, кроме Python 3.11+.

## Как это работает

<p align="center">
  <img src="docs/assets/ReflexMesh-how-it-works.png" alt="ReflexMesh: пользователь передаёт новую задачу роботу-маршрутизатору, который выбирает для неё один инструмент из API, браузера, desktop и CLI; верификатор изучает результат и останавливает конвейер, если нет доказательства" width="100%">
</p>

Картинка показывает целевой дизайн. Из нарисованных инструментов строится только контролируемый браузерный путь; остальные — направления, а не реализованные интеграции.

1. **Приходит задача** от агента. Pi — первый предполагаемый клиент, но ядро остаётся независимым от него, так что те же задачи могут присылать другие агенты и программы.
2. **Маршрутизатор выбирает маршрут** из тех, что задача объявляет разрешёнными. Этот ограниченный выбор делает Jev; нынешний каталог CUA / LLM / PERCEPTION — экспериментальный набор V0, а не окончательная классификация.
3. **Шлюз, принадлежащий коду,** применяет разрешения и лимиты до любого запуска. Выбор маршрута сам по себе ничего не разрешает.
4. **Исполнитель действует** — пока в рамках только контролируемый браузерный исполнитель.
5. **Верификатор проверяет цель.** Запуск считается выполненным, только если верификатор это подтвердил; иначе он останавливается с причиной или возвращает задачу вызывающему агенту.

## Быстрый старт

Python 3.11+. Из клона (Bash; эквиваленты для PowerShell — в разделе [Запуск](#запуск)):

```sh
python -m venv .venv
.venv/bin/python -m pip install -e .
.venv/bin/reflexmesh route --input examples/route-task.json
```

Пример входных данных объявляет `CUA` и `LLM` и возможными, и разрешёнными. Вывод заглушки по умолчанию выглядит так:

```json
{"schema_version": "0.1", "task_id": "browser-demo", "status": "selected", "route": "CUA", "eligible_routes": ["CUA", "LLM"], "reason_code": "stub_fixed_order", "provider": "stub", "is_stub": true, "execution_performed": false, "confidence": null}
```

Это фиксированный порядок заглушки, а не анализ цели, и ничего не было выполнено. Чтобы маршрутизировать через настоящий JevRouter, см. [JevRouter (V0.2)](#jevrouter-v02). Запуск тестов: `python -m unittest discover -s tests -v`.

## Запуск

Python 3.11+. Установка в виртуальное окружение (Bash):

```sh
python -m venv .venv
.venv/bin/python -m pip install -e .
.venv/bin/reflexmesh route --input examples/route-task.json
```

PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\reflexmesh.exe route --input examples/route-task.json
```


Без установки пакета (Bash):

```sh
PYTHONPATH=src python -m reflexmesh route --input examples/route-task.json
```

PowerShell без установки:

```powershell
$env:PYTHONPATH = "src"
python -m reflexmesh route --input examples/route-task.json
```

`--input -` читает JSON из stdin. По умолчанию используется stub:
маршрут выбирается из пересечения
`capabilities` и `allowed_routes` в порядке CUA, LLM, PERCEPTION.
Заглушка не анализирует цель; поле `provider` равно `stub`, `is_stub=true`,
`execution_performed=false`, `confidence=null`. Объявление возможностей
не означает, что исполнители подключены. Результат не является выполнением задачи.

Коды выхода: `0` — маршрут выбран, `3` — отказ, `4` — требуется подтверждение,
`5` — ошибка адаптера/провайдера, `2` — ошибка ввода.
Решение (включая `failed` от адаптера, exit 5) — JSON в stdout.
Ошибка аргументов/чтения/валидации (exit 2) — JSON в stderr, stdout пуст.
`--help` и `--version` выводят обычный текст.

## JevRouter (V0.2)

Заглушка по умолчанию сохранена; реальная интеграция включается явно.
Установите upstream отдельно (Node.js 20+, Git):

```sh
git clone https://github.com/BillionsBobby/JevRouter.git
cd JevRouter
git checkout f944acb6530621bced023352e2358a63218bf4d9
npm ci --ignore-scripts
npm run build
node dist/cli.js serve --provider openrouter --port 8787
```

Перед запуском сервера задайте в его окружении `OPENROUTER_API_KEY`.
Его можно создать на [странице ключей OpenRouter](https://openrouter.ai/settings/keys):
отдельного ключа JevRouter нет. Если у вас уже есть прямой ключ TypeSafe,
задайте `TYPESAFE_API_KEY` или `JEV_API_KEY` и используйте `--provider typesafe`.
Ключи не передаются в Task или CLI ReflexMesh.
Сервер использует собственную policy и сохраняет receipts в `.jevrouter/`
своего рабочего каталога; учитывайте это при выборе каталога и содержимого задач.
При настоящем провайдере goal передаётся облачной модели.

Во втором терминале из каталога ReflexMesh, после установки в `.venv` (Bash):

```sh
.venv/bin/python -m reflexmesh route --provider jevrouter --input examples/route-task.json
```

В PowerShell используйте `.\.venv\Scripts\python.exe -m reflexmesh` с теми же аргументами.

Доступны `--jev-url http://127.0.0.1:8787` и `--timeout 30` (socket I/O,
не общий deadline). При ошибке модель не заменяется заглушкой. При ответе
`needs_confirmation` дальнейшие действия не выполняются. Адаптер предлагает Jev
кандидата `NONE`: если ни один разрешённый маршрут не подходит, ответ —
`abstained` с `upstream_no_fitting_route` ([ADR-0003](docs/architecture/ADR-0003-none-candidate-refusal.md)).
`--no-none-candidate` возвращает прежнее поведение.

Без ключа можно запустить upstream с `--provider demo`, а клиент с
`--allow-demo`. Ответ будет помечен `is_stub=true`. Без этого флага demo отклоняется.
Пример с двумя маршрутами может дать честный отказ по низкой оценке.

Проверка интеграции без ключей после сборки upstream:

```sh
python scripts/check_jevrouter_http.py --upstream-dir /path/to/JevRouter
```

Скрипт сам запускает и завершает локальный demo server во временном каталоге.
