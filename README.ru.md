<h1 align="center">ReflexMesh</h1>

<p align="center"><b>Слой решений и контроля для AI-агентов: направляйте каждую задачу к способу выполнения (API, CLI, модель или браузер) с измеренной маршрутизацией и честным отказом, держите выполнение в рамках разрешений и лимитов под управлением кода и считайте задачу выполненной, только когда это подтвердил verifier. Сегодня: маршрутизация, исследование маршрутизации и spike контролируемого браузерного runtime. Ранний исследовательский код для тех, кто строит агентов.</b></p>

```sh
python -m venv .venv && .venv/bin/python -m pip install -e .
.venv/bin/reflexmesh route --input examples/route-task.json
```

ReflexMesh — универсальный слой принятия решений и координации выполнения
для AI-агентов: выбор инструментов и исполнителей, контроль ограничений и
проверяемый результат. Целевые пути включают API/MCP tools, CLI/скрипты,
модели и агентов, computer use, макросы и workflows.
Jev предназначен для ограниченного выбора, LLM — для планирования и генерации
содержания; код контролирует разрешения и выполнение, verifier проверяет результат.
Браузер — первый прикладной сценарий; desktop добавляется после V1.0.
Интерактивные интерфейсы не определяют границ проекта.
Это целевая концепция; её текущий реализованный объём описан ниже.

**Что есть сегодня:** три вещи. **Маршрутизация** — задача на входе, JSON-решение о маршруте на выходе: от заглушки с фиксированным порядком по умолчанию или от настоящего JevRouter по HTTP, с честным отказом, когда ни один разрешённый маршрут не подходит; только это — поставляемая продуктовая поверхность. **Измеренное исследование маршрутизации** — замороженные протоколы, размеченные наборы данных и датированные отчёты, сравнивающие написанные вручную правила, Jev и LLM и проверяющие поведение при отказе. **Контролируемый браузерный runtime** — экспериментальный `reflexmesh run`, который выполняет одну ограниченную подзадачу на локальном сайте-фикстуре под разрешениями, лимитами, отменой и verifier, которыми владеет код; его приёмочные gates всё ещё открыты. Вокруг этого — система документации (north star, целевая архитектура, шестнадцать инвариантов, дорожная карта, статус, ADR, спецификации и исследовательские отчёты). Исполнители API/MCP, CLI, desktop, макросов и workflow — целевые направления, а не интеграции; см. [Статус](#статус).

Это ранний исследовательский код: у пакета нет runtime-зависимостей, ничто здесь не выполняет произвольную задачу, а выбранный маршрут — рекомендация, а не выполненная работа. [Статус и известные ограничения](#статус) точно говорят, что измерено, а что нет.

## Простыми словами

### Проблема

У AI-агента, которого просят что-то сделать, обычно несколько способов: вызвать API или инструмент MCP, запустить скрипт, спросить модель или управлять браузером. Какой способ лучше, зависит от того, что доступно, что разрешено, сколько это стоит и можно ли проверить результат. На практике всё это отдаётся на импровизацию модели: она выбирает путь, решает, что ей позволено, и объявляет «готово» на собственное слово. Запуск в браузере может завершиться «успешно», хотя форма так и не была отправлена, а агент, который не может выполнить задачу, нередко всё равно выбирает ближайший неверный инструмент вместо того, чтобы так и сказать.

### Для кого это

- **Люди, строящие агентов**, которым нужен тонкий слой решений рядом с их агентом (первый предполагаемый клиент — Pi), а не ещё один фреймворк агентов.
- **Исследователи**, которые хотят увидеть на замороженных протоколах и опубликованных числах, может ли небольшая модель маршрутизации заменить LLM в решении «каким способом?».
- **Контрибьюторы**, которым важны гарантии, которые должен сохранять слой выполнения: разрешения под контролем кода, ограниченные попытки, успех, подкреплённый свидетельствами.

### Что вы получаете

- **Решение о маршруте с честной пометкой.** Строгая Task на входе; JSON-решение на выходе с ясным статусом (выбран, отказ, нужно подтверждение, ошибка адаптера), кодом причины и различимыми кодами выхода. Провайдер по умолчанию сообщает, что он заглушка, и ничего не выполняет.
- **Настоящая маршрутизация через JevRouter, когда вы включите её сами.** Небольшая модель маршрутизации выбирает среди маршрутов, которые разрешает задача; если ни один не подходит, она может так и сказать, а ошибка никогда не прикрывается заглушкой.
- **Числа вместо заявлений.** Маршрутизация оценивалась по замороженному протоколу, а поведение при отказе — отдельно; отчёты называют набор данных, образец для сравнения и ограничения.
- **Рабочий пример контролируемого runtime** (экспериментальный). Одна браузерная подзадача выполняется под разрешениями, лимитами шагов и вызовов модели, дедлайном и отменой, которыми владеет код, и считается завершённой, только если verifier подтвердил цель по свидетельствам фикстуры, включая наблюдение браузера для `current_page`.
- **Записанная дисциплина.** Инварианты, архитектурные решения и поэтапные спецификации фиксируют, что обязан сохранять любой будущий исполнитель.

### Чем это не является

- Не готовый фреймворк агентов, не ваша собственная LLM и не новая RPA-платформа: это тонкий слой решений и экспериментальный runtime вокруг существующих компонентов.
- Не исполнитель задач: произвольное выполнение задач сегодня не поставляется. Выбранный маршрут — рекомендация; браузерный runtime — контролируемый spike на сайте-фикстуре.
- Не обещает офлайн-работу и кроссплатформенность: путь через Jev предполагает облачного провайдера, а `reflexmesh run` требует POSIX-среды (Linux или WSL).
- Не измеренное утверждение о computer use: исследование измеряло только маршрутизацию, а у runtime V0.5 пока нет завершённой приёмочной матрицы качества выполнения и измерения стоимости модели.
- Не хаб интеграций: маршруты API/MCP, CLI, desktop, макросов и workflow на целевой картинке — направления, а не коннекторы.

### Глоссарий

| Термин | Что значит здесь |
|---|---|
| **Маршрут (route)** | Класс способа выполнить задачу. Текущий каталог — `CUA` (computer use), `LLM` и `PERCEPTION`; это экспериментальный набор для V0, а не окончательная классификация. |
| **Task** | Строгий JSON-вход для маршрутизации: идентификатор, цель, маршруты, на которые система способна, и маршруты, которые разрешены. |
| **Capabilities / allowed routes** | Объявления, а не проверки: capabilities говорят, что можно было бы использовать, allowed routes — что можно использовать. Ни то ни другое не проверяет, что исполнитель подключён. |
| **Заглушка (stub)** | Маршрутизатор по умолчанию: берёт первый подходящий маршрут в фиксированном порядке и никогда не читает цель. |
| **Jev / JevRouter** | Небольшая модель маршрутизации и локальный HTTP-сервис, который её обслуживает; внешний проект, с которым общается ReflexMesh. |
| **Кандидат NONE** | Вариант «ничто из этого не подходит», который адаптер предлагает Jev и который превращает плохое совпадение в честный отказ. |
| **Verifier** | Код, который проверяет цель по свидетельствам, например по состоянию на стороне сервера; запуск считается завершённым, только когда он подтвердил. |
| **TextSlot** | Версионируемый неизменяемый фрагмент текста (`name@1`), который предоставляет задача и который может ввести действие, чтобы модель не придумывала содержание. |
| **Супервизор попытки** | Часть runtime, которая владеет допуском, лимитами, отменой и терминальным статусом одной попытки выполнения. |
| **Сайт-фикстура (fixture site)** | Локальный изолированный тестовый сайт с идентификатором запуска и журналом событий, который читает verifier. |

## Что внутри

Метки статуса: без метки — реализовано в этом репозитории; **experimental** — реализовано, но с открытыми приёмочными gates или только в объёме фикстуры; **research** — записанное исследование, а не функция; **planned / target** — не построено.

### Маршрутизация (поставляемая поверхность)

- **Явные контракты.** Строгая `Task` (ровно пять полей, не более 64 КиБ, дубликаты ключей и нечисловые значения отклоняются) и JSON `RoutingDecision` со статусом `selected` / `abstained` / `needs_confirmation` / `failed`, кодом причины и различимыми кодами выхода `0` / `3` / `4` / `5` / `2`. → [Маршрутизация подробно](#маршрутизация-подробно)
- **Честная заглушка по умолчанию.** Провайдер по умолчанию выбирает из пересечения `capabilities` и `allowed_routes` в фиксированном порядке и помечает себя `is_stub=true`, `execution_performed=false`; он никогда не анализирует цель. → [Запуск](#запуск)
- **Настоящая маршрутизация через JevRouter.** Включаемый явно HTTP-адаптер к локальному JevRouter (только loopback); при любой ошибке модель **не** подменяется молча заглушкой. Live-gate V0.2 закрыт для OpenRouter; прямой typesafe не проверен. → [Настройка JevRouter](#jevrouter-v02)
- **Честный отказ.** Адаптер предлагает Jev кандидата `NONE`, так что «ни один разрешённый маршрут не подходит» становится решением `abstained` с `upstream_no_fitting_route`; `--no-none-candidate` возвращает прежнее поведение. → [Свидетельства и эксперименты](#свидетельства-и-эксперименты)
- **Контроль под управлением кода.** Выбор маршрута никогда не санкционирует действие; отправка форм, публикация и другие внешние эффекты не разрешаются самим выбором. → [Зачем ReflexMesh?](#зачем-reflexmesh)

### Свидетельства и исследования

- **Измерено, а не предположено.** Маршрутизация оценивалась по фиксированному протоколу (V0.3, вердикт «useful»), а поведение при отказе — отдельно (V0.3b); результаты и их ограничения опубликованы в [`docs/research/`](docs/research/). → [Свидетельства и эксперименты](#свидетельства-и-эксперименты)
- **Live-свидетельства и проверка без ключей.** Live-маршрутизация через OpenRouter задокументирована (V0.2); `scripts/check_jevrouter_http.py` проверяет интеграцию на локальном демо-сервере без ключей. → [Проверки](#проверки)
- **Воспроизводимые скрипты.** Замороженные наборы данных и протоколы в `experiments/` и скрипты запуска и оценки в `scripts/` перезапускают исследования маршрутизации. → [Справочник](#справочник)

### Контролируемый браузерный runtime (experimental)

- **`reflexmesh run`.** Выполняет одну ограниченную браузерную подзадачу на сайте-фикстуре в loopback; вход — строгий `execution-task/0.1`, провайдеры маршрутизации и действий задаются явно, а результат — один JSON плюс `result.json`, `trace.jsonl` и `evidence.jsonl`. → [Среда выполнения](#среда-выполнения-экспериментально)
- **Лимиты под управлением кода.** Дедлайн по часам, лимиты шагов и вызовов модели, отмена по SIGINT, рабочий процесс с ограниченным периодом ожидания и записанные неизвестные эффекты. → [Среда выполнения](#среда-выполнения-экспериментально)
- **Разрешения, TextSlots и verifier.** Семь именованных разрешений, неизменяемые версионируемые текстовые слоты и пять предикатов постусловий, проверяемых по свидетельствам сервера-фикстуры или, для `current_page`, наблюдению браузера; `completed` назначает runtime, а не harness. → [Среда выполнения](#среда-выполнения-экспериментально)
- **Spike и записанные детерминированные проверки.** Spike V0.4 SystemOneHarness + Browser Use под запретом, отменой и дедлайном runtime прошёл свои проверки; исторический отчёт детерминированной (U) приёмки V0.5 содержит 36 из 36 запланированных подслучаев с результатом pass и [оговорками о происхождении исходников и покрытии C12](docs/research/V0.5-U-acceptance.md#static-review-addendum-2026-10-07); приёмочные подслучаи с реальным браузером (B) и живым Jev (J) ожидают. → [Статус](#статус)

### Система документации

- **Направление, ограничения и свидетельства — в отдельных документах.** North Star, целевая архитектура, шестнадцать инвариантов (`INV-01`..`INV-16`), дорожная карта V0 → V2.0, статус, три ADR, спецификации V0.1–V0.5, исследовательские отчёты и руководства. → [Направление и документы](#направление-и-документы)

### Ещё не построено

- **Исполнители помимо браузерного spike** — прямые инструменты API/MCP, CLI/скрипты, модели и агенты как исполнители, desktop, макросы, workflow: **целевые направления**, а не интеграции. → [Направление и документы](#направление-и-документы)
- **Интерфейс задач** — Task API по MCP/HTTP, интеграция с Pi и handoff (планируется на V0.6); каталоги `integrations/` — пустые заготовки. → [Статус](#статус)
- **Восприятие (OCR/accessibility), ClawBridge, Skyvern, Ui.Vision, адаптеры Cua, супервизор мезо-уровня, восстановление и долговечное хранилище квитанций** — **planned**; соответствующие модули в `src/` — пустые заготовки.
- **Обнаружение возможностей и саморасширение** — только будущее направление ([`docs/architecture/FUTURE_SELF_EXTENSION.md`](docs/architecture/FUTURE_SELF_EXTENSION.md)).

## Как это работает

<p align="center">
  <img src="docs/assets/ReflexMesh-how-it-works.png" alt="ReflexMesh: пользователь передаёт новую задачу роботу-маршрутизатору, который выбирает один инструмент из API, браузера, desktop и CLI; verifier проверяет результат и останавливает линию, пока нет доказательств" width="100%">
</p>

Картинка показывает целевой дизайн. Из нарисованных инструментов строится только контролируемый браузерный путь; остальные — направления, а не реализованные интеграции.

1. **Задача приходит** от агента. Pi — первый предполагаемый клиент, но ядро от него независимо, так что другие агенты и программы могут присылать те же задачи.
2. **Маршрутизатор выбирает маршрут** из тех, что задача объявляет разрешёнными. Это ограниченный выбор делает Jev; текущий каталог CUA / LLM / PERCEPTION — экспериментальный набор для V0, а не окончательная классификация.
3. **Шлюз под управлением кода** проводит в жизнь разрешения и лимиты до того, как что-либо запустится. Выбор маршрута сам по себе ничего не санкционирует.
4. **Исполнитель действует** — пока в объёме только контролируемый браузерный исполнитель.
5. **Verifier проверяет цель.** Запуск считается завершённым, только если verifier это подтвердил; иначе он останавливается с причиной или возвращает задачу вызывающему агенту.

### Что работает сегодня

| Шаг | Сегодня |
|---|---|
| 1. Задача | `reflexmesh route` читает JSON Task (файл или stdin); `reflexmesh run` читает `execution-task/0.1`. |
| 2. Маршрутизатор | Заглушка или включаемый явно адаптер JevRouter возвращает решение; результат — рекомендация. |
| 3. Шлюз | В runtime: список разрешений, лимиты и порядок отмены обеспечиваются кодом в одной контролируемой попытке. |
| 4. Исполнитель | Только `browser.soh` (SystemOneHarness + Browser Use) на сайте-фикстуре в loopback, необязательная закреплённая зависимость. |
| 5. Verifier | Read-only verifier фикстуры; другого verifier нет. |

## Быстрый старт

Python 3.11+. Из клона (Bash; эквиваленты для PowerShell — в разделе [Запуск](#запуск)):

```sh
python -m venv .venv
.venv/bin/python -m pip install -e .
.venv/bin/reflexmesh route --input examples/route-task.json
```

Пример входных данных объявляет `CUA` и `LLM` и возможными, и разрешёнными. Вывод заглушки по умолчанию выглядит так:

```json
{"schema_version": "0.1", "task_id": "browser-demo", "status": "selected", "route": "CUA", "eligible_routes": ["CUA", "LLM"], "reason_code": "stub_fixed_order", "provider": "stub", "is_stub": true, "execution_performed": false, "confidence": null}
```

Это фиксированный порядок заглушки, а не анализ цели, и ничего не было выполнено. Чтобы маршрутизировать через настоящий JevRouter, см. [JevRouter (V0.2)](#jevrouter-v02). Запуск тестов: `python -m unittest discover -s tests -v`.

## Зачем ReflexMesh?

- **Если** ваш агент может выполнить работу несколькими способами — прямым API или MCP tool, скриптом, моделью, браузером, — **то** ReflexMesh призван выбирать среди разрешённых вами способов и оставлять владение разрешениями и выполнением коду, а не модели.
- **Если** «агент говорит, что готово» вас не устраивает, **то** здесь статус завершения назначает runtime, и он принимается только когда верификатор подтвердил цель. Spike V0.4 показал, зачем это нужно: собственный статус `completed` у harness ошибался в обе стороны, а верификатор по состоянию сервера оба раза в наблюдавшихся случаях был прав.
- **Если** вам нужен честный ответ «ни один из этих маршрутов не подходит», **то** адаптер предлагает Jev кандидата `NONE`; в исследовании V0.3b это подняло долю корректных отказов Jev с 22% (прежний адаптер) до 96% на тех же кейсах отказа, без потерь на обычных задачах (25% в отчёте V0.3 — отдельная выборка из 8 кейсов того исследования).
- **Если** маршрутизация должна быть дешёвой и быстрой, **то** исследование V0.3 сообщает для Jev точность 1.00 (как у gpt-5.5) против 0.65 у ручных правил, а в сравнении с эталоном gpt-5.5 — медианную задержку Jev 0.6 с против 6.4 с и стоимость примерно $0.00002 против $0.002 за решение (правила быстрее и бесплатны, но намного слабее на перефразированных задачах) — цифры записаны в [`docs/STATUS.md`](docs/STATUS.md) и [отчёте V0.3](docs/research/V0.3-routing.md).

Это **не** готовый фреймворк для агентов, не собственная LLM и не новая RPA-платформа; это тонкий интеграционный runtime и слой решений вокруг существующих компонентов. Сегодня не поставляется общее исполнение задач: выбранный маршрут — рекомендация, а не выполненная работа, а браузерный runtime пока остаётся контролируемым spike на тестовом сайте. Полностью офлайн-работа и поддержка всех ОС не обещаны — путь Jev предполагает облачного провайдера. Неподдерживаемая задача получает явный отказ или возвращается вызывающему агенту.

## Маршрутизация подробно

`reflexmesh route` — вся поставляемая поверхность. Она читает одну Task, просит провайдера о решении и печатает его как JSON; ничего не выполняется.

**Task 0.1** содержит ровно пять полей: `schema_version` (`"0.1"`), `task_id` (не более 128 символов), `goal` (не более 10 000 символов), `capabilities` и `allowed_routes` (уникальные значения из `CUA`, `LLM`, `PERCEPTION`). Отсутствующие или лишние поля, дубликаты ключей JSON, нечисловые значения и вход свыше 64 КиБ отклоняются. `capabilities` и `allowed_routes` — это объявления, а не проверки: они говорят, что можно и что разрешено использовать, и ни то ни другое не проверяет существование исполнителя.

**Решение** содержит `status`, `route`, `eligible_routes`, `reason_code`, `provider`, `is_stub`, `execution_performed` и `confidence`.

| Статус | Выход | Значение |
|---|---|---|
| `selected` | 0 | Маршрут выбран из подходящего набора (`stub_fixed_order` для заглушки, `upstream_selected` от Jev). |
| `abstained` | 3 | Подходящих маршрутов нет (`no_eligible_route`) или Jev не нашёл подходящего (`upstream_no_fitting_route`, `upstream_no_decision`). |
| `needs_confirmation` | 4 | JevRouter запросил подтверждение (`upstream_confirmation_required`); дальнейших действий не выполняется. |
| `failed` | 5 | Адаптер или провайдер дал сбой; решение всё равно печатается как JSON в stdout, а заглушка **не** подставляется. |
| (ошибка входа) | 2 | Неверный аргумент, ошибка чтения или валидации: JSON в stderr, stdout пуст. |

**Провайдеры.**

- *Заглушка* (по умолчанию): первый маршрут в порядке CUA, LLM, PERCEPTION, который одновременно возможен и разрешён; `provider` равен `stub`, `is_stub=true`, `confidence=null`.
- *JevRouter* (`--provider jevrouter`): HTTP-адаптер только для решений к локальному JevRouter по адресу `http://127.0.0.1:PORT` (только loopback, без proxy, редиректов и повторов; `--timeout` — таймаут сокетного ввода-вывода не более 120 с; ответы свыше 1 МиБ отклоняются). Он описывает Jev подходящие маршруты, фильтрует и проверяет ответ и по умолчанию дополнительно предлагает кандидата `NONE` ([ADR-0003](docs/architecture/ADR-0003-none-candidate-refusal.md)). Демо-upstream отклоняется, если не указан `--allow-demo`, и тогда помечается `is_stub=true`. Решение JevRouter использует `schema_version` `0.2` и добавляет `trace` (хэши запроса и ответа, затраченное время и сводку upstream); это трасса маршрутизации, а не журнал аудита.

**Известные границы** (из [`docs/STATUS.md`](docs/STATUS.md)): сервера задач ReflexMesh нет; адаптер делает только исходящие HTTP-вызовы к loopback-JevRouter; сокетный таймаут — не общий дедлайн и не подтверждает инвариант дедлайна будущего runtime; `is_stub=false` и происхождение от локального сервиса не доказывают обращения к модели; ответ `needs_confirmation` — лишь предложение, поскольку механизма подтверждения и последующего выполнения нет; трасса в stdout не является журналом аудита, а upstream хранит собственные квитанции.

## Среда выполнения (экспериментально)

`reflexmesh run` — минимальный контролируемый браузерный runtime V0.5. Это spike на сайте-фикстуре, а не способ запускать собственные задачи, и его приёмочные gates открыты. Один запрос выполняет одну ограниченную подзадачу: SystemOneHarness владеет внутренним циклом действий, Browser Use выполняет браузерные действия, а ReflexMesh владеет допуском, разрешениями, счётчиками, отменой, терминальными переходами и проверкой ([спецификация V0.5](docs/specs/V0.5.md)).

```bash
reflexmesh run --input task.json --output-dir ./evidence-001 \
  --routing-provider stub --action-provider script --script script.json
```

- **Вход.** JSON `execution-task/0.1` с `task_id`, `revision`, `goal`, `allowed_executors` (реализован только `browser.soh`), `fixture` (loopback-origin и идентификатор запуска), `start_path`, `permissions`, `text_slots`, `criteria` и `limits` (`wall_seconds`, `max_steps`, `max_model_calls`, `max_action_retries`, который должен быть равен 0). Лишние поля, дубликаты ключей и неверные ссылки отклоняются до любой попытки.
- **Разрешения.** `navigate`, `type_text`, `toggle_setting`, `save_settings`, `submit_form`, `start_export`, `delete_account`; действие вне списка задачи отклоняется до того, как достигнет браузера.
- **TextSlots.** Версионируемые неизменяемые тексты (`name@1`); действия ссылаются на слот, а не несут текст, и критерии могут ссылаться на слоты.
- **Критерии.** Четыре постусловия используют состояние и события сервера-фикстуры: `settings_saved`, `form_submitted_once`, `export_completed_once`, `account_intact`. Для `current_page` требуется соответствующее наблюдение браузера с текущим URL и целью; исторического GET на сервере недостаточно.
- **Провайдеры.** `--routing-provider stub|jevrouter` и `--action-provider script|jev`, оба задаются явно; `script` — детерминированная тестовая фикстура, передаваемая через `--script`.
- **Итог.** Один JSON в stdout и `result.json`, `trace.jsonl`, `evidence.jsonl` в выходном каталоге. `attempt_status` — `completed` (выход 0), `blocked` (3), `incomplete` (4), `failed` (5) или `cancelled` (130); ошибки входа и подготовки выходного каталога (до начала попытки) дают выход 2, а ошибка записи выходных файлов после запуска сообщается как `failed` с причиной остановки `output_error` и даёт выход 5. `task_outcome` равен `pass` только для завершённой попытки, у которой все проверки прошли. Успех никогда не берётся из собственного статуса harness.
- **Покрытие verifier.** Завершение проверяет реализованные постусловия и определённость эффектов действий. Из execution constraints выводится только `runtime.budget`; обязательные оценки разрешений, неизменности слотов, единоличного владения сессией, порядка dispatch и отсутствия повторов неясных действий пока отсутствуют. Результат `completed` не подтверждает полное соответствие спецификации V0.5 ([ревью](docs/research/V0.5-review-2026-09-25.md#3-ограничения-выполнения-8)).
- **Контроль.** Супервизор с дедлайном, который стартует до проверок доступности, маршрутизации и запуска; счётчики шагов и вызовов модели; шлюз диспетчеризации и отмены с определённым порядком; рабочий процесс с ограниченным ожиданием и очисткой; неразрешённые действия записываются как неизвестные эффекты, а не угадываются.
- **Настройка лимитов.** Главный временной бюджет — всё время работы системы над задачей, включая ожидание модели и проверку результата; он может составлять часы (`wall_seconds: 7200` — два часа). `null` отключает отдельный лимит времени, шагов или вызовов модели; `limits: null` либо `--no-limits` отключает все три. Ручная отмена, разрешения, проверка результата и ограниченная по времени очистка продолжают работать. Ноль не означает отсутствие лимита. Подробнее: [семантика и примеры](docs/guides/V0.5-local-run.md#task-budgets-hours-and-explicit-unlimited-mode).
- **Учёт роутера.** Роутер заменяем через общий интерфейс; пока реализованы только stub и JevRouter. `max_model_calls` ограничивает локально контролируемые запросы к провайдеру. JevRouter доступен и с конечным локальным лимитом, но его внутренние вызовы остаются неизвестными и неограниченными этим лимитом. Общее число отражается как `null`; один HTTP-запрос не выдаётся за один вызов модели или доказанный общий лимит. Подробнее: [возможности и учёт роутеров](docs/guides/V0.5-local-run.md#replaceable-routers-and-honest-model-call-accounting).
- **Платформа и зависимости.** Первая поддерживаемая среда — Linux или WSL со свежим браузерным процессом на каждую попытку, фикстурой в loopback и закреплёнными необязательными зависимостями (SystemOneHarness и Browser Use). Супервизор использует метод запуска `fork` из POSIX, поэтому `reflexmesh run` не стартует на нативной Windows (измерено на Windows с Python 3.13). CLI маршрутизации и тесты V0.1–V0.3 это не затрагивает.

Пошаговые локальные проверки, сервер фикстуры и манифест U описаны в [руководстве по локальному запуску V0.5](docs/guides/V0.5-local-run.md).

### Известные ограничения

- **Объявления — не проверки.** `capabilities` и `allowed_routes` — фильтр маршрутизации, а не проверка доступности исполнителя и не полноценная авторизация.
- **Маршрутизация общается только с loopback.** Сетевой путь адаптера маршрутизации — исходящий HTTP к локальному JevRouter; proxy, редиректов и повторов нет, как и сервера задач ReflexMesh. Таймаут сокетного ввода-вывода — не общий дедлайн.
- **Выбранный маршрут — рекомендация.** `needs_confirmation` возвращает предложение; механизма подтверждения и последующего выполнения нет. Автоматического возврата к заглушке нет.
- **Свидетельства ограничены объёмом.** Числа тестов и конфигурации относятся к прогонам, названным в отчётах; обновление документации — не новый прогон. Прямой typesafe вживую не проверялся.
- **Gate runtime открыт.** [Независимое ревью](docs/research/V0.5-review-2026-09-25.md) описывает один smoke формы в настоящем Chromium и пробы selector-map/идентичности узлов на `fe088e6`. Эти исторические наблюдения не закрывают обязательную матрицу B; B и J ожидают. Идентичность документа/фрейма, enabled, назначение формы, ревизия политики и полный набор оценок execution constraints остаются неполными. Падение воркера при удержании блокировки gate и полное время очистки дерева процессов не продемонстрированы; стоимость модели не измерена. Runtime требует Linux или WSL.
- **Покрытие инвариантов частичное.** Маршрутизация и CLI работают без Pi; остальные инварианты — требования к следующим этапам, а соответствие путей выполнения пока не установлено.

Без установки пакета (Bash):

```sh
PYTHONPATH=src python -m reflexmesh route --input examples/route-task.json
```

PowerShell без установки:

```powershell
$env:PYTHONPATH = "src"
python -m reflexmesh route --input examples/route-task.json
```

`--input -` читает JSON из stdin. По умолчанию используется stub:
маршрут выбирается из пересечения
`capabilities` и `allowed_routes` в порядке CUA, LLM, PERCEPTION.
Заглушка не анализирует цель; поле `provider` равно `stub`, `is_stub=true`,
`execution_performed=false`, `confidence=null`. Объявление возможностей
не означает, что исполнители подключены. Результат не является выполнением задачи.

Коды выхода: `0` — маршрут выбран, `3` — отказ, `4` — требуется подтверждение,
`5` — ошибка адаптера/провайдера, `2` — ошибка ввода.
Решение (включая `failed` от адаптера, exit 5) — JSON в stdout.
Ошибка аргументов/чтения/валидации (exit 2) — JSON в stderr, stdout пуст.
`--help` и `--version` выводят обычный текст.

## JevRouter (V0.2)

Заглушка по умолчанию сохранена; реальная интеграция включается явно.
Установите upstream отдельно (Node.js 20+, Git):

```sh
git clone https://github.com/BillionsBobby/JevRouter.git
cd JevRouter
git checkout f944acb6530621bced023352e2358a63218bf4d9
npm ci --ignore-scripts
npm run build
node dist/cli.js serve --provider openrouter --port 8787
```

Перед запуском сервера задайте в его окружении `OPENROUTER_API_KEY`.
Его можно создать на [странице ключей OpenRouter](https://openrouter.ai/settings/keys):
отдельного ключа JevRouter нет. Если у вас уже есть прямой ключ TypeSafe,
задайте `TYPESAFE_API_KEY` или `JEV_API_KEY` и используйте `--provider typesafe`.
Ключи не передаются в Task или CLI ReflexMesh.
Сервер использует собственную policy и сохраняет receipts в `.jevrouter/`
своего рабочего каталога; учитывайте это при выборе каталога и содержимого задач.
При настоящем провайдере goal передаётся облачной модели.

Во втором терминале из каталога ReflexMesh, после установки в `.venv` (Bash):

```sh
.venv/bin/python -m reflexmesh route --provider jevrouter --input examples/route-task.json
```

В PowerShell используйте `.\.venv\Scripts\python.exe -m reflexmesh` с теми же аргументами.

Доступны `--jev-url http://127.0.0.1:8787` и `--timeout 30` (socket I/O,
не общий deadline). При ошибке модель не заменяется заглушкой. При ответе
`needs_confirmation` дальнейшие действия не выполняются. Адаптер предлагает Jev
кандидата `NONE`: если ни один разрешённый маршрут не подходит, ответ —
`abstained` с `upstream_no_fitting_route` ([ADR-0003](docs/architecture/ADR-0003-none-candidate-refusal.md)).
`--no-none-candidate` возвращает прежнее поведение.

Без ключа можно запустить upstream с `--provider demo`, а клиент с
`--allow-demo`. Ответ будет помечен `is_stub=true`. Без этого флага demo отклоняется.
Пример с двумя маршрутами может дать честный отказ по низкой оценке.

Проверка интеграции без ключей после сборки upstream:

```sh
python scripts/check_jevrouter_http.py --upstream-dir /path/to/JevRouter
```

Скрипт сам запускает и завершает локальный demo server во временном каталоге.

### Команды и коды выхода

| Команда | Что делает | Коды выхода |
|---|---|---|
| `reflexmesh route [--input FILE\|-] [--provider stub\|jevrouter] [--jev-url URL] [--timeout S] [--allow-demo] [--no-none-candidate]` | Только маршрутизация; печатает JSON RoutingDecision | `0` выбран, `3` отказ, `4` нужно подтверждение, `5` ошибка адаптера или провайдера, `2` ошибка входа |

### Коды отказа адаптера JevRouter

Когда адаптер даёт сбой, у решения `status` равен `failed`, а код причины — один из: `http_error`, `response_too_large`, `transport_timeout`, `transport_error`, `unsupported_provider`, `demo_not_allowed`, `provider_error`, `invalid_response`.

### Система документации

У каждого вида сведений свой источник: цель — [North Star](docs/NORTH_STAR.md), концепция — [целевая архитектура](docs/architecture/TARGET_ARCHITECTURE.md), обязательные ограничения — [инварианты](docs/architecture/INVARIANTS.md) (`INV-01`..`INV-16`), порядок работ — [дорожная карта](docs/ROADMAP.md), а что реально работает — [`docs/STATUS.md`](docs/STATUS.md) со связанными отчётами. У каждого инкремента есть спецификация в `docs/specs/`; изменение инварианта оформляется как ADR ([ADR-0001](docs/architecture/ADR-0001-invariant-review.md), [ADR-0002](docs/architecture/ADR-0002-routing-effects-and-loop-control.md), [ADR-0003](docs/architecture/ADR-0003-none-candidate-refusal.md)). ## Устранение неполадок

| Симптом | Что это значит и что делать |
|---|---|
| `reflexmesh run` падает с `cannot find context for 'fork'` | Runtime выполнения использует метод запуска `fork` из POSIX. Запускайте его на Linux или WSL; CLI маршрутизации на Windows работает. |
| `reflexmesh run` сообщает `blocked` с `executor_unavailable` | Нет необязательных закреплённых SystemOneHarness, Browser Use или бинарника Chromium. Блокировка — это не успешный браузерный запуск; см. [руководство по локальному запуску V0.5](docs/guides/V0.5-local-run.md). |
| `route --provider jevrouter` завершается с кодом 5 | Адаптер не получил корректный ответ (см. коды отказа выше). Заглушка намеренно не подставляется; проверьте, что JevRouter запущен на loopback-адресе, который вы передали, и что ключ его провайдера задан в его собственном окружении. |
| `demo_not_allowed` | Upstream — демо-провайдер. Передайте `--allow-demo`, чтобы принять его (ответ тогда помечается `is_stub=true`), либо запустите upstream с настоящим провайдером. |
| «JevRouter endpoint must be http://127.0.0.1:PORT» | Адаптер принимает только loopback HTTP, без учётных данных, запроса и фрагмента в URL. |
| Опции заглушки отклоняются | `--jev-url`, `--timeout`, `--allow-demo` и `--no-none-candidate` требуют `--provider jevrouter`. |
| Маршрут `selected`, но ничего не произошло | Так задумано: маршрутизация — это не выполнение. Выбранный маршрут — рекомендация, а `execution_performed` равен `false`. |
| `route` завершается с кодом 2 и ничего не печатает в stdout | Ошибка аргумента, чтения или валидации: JSON с ошибкой — в stderr. Текст задачи намеренно не повторяется. |
