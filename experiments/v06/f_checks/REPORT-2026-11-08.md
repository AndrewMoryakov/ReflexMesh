## The headless shell, traced (later on 2026-11-08)

With Playwright's `chrome-headless-shell` 1243, four tests failed where Edge 144 and Chrome 142 pass: the three F06
lost-response tests and the F11 test of a frame of another origin. Traced on the shell, none is a safety failure;
the shell takes another lawful path:

- It does not resend the lost POST: one POST and one submission id for one click, where Chrome and Edge deliver the
  same request two or three times. ReflexMesh's code is the same in both, so the resend found in F06 belongs to the
  browser's network layer, not to the driver.
- Going back or restarting reloads the order page, which already shows the saved note, so the loop stops for
  verification and settles `completed/verified` on the one POST before any second Save is proposed. Chrome and Edge
  restore the page without the note; the second Save is proposed and refused as `repeated_mutation`.
- The frame of another site (localhost) is loaded in process, so its nodes are read and dropped by the origin rule
  instead of never being read. Nothing is offered and nothing reaches it either way.

The tests now hold the invariant on either path (`d5cc079`): one Save dispatched, the form sent once, a resent request
never settled as completed, a second Save refused if it is proposed; nothing of another origin's frame offered or
reached, with the process assertion kept only for another port of the same site, which is always in process.

Two timing issues showed up in the repeated passes. The expired-lease test read the site's claim after a fixed 2.5 s
while closing stops the browser before releasing it; it now waits up to 10 s (`5e6da30`). The dropdown-and-checkbox

## Secret values in the driver's log (later on 2026-11-08)

Closing the partial F12 item "sentinel secrets absent from ordinary logs" (its tests read the trace, the result and the
provider payload, not the output streams) found that it fails on `main`. Browser Use's type watchdog logs
`Typed "<text>"` at INFO on the session's logger whenever the call carries no `sensitive_data`, and ReflexMesh never
passes it (its placeholder rewriting would change the value). Browser Use enables INFO for its loggers on import. One
`reflexmesh browser run` with a secret note slot on `efadaf0` (Edge 144) had the secret once in stderr and nowhere in
stdout, the result, the trace or the other output files; a normal slot value showed the same way. In a whole ledger
pass, the only log lines holding one of the three slot values searched for (the secret, the note, the word `kiwi`)
are these. Read from the code, not run: the Task API keeps a run's stderr in the attempt's `stderr.log`, and the
browser service writes to its own stderr.

The fix is on its own branch from `main`, `fix/v0.6-typed-text-log`: before handing text to `Tools.act`, the dispatch
raises the `browser_use` logger to WARNING and refuses (`adapter_contract_unsupported`) if the session's logger would
still emit INFO, the rule it already applied to the DEBUG log and Laminar. Its three tests fail without the fix and
pass with it (the boundary unit test in WSL; on Edge 144 the `browser_use` log captured during the secret-slot run,
with that logger set to INFO as a plain command-line run has it, and the output streams of `reflexmesh browser run`).
With the fix, the two browser modules (76 tests) passed in three of three passes on Edge 144 with no `Typed` line in
any pass log (on the fix's first form, whose tests differed only in how the log is captured), and the Linux suite
(WSL) has no failures beyond the five fixed in PR #22. After the first typed text, Browser Use's other INFO lines
(navigation, tabs) no longer reach stderr in that process; the run's trace records those steps.

Not established: the V0.5 fixture path (`FixtureBrowser`, the Task API's typing path) goes through the same guard,
and its real-browser tests are Linux-only with Chrome, so none of them ran with the fix.

The item now lists the command-line test, which exists only on that branch: until it is merged, this ledger reports
the item as failed, which is its true state on `main`.

The dropdown-and-checkbox test, open above, passed in each of these three passes as well: nine passes in a row on Edge
since `efadaf0`, against three failures in six slow passes on `5e6da30`. Still not explained.

## Three more partial items (later on 2026-11-08)

- F02, a whole document navigated between observation and dispatch: the order page is observed, then reloaded (the
  very same Save button again) and then replaced by another order's page (a button of the same name). Each time the
  click proposed on the earlier observation is refused as `stale_target` and nothing is posted
  (`test_a_document_navigated_after_the_observation_makes_its_target_stale`). Closed.
- F03, a new slot version against an old observation: under revision 1 the note field is observed; the operator stops,
  revises the note to `note@2` and resumes in the same session. `note@2` on the earlier observation is refused
  (`stale_observation`), the old `note@1` on the new observation is refused (`unknown_slot`), and `note@2` on the new
  one goes through (`test_a_new_slot_version_is_not_applied_to_an_observation_made_before_the_revision`). Closed.
- F05, no commit after terminal and the liveness bound. Every terminal transition seals dispatching, and a click after
  it commits nothing (`dispatches_sealed`); with the cancel and deadline tests that covers the terminal states. A spent
  step budget is not one of them: the observation spends the step, and that step's own action may follow, after which
  the loop ends and seals. The bound on close failed on `main`: with the driver's close replaced by a 60 s sleep, the
  result came 60.5 s after the close was entered, where section 9 allows 8 s. The supervisor started its bound only on
  an accepted cancel or deadline, so a close that hangs after the loop ends on its own held the result up to the
  deadline. The fix is on `fix/v0.6-close-liveness`: the worker marks the attempt's end before closing the provider and
  the session, the supervisor runs the same bound from that mark, and a session the watchdog killed is never handed
  over. Its test fails without the fix (60.5 s) and passes with it.

On `fix/v0.6-close-liveness`, the three browser modules (109 tests) passed in two of three passes on Edge 144. In the
first, `test_an_expired_lease_closes_the_browser_and_kills_the_token` found no retained session. Alone it passed five
of five with and without the fix, and the whole handoff module passed with it. Its lease is 1 s from the token's issue,
so a slow return can close the chain before the test reads it, as it could on `main`. The fix could also cause this
in one case: if the worker takes more than 5 s after its loop ends, the watchdog kills the session, and a killed
session is not handed over. Which of the two happened is not established. That test passed in the twelve earlier passes
without the fix.
